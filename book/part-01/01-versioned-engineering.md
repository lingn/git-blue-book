# 没有版本控制时，我们到底在怕什么

软件项目最难回忆的通常不是“现在的文件长什么样”，而是“它为什么变成这样”。只保留一个最终目录，无法解释中间的决定；只保留很多副本，又会让人分不清哪些文件可以信任。

## 一个熟悉的文件夹

假设你维护一份项目方案，几轮修改后目录里出现：

~~~text
方案.md
方案-final.md
方案-final-2.md
方案-客户确认版.md
方案-真的最终版.md
~~~

这些文件说明你意识到旧内容可能有价值，但它们没有形成可靠历史。你仍然很难回答：

- 哪个版本是当前工作的基线；
- 两个版本究竟差了什么；
- 某段逻辑是谁、什么时候、为什么改的；
- 怎样只撤销一次错误修改而保留之后的正确修改；
- 两个人同时修改后，哪些内容来自哪一方；
- 发布时使用的文件是否就是经过评审的那一版。

文件名能表达意图，却不能建立关系。日期能提供线索，却不能说明一条变化是从哪个版本发展而来。

## 版本控制的工作定义

本书把版本控制定义为：用可识别的历史节点记录一组文件和相关元数据，使人能够比较变化、解释来源、恢复状态，并在多人之间整合修改。

一个有用的历史节点至少包含：

~~~text
快照：这一刻被记录的项目内容
父关系：它从哪个历史节点发展而来
身份：谁创建或记录了这次变化
意图：为什么做这次变化
验证：用什么检查它可以被使用
~~~

不同工具保存这些信息的方式不同。Git 把它们组合成 commit、tree、blob、ref 等对象和引用；后文会逐层展开。这里先建立验收标准：版本记录不只是文件副本，还要让后续的人能沿着历史重现判断。

## 版本控制和备份不是同一件事

备份关注数据丢失后的可恢复性，常见问题是“磁盘坏了还能找回吗”。版本控制关注变化的可追溯性，常见问题是“这次发布为什么包含这行代码，如何只撤销它”。

两者的职责有重叠，但不能互相替代：

| 能力 | 文件副本/备份 | 版本控制 |
| --- | --- | --- |
| 找回丢失的整份数据 | 主要能力 | 可以提供部分帮助 |
| 比较两个历史节点 | 手工或工具辅助 | 核心能力 |
| 记录父子关系 | 通常没有 | 核心能力 |
| 说明作者和变化意图 | 依赖命名或额外记录 | 可作为节点元数据 |
| 多人并行与合并 | 没有固定模型 | 核心能力 |
| 跨系统灾难恢复 | 适合做副本 | 需要结合备份和镜像 |

云盘历史版本也不等于代码版本控制。云盘通常围绕文件和保存时间组织历史，软件项目需要把接口、实现、测试、配置和迁移作为一组变化审查，并保留分支、合并和发布关系。

## 版本记录的质量取决于历史节点

版本越多不一定越安全。没有说明、无法比较、彼此关系不清的副本会增加判断成本。一个可审查的历史节点应满足：

- 可以用稳定名字或完整 ID 指向；
- 能看到与父节点相比的变化；
- 能知道它是否属于某条工作线；
- 能记录实际验证和已知限制；
- 需要撤销时有明确范围，而不是恢复整个目录。

这也是为什么“每天复制一次目录”在软件团队里很快失效：它保存了许多状态，却没有把状态之间的因果和责任固定下来。

## 从单个文件到一组变化

软件变化往往跨越多个文件。一次接口修改可能同时需要：

~~~text
API 定义
实现代码
单元测试
集成测试
配置或数据库迁移
文档和发布说明
~~~

如果只按文件分别复制，后来的人无法知道这些文件是否应该一起回退。版本控制把它们放进同一个提交或一组有顺序的提交，让评审、构建和恢复可以围绕一个明确候选进行。

提交不是越大越好。无关格式化、调试日志和另一个功能混在一起，会削弱审查和回退；过度拆分又会让中间节点无法解释。第二篇的提交章节和第六篇的可审查变更章节会把这个取舍分别落到本地历史与团队评审规则。

## 四个最小能力

一个能支撑软件协作的版本系统，至少要提供：

1. **记录**：把有意义的一组变化保存为历史节点；
2. **比较**：准确说明两个节点之间的文件和元数据差异；
3. **恢复**：按范围撤销、回到旧状态或找回误移动的历史入口；
4. **协作**：合并并行变化，暴露需要人工判断的冲突。

Git 还提供签名、对象校验、远程传输和自动化集成，但这些能力都建立在前四项之上。没有清楚的节点和父关系，后续的审计与发布也无法可靠绑定。

## 版本控制解决不了什么

版本控制不能自动证明：

- 代码逻辑是正确的；
- 测试覆盖了真实风险；
- 提交作者就是远程登录主体；
- 制品来自这个提交；
- 生产实例已经运行这个版本；
- 数据库和异步消息可以安全回退；
- 任何提交都没有敏感信息。

这些问题需要测试、身份、构建、部署、数据和安全系统的额外证据。Git 能让证据有一个稳定的源码坐标，但不能代替其他系统。

## 学完本书后应能回答的问题

面对一次变化，应该能够说清：

~~~text
变化发生在哪个工作区、index、提交或远程引用
它相对于哪个父节点发生
谁记录了对象，谁通过远程认证
候选是否经过评审和检查
制品和运行实例是否绑定同一对象
如果错误，按什么范围恢复
哪些外部状态无法由 Git 单独证明
~~~

这些问题会把本书从命令学习带到工程决策。后面的快照、对象、分支和远程章节，分别负责回答其中的一部分。

## 隔离实验验证了什么

本篇不把历史叙述伪装成可运行的 Git 输出。对象和提交行为在：

~~~bash
./scripts/verify-object-model.sh
~~~

中用临时仓库验证。实验能证明 Git 对象、tree、commit、tag 和 amend 的关系，不证明备份系统、平台评审、CI、制品、部署或组织责任。

## 小结

版本控制要解决的是变化无法识别、解释、比较和恢复的问题。备份保存副本，版本控制保存带父关系和意图的历史节点；四个最小能力是记录、比较、恢复和协作。Git 的价值不在于文件名更整齐，而在于让一次工程决定拥有可追溯的坐标。
