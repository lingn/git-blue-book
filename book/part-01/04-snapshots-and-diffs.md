# Git 保存的是快照：完整视图和差异显示是两件事

Git 的一次提交代表项目在某个历史节点上的完整快照。你在终端看到的补丁，只是 Git 比较两个快照后生成的视图，不是提交内部只保存了几行变化。

## 进入条件与完成标准

本章不要求预先理解 tree 和 blob 的物理格式，但要先接受一个工作模型：一个版本需要能够从一个入口还原整个被记录的项目视图。对象、路径、引用和 pack 的细节在第一篇的下一章和第三篇展开。

读完本章后，你应能：

- 区分快照模型、差异输出和物理存储；
- 解释未变化文件为什么可以复用对象；
- 说明文件名、目录、模式和空目录的边界；
- 判断提交、工作区和差异命令分别展示什么；
- 解释为什么大文件和生成物需要额外治理；
- 不把“diff 看起来很小”当作风险很小。

## 两种记录变化的模型

假设一个文件从版本 A 变成版本 B，版本系统可以保存：

~~~text
增量模型：
A + “把第二行替换为新内容” = B

快照模型：
A = 一份完整项目视图
B = 另一份完整项目视图
差异 = compare(A, B)
~~~

Git 的 commit 指向一份项目 tree，从 tree 可以递归找到被记录路径和文件内容。比较两个 commit 时，Git 再计算新增、删除、修改和重命名等显示结果。

快照模型的价值是每个历史节点都能独立作为一个状态入口。要查看旧版本，不必从最初版本按顺序应用全部补丁；只要找到对应 commit 和 tree 即可。对象物理存储仍会复用未变化内容和压缩相似内容，不影响这个逻辑模型。

## “完整”不是“复制全部字节”

连续提交可以这样表达：

~~~text
提交 A：README v1，app v1
提交 B：README v1，app v2
提交 C：README v2，app v2
~~~

B 的逻辑快照包含 README v1 和 app v2。Git 可以让 B 的 tree 继续指向 A 中的 README 内容，只为 app v2 使用新的 blob。C 再复用 app v2。

因此同时成立：

- 从任意提交出发，可以得到当时完整的被记录项目视图；
- 相同内容在对象库中可以复用，不必重复存储；
- packfile 和 delta 可以改变物理布局，不改变快照语义。

大文件仍可能让对象、网络和备份成本很高。快照模型不会自动让二进制便宜，LFS、制品库和容量治理需要单独设计。

## 快照包含哪些项目事实

Git tree 主要记录：

- 路径名；
- 文件内容对象；
- 文件模式和对象类型；
- 子目录的 tree；
- 子模块的 gitlink 对象 ID。

它通常不记录文件修改时间、所有 POSIX 权限位、进程状态、数据库内容、环境变量和空目录本身。文件模式、属性、换行和 filter 可能影响工作区与 index 的字节，但不会把操作系统的全部元数据纳入快照。

提交说明、作者、提交者、父提交和签名属于 commit 元数据，不是文件内容；它们同样是历史节点的一部分。

## 空目录为什么不会单独保存

Git 通过文件条目构造目录 tree，没有“空目录对象”。如果程序需要一个空目录，仓库通常放一个有意义的占位文件：

~~~text
runtime-data/
└── README.md
~~~

.gitkeep 只是社区习惯的文件名，不是 Git 特殊功能。占位文件会进入快照，删除它后空目录又不会被 Git 单独保留。

部署系统、容器镜像和构建脚本可能自行创建目录。它们的运行行为不应被误写成 Git 快照事实。

## 快照与差异命令

在已有提交的仓库中：

~~~bash
git show HEAD
git show HEAD:path/to/file
git diff HEAD^ HEAD
git diff HEAD^..HEAD
git diff --stat HEAD^ HEAD
~~~

show HEAD 展开当前提交的元数据和相对父提交的差异；show commit:path 读取某个快照中的路径；diff 比较两个树并生成差异。命令输出受路径、属性、外部 diff、重命名阈值和 Git 版本影响。

工作区差异还需要 index 作为边界：

~~~bash
git diff
git diff --staged
git diff HEAD
~~~

这些命令分别比较工作区/index、index/HEAD 和工作区/HEAD。未跟踪文件没有 index 基线，普通 diff 不会显示它的完整内容。

## 重命名是比较结果，不是快照字段

快照中可能只有：

~~~text
旧 tree：docs/guide.md -> blob X
新 tree：manual/guide.md -> blob X
~~~

Git 在 diff 或 merge 时根据删除、添加和内容相似度推断 rename。提交对象没有一条必须保存的“rename 操作记录”。不同阈值和选项可能把同一组快照显示成 rename，或显示成 delete/add。

这不影响文件最终路径和内容的快照事实，却影响历史归因、冲突处理和审查报告。需要确定性时保存旧 tree、新 tree、路径和相似度配置。

## 快照不等于可发布制品

源代码快照只表示 Git 中被记录的文件和元数据。构建还可能读取：

- 依赖锁文件和外部包；
- 编译器、操作系统和环境变量；
- 未跟踪或生成文件；
- LFS payload、子模块仓库；
- 时间、随机数和网络服务；
- 数据库 schema、配置和密钥。

因此“提交快照固定”不等于“制品字节和运行实例固定”。第八篇会把 commit、构建清单、制品摘要和部署实例串成证据链。

## 快照的恢复价值和限制

只要 commit、tree 和 blob 仍由 refs、reflog、bundle 或其他对象入口找到，就可以读取旧快照：

~~~bash
git show <commit>:path/to/file
git archive --format=tar <commit> path/to/file
git ls-tree -r <commit>
~~~

如果路径从未进入任何提交，Git 没有它的快照。若对象已经不可达并被维护清理，本地也可能无法恢复。远端、备份、LFS 服务和其他 clone 需要单独核对。

事故时不要先运行 gc 或 prune。先固定 refs、对象 ID 和快照来源，再决定恢复或清理。

## 隔离实验验证了什么

运行：

~~~bash
./scripts/verify-object-model.sh
~~~

实验用真实 Git 对象验证相同 blob 复用、tree、commit、tag、改写提交和 repack 后的对象关系。它不证明文件系统快照、备份、制品、LFS、数据库或部署状态。

## 小结

Git 用快照作为历史节点的逻辑模型，用差异命令展示节点之间的变化，用对象复用和 pack 优化物理存储。快照记录路径、内容、模式和提交关系，不记录空目录、数据库或运行状态。理解这三层，才能在后面区分“文件变化”“对象变化”“制品变化”和“线上变化”。
