# 发现并创建仓库：`git rev-parse` 与 `git init`

初始化仓库之前，先回答两个问题：终端当前位于哪个目录，Git 会把哪个目录当作仓库根目录。很多“文件怎么没被加入”“命令为什么改了另一个项目”的事故，起点不是 `git init`，而是执行位置没有被核对。

本章只讨论本地仓库的发现和初始化。远程地址、认证、克隆和裸仓库服务端模型在第四篇处理。

## 进入条件与完成标准

准备一个没有重要文件的新练习目录。不要在真实项目的父目录、用户主目录或包含多个项目的工作目录直接运行初始化命令。读完本章后，你应能：

- 用 `pwd` 和 `git rev-parse` 证明当前执行位置；
- 区分“当前目录不是仓库”“当前目录位于某个仓库内”和“目录里有嵌套仓库”；
- 用 `git init` 创建普通工作区仓库，并指定初始分支名；
- 解释初始化不会创建提交、不会跟踪文件、不会连接远程；
- 识别重复初始化、误目录初始化、裸仓库和 `--separate-git-dir` 的边界；
- 在发现执行位置不对时停止并恢复，而不是删除不明的 `.git`。

## 先确认执行位置

在准备好的空目录中执行下面的命令。`pwd` 是操作系统的目录命令，`git rev-parse` 是 Git 的只读查询命令。

```bash
pwd
git rev-parse --show-toplevel
```

在尚未初始化的目录中，第二条命令应以非零状态失败，并报告当前目录不是 Git 仓库。这个失败是有用的边界证据：它说明 Git 尚未从当前目录或父目录发现仓库，不代表 Git 程序损坏。

若当前目录已经位于某个仓库内，`--show-toplevel` 会输出仓库根目录的绝对路径。此时不要为了“让命令成功”再次执行 `git init`。先用 `pwd` 和输出路径判断自己是否进入了预期项目。

一个安全的检查顺序是：

```bash
pwd
git rev-parse --show-toplevel 2>/dev/null || true
```

`|| true` 只适合诊断脚本，不能把失败吞掉后继续执行有副作用的命令。交互操作中应保留原始错误，以便确认“未初始化”还是“路径/权限问题”。

## 初始化普通工作区仓库

确认目录为空或其中只有明确要保留的练习文件后，在该目录执行：

```bash
git init --initial-branch=main
```

预期输出会包含新建仓库的路径，类似：

```text
Initialized empty Git repository in .../git-first-lab/.git/
```

输出中的省略路径会因系统、符号链接和 Git 版本不同而变化。不要把示例中的绝对路径复制到后续命令。

初始化做了三件事：创建 Git 数据目录，写入仓库级配置的基础结构，并让 `HEAD` 具备指向初始分支名的准备状态。它没有写入任何 commit，也没有把工作区文件加入 index。

初始化没有做的事同样重要：

- 不会自动跟踪目录中的文件；
- 不会创建 `main` 分支所指向的提交；
- 不会访问 GitHub、GitLab 或其他远程平台；
- 不会上传文件，也不会替你配置认证；
- 不会为 `.gitignore`、hooks 或 CI 生成团队策略。

因此，创建仓库是本地数据面动作，不需要远程账号。是否允许把后续对象发布到某个远程，是另一条认证和授权链。

## 再次检查 Git 看到的仓库

初始化成功后，在同一目录执行：

```bash
git rev-parse --show-toplevel
git rev-parse --git-dir
git rev-parse --is-inside-work-tree
git symbolic-ref --short HEAD
git status --short --branch
```

普通工作区仓库应满足以下不变量：

| 观察 | 预期 | 说明 |
| --- | --- | --- |
| `--show-toplevel` | 当前练习目录 | 工作区根目录，不是 `.git` 目录 |
| `--git-dir` | 练习目录下的 `.git` 或其实际路径 | Git 数据目录可能通过其他方式放置 |
| `--is-inside-work-tree` | `true` | 这是有工作区的仓库 |
| `symbolic-ref --short HEAD` | `main` | 初始分支名已写入 `HEAD`，但还没有提交 |
| `status --short --branch` | 分支存在、尚无提交、无已跟踪变化 | 输出文字随 Git 版本变化 |

如果 `symbolic-ref` 失败，可能是当前 Git 版本或初始化方式没有设置符号引用。保留 `git status --branch` 的完整输出，并确认没有把命令执行在 `.git` 内部。不要因为分支名显示不同就删除仓库；分支名可以通过配置或后续引用操作调整。

## Git 如何发现父目录仓库

Git 命令通常从当前目录向上查找仓库数据目录。因此，在仓库的子目录执行：

```bash
mkdir -p docs/examples
cd docs/examples
git rev-parse --show-toplevel
```

输出仍然是仓库根目录。回到根目录：

```bash
cd "$(git rev-parse --show-toplevel)"
```

这条命令只在前一条查询已成功时使用。路径含空格时，命令替换和引号可以避免 shell 把路径拆成多个参数；如果你不确定当前是否在仓库中，先手动记录 `pwd`，不要直接把可能为空的命令替换交给 `cd`。

### 嵌套仓库不是普通子目录

如果在已存在的仓库内部再次执行 `git init`，Git 可能在子目录创建嵌套仓库。外层仓库会把这个路径视为普通目录、未跟踪路径或 gitlink 候选，具体取决于后续操作。嵌套仓库不是“让外层自动管理两份历史”的开关。

发现误初始化后，先保存以下信息：

```bash
pwd
git -C path/to/suspect rev-parse --show-toplevel
git -C path/to/suspect rev-parse --git-dir
```

只有在确认该目录没有需要保留的历史、配置或未分享对象后，才可以按团队的文件处置流程移除误建的数据目录。路径不明确时，不运行递归删除；真实项目中删除 `.git` 可能让本地未分享提交、reflog 和配置失去恢复入口。

## 选择初始分支名的边界

`--initial-branch=main` 只影响初始化时的名称。也可以通过 `init.defaultBranch` 设置默认值：

```bash
git config --global init.defaultBranch main
```

全局配置会影响当前用户以后创建的仓库，属于持久化修改。执行前先用上一章的配置来源命令确认目标作用域，组织管理的设备不要擅自覆盖系统策略。已经初始化的仓库不会因为修改这个全局值而自动重命名现有引用。

不同团队可能使用 `main`、`trunk` 或其他名称。名称本身不决定合并策略、保护规则或远程默认分支；这些是托管平台控制面和团队流程的独立事实。

## 普通仓库、裸仓库和分离 Git 目录

本书第一次提交练习使用普通仓库，因为它同时包含工作区和 `.git` 数据目录。另有三种容易混淆的形式：

| 形式 | 初始化方式 | 是否有工作区 | 适用场景 |
| --- | --- | --- | --- |
| 普通仓库 | `git init` | 有 | 本地开发和练习 |
| 裸仓库 | `git init --bare` | 没有 | 远程接收端、镜像和备份目标 |
| 分离 Git 目录 | `git init --separate-git-dir=...` | 有 | 工作区与 Git 数据需要分开存放 |

不要把裸仓库目录当作可以直接编辑的项目目录，也不要在没有备份和所有权说明时移动分离的 Git 数据目录。远程服务是否允许直接使用裸仓库，还涉及 receive-pack、认证、授权和并发控制，不能由 `git init --bare` 一条命令证明。

## 初始化失败时怎么处理

| 现象 | 先收集的证据 | 可能原因 | 恢复边界 |
| --- | --- | --- | --- |
| `not a git repository` | `pwd`、`ls -la`、`git rev-parse --show-toplevel` | 尚未初始化或在错误目录 | 回到预期练习目录后再初始化 |
| `cannot mkdir .git` | 目录权限、挂载状态、父目录所有权 | 当前目录不可写 | 换到可写的专用目录，不修改系统权限作为第一反应 |
| 已有 `.git` 的提示 | `git rev-parse --git-dir`、`git status` | 重复初始化或误入现有仓库 | 先确认历史，再决定继续使用或新建目录 |
| `detected dubious ownership` | 仓库路径、文件所有权、`safe.directory` 来源 | Git 的目录所有权保护 | 由仓库所有者或管理员确认后按范围配置，不用通配符绕过保护 |

失败时不要删除 `.git`、不要在父目录执行 `git init`，也不要把失败信息替换成“命令成功但没有输出”。恢复动作的第一目标是保留现有对象和引用。

## 隔离实验验证了什么

本章与第二篇共享实验：

```bash
./scripts/verify-part-2.sh
```

脚本在临时目录中验证：初始化前仓库发现失败，初始化后根目录、Git 数据目录、工作区标志和初始分支一致；之后的提交和状态矩阵也都在同一临时仓库完成。实验使用虚构身份，不读取本机全局配置，不连接网络，退出时删除临时目录。

实验能证明 Git 本地发现和初始化的状态变化，不能证明文件系统权限、网络文件系统租约、托管平台创建仓库、默认分支控制面或真实认证。那些结论需要目标环境的专项验收。

## 小结

`git init` 只是为本地历史准备容器。先用路径和仓库发现命令证明执行位置，再初始化；初始化后用 `rev-parse`、`symbolic-ref` 和 `status` 验证不变量。仓库发现、工作区、裸仓库和远程服务是不同边界，不能靠“命令没有报错”把它们混为一谈。
