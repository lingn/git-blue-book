# 分支模型先说明状态，不先规定名字

团队讨论“采用哪种分支模型”时，经常先争论分支名和生命周期。真正影响风险的是每条分支承载什么状态、允许谁更新、与发布和修复怎样关联。两个团队都使用 `main`、`feature/*` 和 `release/*`，如果一个团队从主线持续发布，另一个团队长期维护多个发布线，它们面对的合并、回补和恢复问题并不相同。

## 进入条件与完成标准

本章假设读者已经理解分支是可移动引用，能使用 `merge-base`、`log` 和祖先关系判断提交图。示例命令在已有 `origin`、当前位于仓库根目录的开发者 clone 中执行，只读取本地 refs，除 `git fetch` 外不改变状态。

开始前记录：

~~~bash
git status --short --branch
git remote -v
git branch --show-current
git for-each-ref --format='%(refname) %(objectname)' refs/heads refs/remotes/origin
~~~

`git fetch --prune origin` 会下载对象，并更新或删除 `refs/remotes/origin/*` 中的本地缓存。工作区和当前本地分支不会因此自动合并。仓库有未提交修改时也能 fetch，但后续切换或整合可能被这些修改阻止。

读完本章后，应能从状态、更新者、发布关系和维护窗口选择分支策略，并为功能分支、发布分支和维护分支分别写出创建、整合、删除和恢复条件。

## 先定义四类状态

主线通常表示团队当前整合结果。它是否始终可发布，要由团队明确，不能从 `main` 这个名字推断。功能分支承载尚未进入主线的候选变化，允许改写到什么程度取决于是否已有评审、CI 或其他分支依赖它。发布分支用于冻结或稳定一个发布线，维护分支则服务于仍在支持的旧版本。发布分支和维护分支有时是同一条引用，也可能完全不需要。

每类分支至少写清六个字段：

| 字段 | 要回答的问题 |
| --- | --- |
| 状态含义 | 这条分支表示开发中、已整合、候选发布还是已发布维护线 |
| 创建来源 | 从哪个完整 OID 或不可变发布点创建 |
| 允许更新者 | 开发者、合并服务、发布机器人或紧急身份中的哪些主体 |
| 允许的历史形状 | 是否只能快进，是否允许 merge commit，是否允许受控改写 |
| 退出条件 | 何时合入、关闭、归档或删除 |
| 恢复来源 | 误删、错误合并或错误强推后从哪里找回 |

分支名只是这些字段的入口。平台保护规则、CI 触发器和发布脚本如果只匹配名字，却没有稳定的状态定义，改名或新增维护线时很容易出现空保护和漏跑。

## 四种常见组织方式

### 主干开发

主线更新频繁，功能分支较短，未完成能力通过兼容设计、特性开关或小步提交隔离。它减少长期分叉，却要求主线检查足够快、集成失败能快速回退，数据库和消息变更也要支持混合版本。

需要观察的不只是功能分支存在几天，还包括候选等待时间、目标分支前进速度、队列重建次数和主线恢复时间。把一个长期项目拆成许多短分支，如果每次都依赖同一组未合入前置提交，实际分叉并没有消失。

### 功能分支工作流

每项变化在独立分支上完成评审，再整合到主线。这个名字覆盖的范围很宽：分支可以由一人维护，也可以被多人和自动化共同使用；可以允许 rebase，也可以把推送后的 OID 当作稳定坐标。

共享前要决定两件事。其一，功能分支是否允许改写；其二，后续分支能否以它为父。允许堆叠评审时，父分支一旦 rebase，所有后继候选、审批和检查都要重新绑定。

### 发布分支

发布分支从已知候选创建，用于稳定特定版本。它适合需要冻结窗口、并行准备下一个版本或保留多条支持线的产品。代价是同一修复可能要进入多个分支，并分别生成提交、制品和部署证据。

修复不能只记录“已 cherry-pick”。至少保存缺陷来源提交、每个目标分支的 picked OID、冲突处理、构建制品和实际发布范围。后续主线已经包含等价变化时，也要确认维护分支上的实现没有遗漏依赖。

### 长期维护分支

维护分支代表仍受支持的旧版本，通常只接受安全修复和高优先级缺陷。它需要明确支持截止时间、允许的变化类型、测试环境和发布权限。旧分支缺少当前 CI、依赖服务或构建工具时，不能因为 cherry-pick 成功就判定修复可发布。

## 用提交图核对声明

假设团队声明 `release/2.x` 从已发布标签 `v2.4.0` 维护，当前主线是 `origin/main`。在开发者 clone 中执行：

~~~bash
git fetch --prune origin
release_tip="$(git rev-parse --verify origin/release/2.x^{commit})"
main_tip="$(git rev-parse --verify origin/main^{commit})"
release_base="$(git merge-base "$release_tip" "$main_tip")"

printf 'release=%s\nmain=%s\nmerge-base=%s\n' \
  "$release_tip" "$main_tip" "$release_base"
git log --left-right --cherry-pick --oneline \
  "$release_tip"..."$main_tip"
~~~

这里的输出字段都是本地 fetch 后的观察值。`--left-right` 用 `<` 和 `>` 标出只从一侧可达的提交，`--cherry-pick` 会省略能识别为补丁等价的成对提交。它有助于找线索，不证明两个分支的运行行为相同，也不能替代发布和数据库证据。

命令失败时先按错误分流：引用不存在，检查远端是否发布了该分支以及 fetch refspec 是否包含它；对象缺失，检查浅克隆或部分克隆边界；工作区不是问题，因为这些命令不切换分支。不要为了让命令成功而直接创建同名本地分支，这会把“服务器没有观察到该 ref”和“本地自己造了一个名字”混在一起。

## 分支策略的决策矩阵

| 约束 | 更适合的组织方式 | 需要补的控制 |
| --- | --- | --- |
| 主线每天多次发布，变化可小步兼容 | 短功能分支或主干开发 | 快速检查、特性隔离、自动回退和数据库兼容 |
| 固定周期发布，冻结后还要继续开发 | 发布分支 | 修复回补、候选冻结、制品提升和截止规则 |
| 同时支持多个客户版本 | 长期维护分支 | 支持矩阵、目标分支测试、依赖归档和退役流程 |
| 大型变化必须分批评审 | 堆叠功能分支 | 父子候选映射、重建顺序和审批失效规则 |
| 合规要求主线只由服务身份更新 | 任一模型均可 | 合并服务、受保护引用、独立审批和审计事件 |

分支策略不能单独解决发布风险。主线稳定、候选可评审、制品可追踪和运行可恢复分别需要评审、CI/CD 与运维证据。

## 创建、整合和删除都有前置条件

创建功能分支前固定目标基线；开始评审前固定功能头和共同祖先；整合时固定目标 old OID、候选 OID 和合并策略；删除分支前确认最终主线对象、未合入变化和恢复引用。平台可能在合并后自动删除源分支，但本地 clone、其他远程和评审记录仍可能引用旧对象。

删除本地分支前可以检查：

~~~bash
branch="feature/payment-retry"
tip="$(git rev-parse --verify "refs/heads/$branch^{commit}")"
git branch --contains "$tip"
git for-each-ref --contains="$tip" --format='%(refname)' refs/heads refs/remotes
git log --left-right --cherry-mark --oneline origin/main..."$tip"
printf 'candidate=%s\n' "$tip"
~~~

前两条命令只列出本地哪些可见引用包含该 OID，第三条用 `=`、`<` 和 `>` 辅助识别补丁等价和两侧独有提交。它们都不是通用的“是否已合并”判定，输出还受 fetch 时点和可见 refs 影响。可靠做法是先保存完整 OID，再按团队采用的 merge、squash 或 rebase merge 方式验证最终结果。Merge 可以检查祖先关系；squash 和 rebase merge 还要结合评审记录、补丁映射和最终 tree。

误删分支时不要立即运行清理。先用保存的 OID、reflog、评审平台和同事 clone 建立 `refs/recovery/*`，再恢复工作分支。恢复步骤见[reflog](../part-5/11-reflog.md)和[综合恢复案例](../part-5/12-recovery-cases.md)。

## 失败方式和恢复边界

| 现象 | 先固定的证据 | 安全动作 |
| --- | --- | --- |
| 发布分支找不到某个修复 | 来源 OID、目标 OID、patch-id、评审和发布记录 | 判断未迁移、补丁等价或被后续提交覆盖，再决定 cherry-pick 或重新实现 |
| 功能分支长期无法合入 | base/head、依赖分支、冲突、检查等待时间 | 缩小变更或明确堆叠关系，不用无条件强推刷新表面状态 |
| 自动删除后找不到源分支 | 最终主线、评审候选、远端事件、reflog | 先建恢复 ref；squash/rebase 场景不要只查祖先 |
| 旧维护线构建失败 | 目标分支 OID、工具链、依赖和历史 CI | 恢复可复现环境或停止支持，不把主线绿色结果转借给旧分支 |
| 分支规则漏掉新命名 | 规则 scope、真实 refs、审计和行为探针 | 恢复保护范围，检查漏保护窗口中的所有更新 |

## 小结

分支模型是一份状态与责任契约。主线、功能分支、发布分支和维护分支分别写清来源、更新者、历史形状、退出条件和恢复来源后，命名才有稳定含义。团队可以选择不同的图形，但不能省略候选绑定、共享边界、发布证据和恢复责任。
