# 评审请求是一台会反复失效和重算的状态机

评审页面上的“已批准”“检查通过”和“可以合并”都是某个时刻的判断。功能分支新增提交、目标分支前进、所有权规则变化或检查重新运行后，先前结论可能不再适用。把评审请求理解为静态讨论页，很容易把旧审批和旧绿色结果带到新候选上。

## 进入条件与完成标准

本章使用厂商无关模型，不描述某个平台的按钮。开始前应能区分功能头、目标头、共同祖先和候选提交，并理解远程跟踪引用只是本地缓存。

本地取证命令在开发者 clone 的仓库根目录执行：

~~~bash
git status --short --branch
git fetch origin
feature="$(git rev-parse --verify HEAD^{commit})"
target="$(git rev-parse --verify origin/main^{commit})"
base="$(git merge-base "$target" "$feature")"
printf 'feature=%s\ntarget=%s\nbase=%s\n' "$feature" "$target" "$base"
~~~

这组命令会更新本地远程跟踪引用和对象库，不会创建评审请求，也不会读取平台审批、CI 或规则状态。工作区有改动时仍可执行，但这些改动不在 `feature` OID 中。

读完本章后，应能为评审请求定义状态、事件和失效条件，并从本地 Git 证据、平台事件和 CI 记录中还原一次合并决定。

## 评审请求的稳定身份和可变版本

评审编号或 URL 是讨论对象的稳定入口，不是代码版本。一次评审至少同时包含：

| 字段 | 含义 | 为什么不能省略 |
| --- | --- | --- |
| 仓库稳定 ID | 评审属于哪个仓库资产 | 仓库改名或转移后仍要关联 |
| 评审稳定 ID | 讨论、审批和审计的容器 | 标题与分支名都可变化 |
| 功能头 OID | 发起者当前提出的提交 | 新推送会让旧审批和结果可能过期 |
| 目标 ref 与目标 OID | 计划更新的引用及当时基线 | 目标前进会改变组合结果 |
| 候选 OID 或 tree | 实际接受检查的对象 | 功能头不一定就是合并候选 |
| 候选构造方式 | feature、merge、squash、rebase 或 queue | 决定对象身份和父关系 |
| 策略版本 | 当时使用的审批、检查和保护规则 | 规则改变后结论可能不同 |

平台如果只提供部分字段，团队需要从事件 API、CI 记录或自建证据清单补齐。用“评审 #42 已通过”作发布依据时，至少要附上当时的候选 OID 和策略版本。

## 状态由事件推进

可以把评审请求建模为以下状态：草稿、待评审、待修改、待检查、可合并、排队中、已合并、已关闭。状态名可以不同，关键是每次变化都由可追踪事件触发。

常见事件包括：创建评审、发布新功能头、目标分支前进、添加或撤销审批、代码所有者变化、检查开始或结束、候选重建、进入或离开队列、引用条件更新成功或失败、管理员绕过、关闭和重新打开。

状态转换记录至少保存：

~~~text
review_id: <稳定 ID>
event_id: <平台事件 ID>
observed_at: <采集时间>
actor: <平台主体及委托链>
old_feature_oid: <可为空>
new_feature_oid: <可为空>
target_oid: <当时目标>
candidate_oid: <当时候选>
policy_version: <规则版本或摘要>
decision: <状态变化>
reason: <审批、检查、冲突、过期或绕过>
~~~

平台显示的更新时间不能替代事件时间，也不能证明所有事件都被完整导出。审计和灾难恢复需要另外验证游标、分页、事件覆盖和时钟边界，详见[审计日志与证据留存](../part-12/04-audit-logs-and-evidence-retention.md)。

## 哪些变化会使旧结论失效

### 功能头变化

新提交改变了评审对象。即使只修改提交说明，OID 也会变化；如果平台按 OID 绑定审批，旧审批应过期。如果平台允许保留部分审批，需要明确哪些角色、路径或风险维度仍然有效，不能默认“差异很小”。

### 目标基线变化

功能头不变，目标分支前进后，临时合并候选和冲突结果可能变化。只验证功能头无法覆盖最新组合。合并队列会为当前顺序重建候选，入队前绿色结果不能自动转给新候选。

### 策略和所有权变化

必需检查改名、所有者文件变更、审批人数调整或例外到期后，旧的“可合并”结论要重新求值。候选仓库中的策略变化不能自行放宽同一候选的门禁，组织级信任边界应在候选之外。

### 外部证据变化

密钥撤销、测试结果被判定不可靠、制品被隔离或依赖来源失效时，代码对象没变，决策仍可能失效。评审系统需要保留失效原因，而不是简单覆盖旧状态。

## 草稿和待评审不是权限边界

草稿能告诉团队“当前还不请求最终决定”，但它通常不会阻止分支被其他人读取、CI 执行代码或自动化处理事件。敏感凭据、未获授权的数据和危险流水线不能依赖草稿状态保护。

进入正式评审前固定：

~~~bash
git status --short --branch --untracked-files=all
git diff --name-status "$base"..."$feature"
git log --format='%H%x09%P%x09%s' "$base".."$feature"
git diff --check "$base"..."$feature"
~~~

这里 `base`、`feature` 来自前面的完整 OID。若命令输出与平台 diff 不同，先核对平台候选类型、目标 OID、浅克隆边界和路径过滤，不要凭截图修改本地历史来“对齐”。

## 评审决定必须绑定对象和范围

一条审批至少说明审批者、角色、候选 OID、目标 OID、评审范围、时间和决定。代码所有者批准某个目录，不自动代表安全、数据库或发布负责人批准其他风险。一个人可以同时拥有多个角色，但审计记录要保留是以哪个职责作出决定。

评审意见可以分为阻断、非阻断和信息性建议。平台是否原生支持这些类别并不重要，团队规则必须能确定：未解决意见是否阻止合并，谁能标记已解决，新候选出现后是否重新打开，以及机器人生成的建议是否算审批。

## 合并是条件更新，不是页面动作

真正完成评审的是目标引用从预期 old OID 更新到最终 new OID。合并动作执行前应重新核对：

~~~text
target_ref: refs/heads/main
expected_old: <评审或队列生成候选时的目标 OID>
candidate: <已通过检查与审批的候选 OID>
merge_method: <merge/squash/rebase/fast-forward>
policy_version: <实际求值版本>
final_new: <计划写入目标引用的 OID>
~~~

如果目标引用已不等于 `expected_old`，旧候选应过期并重新生成，不能用强制更新跳过竞态。Git 能提供原子引用更新机制，平台还要把审批、检查和身份决定绑定到同一次条件更新。

## 常见故障与恢复

| 症状 | 先固定 | 安全动作 |
| --- | --- | --- |
| 页面显示已批准，但最新提交没人看过 | 审批 OID、当前功能头、审批保留规则 | 使旧审批过期，针对新候选重审 |
| 功能头绿色，评审仍不可合并 | 目标 OID、候选类型、必需检查、冲突状态 | 找缺失状态，不要反复重跑无关检查 |
| 评审显示可合并，引用更新却失败 | expected-old、服务器当前目标、队列位置 | 让候选过期并从新基线重建 |
| 关闭后重新打开，旧检查仍显示绿色 | old/new 功能头、attempt、结果绑定 | 只接受属于当前候选和当前策略的结果 |
| 管理员绕过后看不到原因 | actor、规则、old/new OID、事故与批准记录 | 冻结证据、补记真实时序并回收权限，不能伪造事前审批 |
| 平台事件缺页或乱序 | cursor、sequence、采集时间和原始响应 | 标记证据不完整，补采或升级调查，不能据此作确定归因 |

本地 `git log` 能还原最终提交图，不能还原谁在什么时间看过哪一版代码。平台数据缺失时，应把结论写成“Git 历史可确认，评审过程证据不完整”，不要从 author、committer 或签名猜审批事实。

## 小结

评审请求的稳定身份负责聚合讨论，可变的功能头、目标基线、候选、审批、检查和策略版本共同决定某一刻能否合并。任何一层变化都要按明确规则使旧结论过期。最终合并以目标引用的条件更新为完成点，页面状态只是这次决定的输入和观察结果。
