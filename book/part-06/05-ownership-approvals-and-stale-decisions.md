# 所有权和审批：谁有上下文，谁能作出决定

审批数量只说明有多少个主体点击了同意，不能说明这些人是否覆盖代码、数据、安全和运行风险。所有权规则的作用，是把变化路径和工程责任关联起来；最终决定仍要看候选版本、角色独立性、评审范围和组织授权。

## 进入条件与完成标准

本章不假定某个平台原生支持哪种所有者文件或审批规则。不同产品的匹配语义、继承、权限和套餐可能不同，落地前要按核对日期记录实际行为。

开始设计规则前，需要有仓库稳定 ID、默认分支、目录责任、服务运行 owner 和紧急联系人。只有一份路径文件，没有组织成员来源和替补机制，不能形成可用所有权。

读完本章后，应能区分代码所有者、风险审批者、合并者和规则管理员，设计候选绑定与审批失效条件，并识别自审批、影子所有权和长期无人维护等故障。

## 四种职责不要合并成一个“owner”

| 职责 | 主要问题 | 不自动拥有的权力 |
| --- | --- | --- |
| 代码所有者 | 是否理解路径实现和接口影响 | 批准安全例外、发布生产或修改规则 |
| 风险审批者 | 安全、隐私、数据、合规或架构风险是否可接受 | 代替代码细节评审 |
| 合并者 | 当前候选是否满足全部门禁，能否更新目标引用 | 改变审批内容或借用他人决定 |
| 规则管理员 | 所有权和审批策略是否正确部署 | 日常绕过同一规则 |

小团队里一个人可能承担多个职责，但系统要保留角色。作者以代码所有者身份看过实现，不等于以安全审批者身份接受了凭据范围扩大。

## 路径匹配只是候选所有者集合

所有者文件通常按路径模式把变更映射到个人或团队。真正的有效审批还要经过：

1. 候选包含哪些路径，重命名前后怎样归属；
2. 匹配规则来自哪个受信任版本；
3. 所有者组在评审时有哪些有效成员；
4. 审批者是否独立于作者和自动化主体；
5. 该审批是否绑定当前候选 OID；
6. 目标基线或风险范围变化后是否需要重审。

候选自己修改所有者文件时，不能用修改后的规则批准同一个候选。安全做法是从目标基线或组织外部策略读取所有权，再把规则变化作为独立受控变更处理。

## 所有权来源要覆盖代码之外的责任

目录结构不总与运行责任一致。共享库、数据库 schema、基础设施模板和 CI 配置可能影响许多服务。单纯按文件路径选择评审者，会漏掉反向依赖和运行 owner。

可以把评审者集合写成几类输入的并集，再由门禁决定必需角色：

~~~text
path owners
+ build graph affected owners
+ runtime/service owners
+ risk-specific approvers
+ migration or release owners
~~~

构建图缺边或服务登记过期时，结果应标记为证据不足，不能把空集合当作无需审批。Monorepo 的变更闭包和所有权边界见[拓扑治理](../part-09/05-monorepo-topology-and-ownership.md)。

## 审批必须带版本和范围

一条可审计审批至少包含：

~~~text
review_id: <稳定 ID>
candidate_oid: <完整 OID>
target_oid: <当时目标基线>
principal: <平台主体>
role: <code/security/data/release/...>
scope: <路径、组件或风险维度>
decision: <approve/request-changes/comment>
decided_at: <事件时间>
policy_version: <规则版本或摘要>
~~~

显示名和邮箱不够稳定，主体还要能关联组织身份、团队成员来源和委托链。机器人评论、测试状态和人类审批是不同事件，不能因为显示在同一时间线上就混为一类。

## 哪些情况应使审批过期

功能头变化通常使审批过期。团队可以按风险允许文档、测试或自动生成文件变化保留部分审批，但规则必须确定性地识别范围，并对未知路径采取明确处理。仅凭“平台判断改动很小”保留审批，审计时无法重放。

目标基线前进后，代码细节审批可能仍适用于功能差异，集成和发布审批却可能需要重算。所有者成员变化、密钥撤销、规则版本变化或发现旧审批者无权决定时，也要撤销有效性，同时保留原始事件。

“撤销审批”不是删除历史。系统应记录原决定、失效事件、原因和后续重审。

## 独立性不是人数问题

要求两次审批，如果两次都由作者控制的机器人、同一共享账号或同一委托会话产生，不能形成独立判断。有效独立性至少检查：

- 主体不是作者本人或作者可直接控制的凭据；
- 评审者在决定时拥有对应角色；
- 评审者看到的是当前候选和完整风险范围；
- 规则管理员不能日常批准自己的放宽；
- 紧急例外由独立批准人授权并有到期时间。

组织不必追求绝对职责分离，但高风险引用、发布和权限策略需要明确哪些组合禁止由一人完成。

## 所有者缺席时要有替补路径

只有一个个人账号的所有权规则会在休假、离职或事件期间阻断仓库。替补机制应使用团队或轮值角色，并规定升级时间。长期用管理员绕过代替替补，会让路径所有权失去作用。

定期对账至少检查：所有者模式是否仍命中真实路径，团队是否还有有效成员，成员是否仍承担运行责任，新组件是否未登记，已删除目录是否留下宽匹配，以及外部协作者是否被错误纳入批准组。

## 失败方式与恢复

| 症状 | 常见原因 | 安全动作 |
| --- | --- | --- |
| 所有者规则显示通过，但没人看关键目录 | 路径模式、重命名或生成路径漏匹配 | 使决定过期，修正规则并重审受影响候选 |
| 新增提交后审批仍有效 | 平台保留策略过宽或候选绑定缺失 | 固定旧新 OID，按角色和范围重新求值 |
| 规则匹配到空团队 | 身份同步、团队退役或仓库转移 | 阻断高风险更新，恢复替补 owner，不给全员管理员 |
| 作者通过机器人自批 | 机器人凭据和委托主体未关联 | 撤销结果，修复主体模型并审计历史使用 |
| 所有者文件放宽自身门禁 | 从候选版本读取策略 | 改从目标基线或外部可信策略读取，复查放宽窗口 |
| 两个 owner 给出冲突决定 | 角色、范围或规则组合未定义 | 按预先定义的 deny/升级语义处理，不用最后点击者覆盖 |

真实平台对这些场景的事件字段和失效行为可能不同。验收时需要在专用测试仓库中以普通贡献者、所有者、规则管理员和紧急身份分别操作，并保存原始平台输出。本地 Git 实验只能验证路径和对象变化，不能证明平台审批。

## 用候选之外的快照重放审批求值

所有权文件如果和业务代码放在同一个候选里，候选就可能同时修改“谁必须审批”和“我已经获得审批”的解释。一个可重放的求值过程至少把下面三类输入分开保存：

```text
trusted_ownership_snapshot: 目标基线或组织控制面发布的路径、角色和主体
candidate_commit: 本次评审实际验证的完整 OID
approval_events: candidate OID、角色、主体、决定和 policy version
```

候选中新增或修改所有权文件可以成为待评审内容，但不能立即改变同一候选的有效审批集合。需要改变所有权时，先按规则审批并发布新的信任快照，再让后续候选引用新版本。快照缺失、路径没有 owner 或身份目录无法确认时，结果应是 `inconclusive`，不能把空集合解释为“无需审批”。

### 隔离实验的前置条件和状态变化

实验从仓库根目录执行，只需要 Git、Bash、`mktemp` 和 `awk`，不连接网络、不读取当前仓库的远端，也不修改当前工作区：

```bash
git --version
TMPDIR=/private/tmp bash scripts/verify-ownership-approval-boundaries.sh
```

成功输出为：

```text
Ownership snapshot, independent approvals, candidate binding, stale decisions, and owner outage boundaries passed.
```

脚本在临时仓库中先创建基线 `T0` 和外部的 trusted ownership snapshot，再生成候选 `F1`、`F2`。`F2` 同时修改安全策略和候选内的所有权文件，试图把安全审批人替换成作者；求值器仍从临时目录中的可信快照读取 owner。状态变化和验收点如下：

| 场景 | 预期结果 | 说明 |
| --- | --- | --- |
| `F1` 只有作者对 `code` 角色的审批 | `deny/self-approval` | 人数为一不代表主体独立 |
| `F1` 有 `payments-owner` 对当前 OID 的审批 | `allow` | 角色、主体、候选和策略版本均匹配 |
| `F2` 仍沿用 `F1` 的 `code` 审批 | `deny/missing-owner-approval` | 新候选不能复用旧 OID 的决定 |
| `F2` 修改候选内所有权文件，但没有可信 `security-owner` 审批 | `deny` | 候选不能自授权或删除外部 owner |
| 目标从 `T0` 前进后仍使用 `F2` | `deny/candidate-stale` | 目标基线变化使组合结果需要重算 |
| trusted snapshot 不再为安全路径匹配 owner | `inconclusive` | 身份/责任数据缺失，不能默认放行 |

脚本的 `allow`、`deny` 和 `inconclusive` 是本地求值器输出，不是 GitHub、GitLab 或其他托管平台的 API 响应。它证明的是输入分离和候选绑定的逻辑不变量；真实平台仍要用普通作者、代码所有者、风险审批者、机器人和管理员分别测试，并保存平台原始审批事件、权限快照、规则版本和最终引用 OID。

## 小结

所有权把变化与责任关联，审批把具体主体对具体候选和范围的决定保存下来。路径、构建图、运行责任和风险角色共同决定谁需要参与；候选、目标或策略变化后，旧决定必须按规则失效。审批数量只有在主体独立、角色有效、范围完整和版本绑定都成立时才有意义。
