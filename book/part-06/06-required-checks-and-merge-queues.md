# 必需检查与合并队列：绿色结果必须属于当前候选

必需检查把自动验证接入主线更新门禁。检查名称显示为绿色，只能证明某个报告者对某个对象提交了一次成功状态。候选 OID、目标基线、流水线版本或报告者身份不清楚时，这个绿色结果不能安全地用于合并决定。

## 进入条件与完成标准

本章讨论协作控制面。CI 怎样触发、checkout、构造候选和生成制品，由[第八篇](../part-08/README.md)详细解释。本章假设团队已经能记录功能头、目标头和候选 OID。

本地只能核对 Git 对象：

~~~bash
git fetch origin
feature="$(git rev-parse --verify HEAD^{commit})"
target="$(git rev-parse --verify origin/main^{commit})"
base="$(git merge-base "$target" "$feature")"
git show --no-patch --format='%H%n%P%n%T%n%s' "$feature"
printf 'target=%s\nbase=%s\n' "$target" "$base"
~~~

fetch 更新本地远程跟踪引用，不读取平台检查。读完本章后，应能设计必需检查契约、处理跳过与失败、判断结果是否过期，并解释合并队列为什么必须按队列位置重建候选。

## 一条必需检查需要稳定身份

规则如果只保存显示名称 `test`，另一个应用或旧流水线可能报告同名状态。稳定检查身份至少包含：

| 字段 | 作用 |
| --- | --- |
| `check_id` | 规则引用的稳定检查标识，不依赖显示文案 |
| reporter principal | 哪个应用、工作负载或服务有权报告 |
| candidate OID | 结果验证的 commit 对象 |
| target OID | 生成组合候选时使用的目标基线 |
| pipeline version | 哪一版可信流水线定义产生结果 |
| attempt | 首次运行、重跑或恢复尝试 |
| conclusion | success、failure、neutral、cancelled、skipped 或 unavailable 等规范化结果 |
| evidence link | 日志、测试清单、制品或来源证明的位置 |

平台原始状态可能比这张表简单，也可能提供更多字段。团队可以做规范化层，但必须保留原始事件，不能把 `skipped`、超时和采集失败统一改成成功。

## 必需检查集合来自风险和变更闭包

所有候选都需要的基线检查可以固定，例如格式、单元测试、秘密扫描和构建输入验证。路径或组件检查则应由变更闭包选择，而不是只看 Git diff 的直接路径。

共享库、构建脚本、锁文件、CI 配置、数据库 schema 和部署模板可能影响许多下游。依赖图缺失时，应运行更宽的检查集或标记证据不足，不能把“没有匹配任务”解释为“无需测试”。

检查集合变化本身要版本化。保护规则期待 `integration-v2`，流水线改名为 `integration` 后，候选可能永久等待；若规则按名称自动接受任意报告者，又会扩大伪造风险。

## 结果属于候选，不属于分支名

功能分支 `feature/a` 从 `F1` 前进到 `F2` 后，`F1` 的结果不能转给 `F2`。目标分支从 `T1` 前进到 `T2` 后，即使功能头仍是 `F2`，基于 `T1` 生成的临时合并候选也可能过期。

检查复用只有在输入等价得到证明时才安全。缓存键至少考虑候选 tree、构建输入、工具链、平台和策略版本。两个候选 tree 相同，但父关系、目标基线或不受信任配置不同，评审与发布结论仍可能不同。

第八篇的[候选提交](../part-08/02-candidate-commits.md)给出 candidate record 的完整模型。本章的合并门禁只接受能回到该记录的检查结果。

## Skipped、neutral 和 unavailable 要显式处理

路径过滤可能让作业没有启动，平台也可能把取消、跳过和中立结论显示为非失败。每种规范化状态都要有门禁语义：

- `success`：报告者、候选和策略都匹配，且实际执行完成；
- `failure`：候选未满足检查，修复代码或可信流水线后重跑；
- `skipped`：只有规则证明该候选确实不需要此检查时才可接受；
- `neutral`：结果提供信息但不作通过决定，不能冒充 success；
- `cancelled`：本次尝试没有结论；
- `unavailable`：报告、日志或外部服务不可用，应按风险选择阻断或升级。

不稳定测试需要单独治理。不断重跑直到绿色会丢失失败频率和候选风险。重跑记录要保留所有 attempt，并区分代码变化、测试修复和基础设施恢复。

## 合并队列解决的是目标前进竞态

有两个已批准变更 A、B，同时基于 `T0` 通过检查。A 先进入主线后，B 的原候选没有验证 `T0+A+B`。合并队列按顺序生成：

~~~text
Q1 = integrate(T0, A)
Q2 = integrate(Q1, B)
~~~

B 在第二个位置的检查必须属于 `Q2`。A 离队、B 更新、目标被外部更新或策略变化时，后续候选要重新生成。不同位置即使包含相同功能头，也不能直接复用队列结果。

队列记录至少保存队列 generation、位置、目标 old OID、前序候选、功能头、候选 OID、策略版本和最终条件更新结果。页面上的“排队中”不够支撑事故调查。

## 最终写入必须比较 expected-old

候选全部通过后，合并服务仍要确认目标引用没有脱离生成候选时的基线。逻辑上相当于：

~~~text
update refs/heads/main from expected_old to final_new
only if current == expected_old
~~~

条件失败应让候选过期，重新从服务器当前目标生成。强制更新或先覆盖本地远程跟踪引用再推送，会掩盖并发变化。

本书的本地实验用 `git update-ref <ref> <new> <old>` 验证 expected-old 条件更新。它能证明 Git 引用比较机制，不能证明托管平台把审批、检查和队列事件原子地接到同一次更新。

## 失败方式和恢复

| 症状 | 先固定 | 安全动作 |
| --- | --- | --- |
| 必需检查永久 pending | check ID、报告者、候选、流水线版本和跳过规则 | 恢复正确映射或报告，不要先关闭全部保护 |
| 同名检查由错误应用报告成功 | 原始 reporter、安装和权限事件 | 使结果无效，收窄报告权限并复查历史合并 |
| 重跑后变绿但没有代码变化 | 全部 attempt、失败类别和环境 | 保留不稳定证据，修复测试或基础设施后再决定 |
| 路径过滤漏跑 | old/new OID、NUL 路径、依赖图和策略版本 | 扩大检查闭包并补跑当前候选 |
| 队列反复重建 | 外部主线更新、功能头变化、flaky 和策略变化 | 按根因分流，限制非队列写入，不盲目增加重试 |
| 队列候选通过但最终更新失败 | expected-old、服务器 current、generation | 过期并重建，不能强推旧候选 |

## 平台验收边界

真实环境至少验证：未授权应用能否伪造同名状态；跳过任务怎样映射；目标前进后结果是否过期；队列候选在哪个 ref 或隐藏对象上运行；管理员、机器人和 API 是否绕过同一规则；审计事件能否关联候选与最终 OID。每项结果都记录产品版本、权限、套餐和核对日期。

## 小结

必需检查是一份带身份和对象绑定的证据，不是一个绿色名称。合并队列为当前目标和当前顺序重建组合候选，解决并发合并让旧结果过期的问题。最终更新仍要比较 expected-old，并把候选、检查、队列和引用事件保存在同一条证据链中。
