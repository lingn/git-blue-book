# CI 身份与状态回报：同名检查不代表同一报告者

CI 既读取候选代码，又向评审和保护规则写入结论。若验证不受信任变更的作业同时拥有主线写权限、发布凭据和状态回报权限，一段候选代码就可能改变用于判断自己的证据。身份与权限设计要把执行者、报告者、合并者和发布者分开。

## 进入条件与完成标准

本章从[机器身份](../part-10/02-machine-identities.md)和[CI 触发与 checkout](../part-08/01-triggers-and-checkout.md)抽取评审所需的身份边界，不重复令牌、工作负载身份和流水线执行细节。

设计前列出所有 CI 主体、凭据来源、允许读取的仓库、允许写入的状态和引用，以及审计中能观察到的委托链。读完本章后，应能定义检查报告者身份，防止候选自授权，并在状态错绑或身份失效时收回结果。

## 四类主体承担不同动作

| 主体 | 需要的能力 | 默认不应拥有 |
| --- | --- | --- |
| 候选验证 runner | 读取固定候选和测试依赖，写临时日志 | 主线写入、生产 secrets、可信制品提升 |
| 检查报告服务 | 为指定候选写规范化结果 | 执行任意候选脚本、修改规则 |
| 合并服务 | 读取审批和检查，条件更新受保护引用 | 重新解释或伪造检查内容 |
| 发布服务 | 读取已批准制品和证据，提升环境状态 | 按可移动分支名重新构建未知对象 |

实现可以把多个动作放在一个平台应用中，但权限、会话和审计仍应区分。一个长期管理员令牌贯穿所有阶段，会让撤销、归因和最小权限都失去边界。

## 候选代码不能决定自己的信任根

评审中的流水线文件、脚本、依赖和容器定义可能都来自候选。若同一候选还能修改必需检查列表、允许报告者或 secrets 范围，它就能降低门禁后给自己返回成功。

受信任控制面至少放在候选之外：

- 允许启动哪些流水线模板；
- 哪些主体能报告必需状态；
- 哪些 secrets 可进入哪种事件；
- 哪些候选允许申请写权限；
- 合并和发布使用哪一版策略；
- 规则更新需要哪些独立审批。

候选可以请求新增测试或修改项目脚本，控制面要把这种变化当作输入，而不是自动采用为本次门禁。

## 状态回报需要可验证声明

一条检查结果至少包含：

~~~text
repository_id: <稳定仓库 ID>
candidate_oid: <完整 OID>
check_id: <稳定检查 ID>
reporter_principal: <工作负载或应用主体>
run_id / attempt: <运行和尝试>
pipeline_version: <可信模板或摘要>
started_at / completed_at: <执行时间>
conclusion: <规范化结论>
evidence: <日志、测试清单、制品或来源证明>
~~~

提交 author、committer 和签名不能替代报告者主体。平台应用名称也可能被重装或迁移，长期审计需要保存安装、工作区、环境和委托身份。

## 短期凭据缩小泄漏窗口

CI 应优先使用绑定仓库、候选、环境和短有效期的工作负载凭据。长期个人令牌会把员工生命周期、个人权限和自动化运行耦合在一起，离职或权限调整后也难以证明所有副本已撤销。

短期不等于安全。凭据声明的 audience、subject、仓库、ref、事件类型和环境仍要由接收端验证；日志、缓存、制品和子进程也可能泄漏凭据。安全模型和轮换流程见[凭据泄漏章节](../part-10/01-credential-leak-history-cleanup.md)。

## Fork 和外部贡献要按不受信任事件处理

外部贡献者提交的代码可能在 fork 上运行，也可能在目标仓库的临时候选上运行。只要代码未受信任，验证任务就不应自动获得写主线、读取生产 secrets 或发布可信制品的能力。

需要高权限复验时，可以在审批后由受信任流水线重新检出固定候选，使用受控模板和新的工作负载身份执行。不能直接提升原不受信任作业生成的可变输出。

## 身份故障会让旧结果失效

应用被卸载、密钥泄漏、工作负载映射错误或组织成员关系变化后，要判断影响窗口内哪些状态由该主体报告。仅撤销凭据不能自动撤销已经写入的绿色结果。

处理顺序是先围栏继续报告和引用更新，再导出主体、候选、检查、时间和使用记录，之后按风险使旧结果过期并重新验证。若日志不足，结论应标记为证据不完整。

## 失败方式和恢复

| 症状 | 先固定 | 安全动作 |
| --- | --- | --- |
| 检查显示正确名称，来源应用不明 | 原始状态事件、安装 ID、principal 和权限 | 不接受结果，恢复可信报告者映射 |
| 候选流水线获得生产 secret | 事件类型、候选 OID、secret 发放和日志 | 撤销轮换、冻结制品与发布，调查泄漏范围 |
| 个人离职后 CI 中断 | token owner、工作流、仓库和环境 | 切换工作负载身份，复查个人令牌产生的历史结果 |
| 重装应用后旧状态仍被接受 | 旧新安装主体、check ID 和规则缓存 | 使旧绑定失效，按新主体重新报告 |
| Runner 被攻陷 | 候选、镜像、缓存、凭据、日志和制品 | 围栏 runner 与输出，使用可信环境重建和复验 |
| 合并服务能自行报告检查 | 权限清单和审计委托链 | 分离报告与更新权限，复查相关合并决定 |

## 本地实验不能证明什么

本地 bare 仓库、hook 和环境变量可以演示不同进程对 refs 的写入限制，不能证明真实平台对应用安装、OIDC 声明、token audience、fork secrets、状态 API 和审计事件的处理。平台验收必须在专用组织和测试仓库中按实际身份执行，并记录产品版本、权限、套餐和核对日期。

## 小结

CI 结果要同时绑定候选和报告者。验证 runner 负责执行不受信任代码，报告服务写入规范化结论，合并服务条件更新引用，发布服务提升已批准制品。信任根位于候选之外，主体失效时还要使影响窗口内的旧结果过期，不能只撤销当前凭据。
