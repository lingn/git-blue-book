# 受保护引用与例外：把团队约定变成可审计更新

Git 允许有写权限的客户端请求创建、移动和删除引用。受保护引用在服务端增加一层决定：哪个主体可以对哪些 refs 执行哪些更新，必须携带哪些评审与检查证据，发生竞态或证据缺失时怎样处理。

## 进入条件与完成标准

本章使用厂商无关名称。不同平台可能称为分支保护、规则集、推送规则、合并检查或受保护分支，能力、继承、API、权限和计费都可能变化。落地前必须在[事实登记表](../../docs/FACT-REGISTER.md)记录目标产品的核对结果。

本章只解释一次仓库引用更新。跨组织的规则作用域、组合、渐进执行和例外生命周期以[规则与例外治理](../part-12/03-policy-rules-and-exceptions.md)为权威来源。

读完本章后，应能把团队约定翻译为服务端引用更新契约，设计普通、自动化和紧急路径，并在规则误配时安全回退而不制造无保护窗口。

## 一次受控更新有七组输入

~~~text
repository_id
target_ref, expected_old, proposed_new
actor principal and delegated identity
candidate and construction context
review and ownership decisions
required checks and reporter identities
policy version and active exception
~~~

服务端最终输出 accepted、denied 或 inconclusive，并保存原因。`accepted` 还要记录真实 new OID；`denied` 保存命中规则和修复线索；`inconclusive` 表示证据采集、策略求值或外部服务不完整，不能悄悄按 success 处理。

## 规则对应具体风险

| 风险 | 常见控制 | 控制仍不能证明什么 |
| --- | --- | --- |
| 未经评审进入主线 | 只允许评审请求或合并服务更新 | 评审是否覆盖真实风险 |
| 作者自行批准 | 独立审批或指定所有者审批 | 审批者是否有完整上下文 |
| 新提交沿用旧决定 | 候选变化后使审批和检查过期 | 平台失效规则是否无漏项 |
| 未验证候选进入主线 | 必需检查绑定候选和报告者 | 测试是否充分、外部输入是否可信 |
| 主线被删除或改写 | 禁止删除和非快进更新 | 管理员、API 或机器身份是否绕过 |
| 并发合并复用旧绿色结果 | 合并队列和 expected-old 条件更新 | 队列候选是否覆盖真实发布路径 |

规则数量不是成熟度指标。每条规则都要有 owner、失败处理、观察指标、例外条件和回退版本。

## 直接 push、合并服务和发布机器人分别授权

普通贡献者通常可以推功能分支，不应直接更新主线。合并服务只在评审与检查满足时更新指定主线。发布机器人可能创建附注标签或更新发布引用，不应因此获得删除主线和修改规则的权限。

权限要按 ref 和动作拆分：创建、快进、非快进、删除、创建标签、移动标签和修改默认分支是不同能力。一个能写 `refs/heads/*` 的 deploy key 可能比实际任务需要的范围大得多。

本地 `receive-pack` hook 可以观察 old OID、new OID 和 ref name，并按祖先关系拒绝更新。它看不到平台评审、真实身份、应用安装和合并队列，除非上层系统把可信断言传入并验证。不能把客户端提供的环境变量当作认证身份。

## 规则变化先观察再执行

新增必需检查、收紧审批或扩大保护范围，可能同时阻断大量仓库。安全推广顺序是：固定当前规则和行为基线，在测试仓库验证，再用 audit 或 would-deny 观察真实流量，修正空匹配和身份例外，最后按 cohort 扩大 enforce。

每阶段定义停止条件，例如拒绝率异常、必需检查永久等待、机器人入口全部失败、审计事件缺失或紧急通道不可用。没有观察模式的平台，可以先在影子求值服务或少量 canary 仓库验证，不能直接全组织切换。

## 例外是有期限的对象

紧急修复可能需要绕过等待时间、某项不稳定检查或普通合并路径。例外至少包含：

~~~text
exception_id
incident_or_change_id
repository_id, target_ref
allowed_actor, allowed_action
expected_old, optional proposed_new
waived_rule_ids
approver and reason
starts_at, expires_at
compensating_controls
usage events and revocation
~~~

例外不应是永久管理员列表，也不能用一个宽 allow 覆盖所有规则。使用后立即核对服务器最终 OID、CI 与部署状态，回收会话和权限，并保留真实时间顺序。事后补评审只能作为后续决定，不能伪装成更新前已经批准。

Break-glass 身份与普通例外不同。它用于策略服务、身份系统或控制面本身故障，需要独立保管、双人启用、最短有效期和专门演练。常规热修复不应每次都走 break-glass。

## 回退规则不等于关闭保护

规则变更造成全面阻断时，先恢复上一份已知良好策略版本。回退前后仍要保留最小基线，例如禁止删除、限制非快进、固定合并主体和记录 old/new OID。把总开关关闭会制造新的未知更新窗口。

回退后审查降级期间发生的每次引用更新，再修复检查名称、作用域、主体映射或外部服务。策略配置和平台实际观察要对账，声明文件恢复并不证明服务端已经生效。

## 行为探针验证规则是否真的工作

平台配置页面显示启用，只能证明声明存在。专用测试仓库应定期验证：

1. 普通贡献者直接更新主线被拒绝；
2. 缺审批或检查的评审不能合并；
3. 满足当前候选要求后，合并服务能条件更新；
4. 非快进和删除请求按规则拒绝；
5. 检查改名、所有者缺席和目标前进时不会错误通过；
6. 紧急例外只允许目标动作，并能到期和撤销；
7. 每条 accepted/denied/exception 事件都能从审计系统查询。

这些输出属于平台控制面，不能用本地 bare 仓库伪造后写入正文。验收记录注明产品、版本、权限、套餐、测试主体和核对日期。

## 失败方式和恢复

| 症状 | 先固定 | 安全动作 |
| --- | --- | --- |
| 新规则让所有评审无法合并 | 策略版本、would-deny、检查与身份映射 | 停止扩大范围，恢复上一已知版本 |
| 管理员日常直接推主线 | actor、old/new OID、规则和绕过原因 | 收窄绕过，复查历史更新并建立正常合并路径 |
| 新分支命名没有保护 | 真实 refs、scope 和规则部署 | 围栏漏保护 ref，审查窗口内所有更新 |
| 例外到期后仍可写 | 例外对象、缓存、会话和使用事件 | 撤销授权与会话，检查到期后的引用更新 |
| 回退时出现无保护窗口 | 旧新策略、传播时序和更新事件 | 恢复最小基线，调查窗口，不用全员管理员补救 |
| 页面规则与行为探针不一致 | 声明、平台观测、审计和探针 | 标记策略漂移，按可信来源修复并重新验收 |

## 小结

受保护引用把身份、候选、审批、检查和策略绑定到一次 expected-old 引用更新。普通贡献、合并服务、发布机器人和紧急身份分别授权；规则先观察再执行，例外有范围、有期限并保留使用事件。故障时恢复上一份策略和最小基线，不能用关闭全部保护换取短暂畅通。
