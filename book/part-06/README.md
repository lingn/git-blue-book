# 第六篇：让共享历史经过可审查、可验证的更新

个人仓库里，分支移动通常只影响自己。提交进入团队共享的主线后，同一个引用会同时被评审、CI、发布、审计和其他开发者引用。团队协作因此多出一组 Git 对象之外的状态：谁提出变更，评审针对哪个候选，检查验证了哪个对象，主线更新时使用了哪一份规则，以及紧急绕过是否已经回收。

本篇建立一条厂商无关的协作链。GitHub 的 pull request、GitLab 的 merge request 和其他托管平台的变更请求，在本书中都称为“评审请求”。平台按钮和套餐会变化，本篇只使用稳定的对象、身份、评审、检查和引用更新模型。具体平台落地前，仍要按产品版本、权限和核对日期确认行为。

## 进入条件

开始前应已经理解：

- commit、parent、tree、引用和可达性；
- 本地分支、远程跟踪引用和服务器引用的区别；
- merge、rebase 和 cherry-pick 会怎样改变提交图；
- `fetch`、`push`、非快进拒绝和显式租约的边界；
- 工作区、index 与候选提交不是同一层状态。

这些模型分别由[第三篇](../part-3/README.md)、[第四篇](../part-4/README.md)和[第五篇](../part-5/README.md)承担。本篇不重复命令定义，只解释它们进入多人系统后的决策和证据要求。

## 三条职责边界

本篇只承担从变更提议到共享引用更新的协作模型。相邻主题按下面的边界分工：

| 问题 | 权威位置 | 本篇只保留什么 |
| --- | --- | --- |
| CI 检出了哪个候选、怎样生成制品、怎样部署 | [第八篇](../part-08/README.md) | 合并前需要哪类结果，以及结果何时过期 |
| 组织规则怎样组合、推广、例外和回退 | [第十二篇](../part-12/README.md) | 单个仓库的一次引用更新需要哪些控制 |
| push、认证、授权和远程跟踪引用 | [第四篇](../part-4/README.md) | 引用更新进入评审控制面后的额外状态 |
| amend、rebase、revert、reset 和强推恢复 | [第五篇](../part-5/README.md) | 共享边界怎样改变可用动作 |

本地 bare 仓库和 hook 能验证 Git 接收、引用更新与并发条件，不能冒充托管平台的评审、代码所有者、套餐权限、合并队列或审计日志。本篇凡是涉及平台控制面的实验，都会明确写出这一限制。

## 读完后的能力

读完本篇后，应能为一次主线更新固定功能头、目标基线、候选和最终提交；能判断审批与检查是否仍属于当前候选；能解释三种合并方式对 OID、回滚和归因的影响；能设计代码所有权、必需检查、合并队列和紧急例外的最小协作契约；也能在平台显示异常时，把 Git 数据面、身份、评审、CI 和策略证据分开采集。
