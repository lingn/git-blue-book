# 可重复构建：把同一输入变成可比较的输出

同一个 Git 提交不保证每次构建得到相同字节。提交只固定了 commit、tree 和其中的文件内容，构建还会读取依赖、编译器、基础镜像、时间、随机数、路径、区域设置、网络响应和缓存。要判断一个制品能否被复现，必须先定义“哪些输入相同”，再定义“输出相同”需要达到什么强度。

本章把可重复构建放在候选之后、制品提升之前。候选章负责回答“应该验证哪个源码对象”，本章负责回答“在一组声明的输入和过程约束下，能否再次得到同一制品”。[制品与部署证据链](03-source-artifact-deployment-evidence.md)负责把已经生成的摘要提升到发布、部署和运行环境；本章不把本地归档实验冒充成真实编译器或容器平台的证明。

本章以 Git 2.49.0、Bash 和本地隔离仓库为验证基线，核对日期为 2026-08-22。不同语言工具链、容器构建器、制品库和 CI 平台的确定性开关、权限、缓存和计费会变化，落地时要记录产品、版本、权限、套餐和核对日期。

## 进入条件和退出能力

进入本章前，读者应理解 commit/tree、候选上下文、制品摘要和分离 `HEAD`。读完后，应能：

- 区分逐字节相同、语义相同和来源可追溯三种不同目标；
- 枚举一次构建的源码、依赖、工具链、运行环境和外部输入闭包；
- 找出时间、随机数、路径、顺序、区域设置、网络和缓存造成的非确定性；
- 设计两次或多次构建的比较协议，并说明失败时保留哪些证据；
- 判断什么时候必须修正构建过程，什么时候只能保留差异并依靠来源证明；
- 把构建一次、多环境提升和数据库兼容边界接入发布决策。

## 先定义“相同”

“可重复”在不同团队中可能表示三种强度。发布政策必须选择一种作为门槛，不能在构建失败后临时改变定义。

| 目标 | 判断方式 | 能证明什么 | 不能证明什么 |
| --- | --- | --- | --- |
| 逐字节可重复 | 相同输入多次生成的制品 digest 完全相同 | 字节输出在声明环境中稳定 | 未声明输入没有影响 |
| 语义等价 | 解包、接口、测试或规范化比较一致 | 输出行为或内容满足选定规范 | 每个字节、元数据和签名都相同 |
| 来源可追溯 | 制品 digest 与源码、依赖、工具链和命令有可验证关联 | 可以解释制品从哪里来、由谁构建 | 不保证第二次构建会得到同一字节 |

逐字节比较最容易自动化，但并非所有输出都适合它。带有签发时间的签名、包含机器路径的调试符号或依赖外部服务的生成文件可能无法直接消除差异。此时要在发布前明确语义比较和来源证明的门槛，不能先把“相同”降级成“看起来能运行”。

## 构建输入是一个闭包

构建输入不止是候选 commit。一个可以复核的输入闭包至少包括：

```text
candidate commit/tree
generated source and code generator
direct and transitive dependencies
package or module resolution result
compiler/interpreter/linker/tool versions
runner image and operating-system files
build flags, environment and locale
clock, random seed and filesystem ordering
network responses, credentials and external services
cache contents and cache provenance
```

其中任意一项未固定，都可能让相同源码产生不同字节。`source_commit` 和 `source_tree` 仍然必须保留，因为不同 commit 可以有相同 tree，构建日志、评审和候选过期规则需要提交身份；但它们只是输入闭包中的第一层。

### 源码和生成文件

源码归档、代码生成器和生成结果要分开记录。把生成文件提交到 Git 可以让 tree 固定，但生成器版本、模板、输入 schema 和生成命令仍可能在 runner 外部变化。构建流程应选择一种明确策略：

- 生成文件作为源码的一部分，构建前验证它与生成命令的结果一致；
- 生成文件不入库，每次在固定工具链中生成，并把生成器和输入摘要写入来源记录。

两种策略都可以成立，不能在同一仓库里一部分生成文件被信任、另一部分又被静默覆盖。生成步骤如果读取工作区之外的文件，要把这些文件纳入输入清单，或在隔离环境中拒绝读取。

### 依赖和缓存

依赖锁文件固定的是解析结果，前提是 resolver、索引、镜像和传递依赖也有稳定身份。一个顶层版本号可能解析到不同包字节；一个 Git 依赖固定了 commit，也可能在其构建过程中下载可变工具或脚本。

缓存是加速手段，不是来源证明。缓存键至少要包含会影响输出的输入摘要，缓存条目还要记录创建者、生成时间、工具链和来源。命中旧缓存时，构建应能从干净环境重新取得相同输入；无法证明缓存来源时，应把它当作未取得输入，不能把缓存内容直接提升到可信制品。

### 工具链和 runner

编译器小版本、链接器、系统头文件、证书、时区数据库和基础镜像都可能改变输出。记录“Linux runner”或“使用默认 JDK”不够，至少保存工具名称、完整版本、镜像 digest、关键系统包和执行器身份。工具版本如果只能由路径推断，应在构建开始时打印并把输出摘要化保存，不能事后从日志猜测。

## 常见非确定性来源

| 来源 | 典型表现 | 控制办法 | 仍需保留的证据 |
| --- | --- | --- | --- |
| 时间 | archive、编译产物或压缩文件包含当前时间 | 统一 `SOURCE_DATE_EPOCH` 或固定输入时间 | 时间来源、时区和是否允许变化 |
| 随机数 | UUID、临时目录、并行任务顺序不同 | 注入可审计种子，或移除随机字段 | 种子来源、用途和泄漏风险 |
| 文件顺序 | 不同文件系统枚举顺序改变归档或链接结果 | 按字节序排序，显式定义 locale | 排序规则和文件清单 |
| 绝对路径 | 调试信息或生成文件带入 runner 路径 | 使用稳定前缀或剥离路径 | 剥离规则和调试信息取舍 |
| 区域设置 | 小数、排序、大小写和换行不同 | 固定 `LC_ALL`、`LANG`、`TZ` 和换行规则 | 实际环境变量白名单 |
| 网络 | 在线索引、远程脚本、时间服务返回变化 | 离线构建、完整镜像、精确 digest | 请求目标、响应摘要和凭据范围 |
| 压缩/并行 | gzip header、线程调度、压缩库版本变化 | 固定参数、线程数和工具版本 | 工具版本、参数和并行度 |
| 机器特性 | CPU 指令集、内核、链接地址布局不同 | 固定目标平台和特性集合 | runner 标签、架构和内核版本 |

控制办法不是把所有环境变量都写进日志。环境可能包含秘密，使用字段白名单并对日志做脱敏；需要证明的字段进入签名或受保护的构建清单，不能把完整 `env` 输出当作审计证据。

## 构建清单的最小契约

构建清单应在输出完成后以不可变方式保存，并与制品摘要关联。格式可以是组织定义的 JSON、DSSE、文本清单或平台证明，字段语义不能退化为一个版本字符串：

```text
schema_version
repository_identity
candidate_commit / candidate_tree / candidate_kind
source_archive_digest
generated_source_digest
dependency_lock_digest
resolved_dependency_digests
builder_identity / runner_image_digest
toolchain_versions
build_command_identity
environment_allowlist_digest
source_date_epoch / locale / timezone
cache_key / cache_provenance
external_input_digests
artifact_name / artifact_digest / artifact_size
attempt / started_at / finished_at
comparison_policy / comparison_result
```

`comparison_result` 要说明是逐字节通过、语义比较通过、来源证明完整，还是因缺少输入而无法判断。清单本身也要计算摘要，防止制品字节变了而清单仍然声称旧摘要；清单中不能写入 token、私钥、完整环境变量和未经脱敏的内部 URL。

### 清单和日志不是同一件事

日志适合记录过程和失败上下文，清单适合表达被批准的输入和输出。日志可以被截断、重试或写入不同系统，不能只靠一行“build passed”恢复来源。发布系统应把清单位置、访问主体、保留期和签名策略写入发布记录；签名和信任根的完整设计见第十篇。

## 设计一次可重复性比较

一次比较应把“准备输入”和“执行构建”分开，避免第一次运行留下的工作区、缓存或生成文件污染第二次。推荐状态机如下：

```text
固定候选与构建清单
  -> 创建干净 runner / 工作区
  -> 取得锁定的依赖、工具链和外部输入
  -> 构建 attempt A
  -> 保存制品、日志、清单和摘要
  -> 丢弃工作区与未声明缓存
  -> 使用同一清单构建 attempt B
  -> 比较摘要和差异，分类结论
```

两次构建都要从干净起点开始。仅在同一个工作区连续运行两次，可能把第一次生成的文件、编译缓存或下载内容带到第二次，得到“稳定”但不可归因的结果。若必须复用缓存，先执行一次禁用缓存的基线，再把缓存作为单独变量测试，并保存命中详情。

在 CI 工作目录中，下面的片段只验证同一个 Git 候选能否生成相同的源码归档。它不是任意语言编译器的通用构建脚本：

```bash
source_commit="${CI_SOURCE_COMMIT:?CI_SOURCE_COMMIT is required}"
runner_temp="${CI_RUNNER_TEMP:?CI_RUNNER_TEMP is required}"
test -d "$runner_temp"
git cat-file -e "$source_commit^{commit}"

archive_a="$runner_temp/source-a.tar"
archive_b="$runner_temp/source-b.tar"
git archive --format=tar --mtime='UTC 1970-01-01' \
  --prefix=source/ "$source_commit" > "$archive_a"
git archive --format=tar --mtime='UTC 1970-01-01' \
  --prefix=source/ "$source_commit" > "$archive_b"

if command -v sha256sum >/dev/null 2>&1; then
  digest_a="$(sha256sum "$archive_a" | awk '{print $1}')"
  digest_b="$(sha256sum "$archive_b" | awk '{print $1}')"
else
  digest_a="$(shasum -a 256 "$archive_a" | awk '{print $1}')"
  digest_b="$(shasum -a 256 "$archive_b" | awk '{print $1}')"
fi

test "$digest_a" = "$digest_b"
printf 'source_archive_digest=%s\n' "$digest_a"
```

前置条件是 runner 已核对候选 OID、当前 Git 版本支持 `--mtime`、临时目录只供当前作业使用，并且 `source_commit` 已从可信调度记录取得。命令只读 commit 和 tree，在临时目录写两个归档文件；它不会修改 refs、index 或工作区。文件不存在、对象缺失、摘要工具不可用或两次摘要不同，都应使作业失败并保留清单和日志。

恢复办法是丢弃临时 runner 和未批准制品，检查候选、工具版本和工作区来源后重新执行。不要先把 `--mtime`、排序或 `SOURCE_DATE_EPOCH` 写入发布清单再声称编译产物可重复；这些选项只控制它们实际覆盖的输入。

## 处理“不相同”的结果

比较失败后先保存两个制品和对应清单，不能只留第二次输出。按证据分为四类：

| 结果 | 说明 | 默认决策 |
| --- | --- | --- |
| digest 相同 | 声明范围内逐字节一致 | 可进入下一层发布门禁，仍需核对来源和权限 |
| digest 不同，已知差异 | 差异来自明确允许的签发时间、签名或平台元数据 | 按发布政策做语义比较，并保留差异清单 |
| digest 不同，未知差异 | 输入、工具或过程有未解释变化 | 阻止提升，先定位非确定性 |
| 只有一个 attempt | 没有比较样本 | 不能称为可重复，只能称为一次构建 |

差异分析可以先比较归档清单、文件大小和规范化内容，再对二进制做字节级定位。规范化比较的规则必须固定并进入 `comparison_policy`，不能为让结果通过而临时删除字段。两个制品都可能可运行，但只有一个来源证明完整时，发布系统应按证据缺口处理，而不是按运行结果选一个。

## 构建一次，再提升同一制品

一旦某个制品通过构建和安全门禁，测试、预发布和生产通常应引用同一不可变 digest，只改变经过审计的环境配置。每个环境重新构建，即使源码和依赖看似相同，也会产生新的制品、清单、检查结果和回退目标。

这条策略不能绕过数据库和外部副作用。新制品与旧制品同时运行时，API、消息、schema 和配置必须覆盖混合版本窗口；制品回退可能需要向前修复数据或恢复兼容配置。具体发布引用、部署观测和五种回退动作见[制品与部署证据链](03-source-artifact-deployment-evidence.md)。

## 常见误区与故障恢复

| 误区或症状 | 先检查 | 安全恢复 |
| --- | --- | --- |
| 同一 commit 每次摘要不同 | runner、依赖解析、时间、路径、缓存和网络 | 保存两套清单和制品，固定一个变量后重跑 |
| 只有本地构建可重复 | 本地工具版本、操作系统、缓存和环境 | 在代表性干净 runner 重建，不能把本地摘要直接发布 |
| 关闭时间戳后仍不一致 | 文件顺序、压缩参数、随机种子、绝对路径 | 比较差异字节，增加明确的构建输入或规范化规则 |
| 缓存命中后通过，禁用缓存失败 | 缓存内容和生成者、依赖镜像和网络 | 先恢复可验证输入，再决定缓存是否纳入受信任闭包 |
| 语义相同但字节不同 | 比较政策和差异清单 | 明确语义门槛并保留来源证明，不把它标成逐字节通过 |
| 构建清单缺少工具或依赖身份 | runner 日志、锁文件、外部 resolver 记录 | 阻止制品提升，补齐清单或重新构建 |
| 第二次构建读取第一次工作区 | 工作区摘要、生成文件和缓存目录 | 丢弃两个工作区，从干净 runner 重新执行 |

遇到不确定性时，恢复路径优先保护证据，再清理环境。删除第一次制品或覆盖清单会让后续无法判断差异来自代码、环境还是修复动作；只有在摘要和清单已经进入受保护存储后，才可以按保留策略清理临时目录。

## 隔离实验与真实边界

在本书仓库根目录运行：

```bash
bash scripts/verify-reproducible-build.sh
```

实验使用 `mktemp` 临时目录和虚构身份，创建一个本地 Git 仓库。它在相同候选 commit 上生成两份固定时间、固定前缀的源码归档，比较两份摘要；随后故意改变一个未声明的构建输入，验证摘要变化会被识别，并检查清单保存了候选、tree、输入摘要和输出摘要。实验不连接网络，不读取用户级 Git 配置，也不修改蓝皮书仓库。

成功输出为：

```text
Reproducible source archive, manifest, and nondeterministic input detection passed.
```

该实验只证明 Git 源码归档和摘要比较的确定性，以及未声明字节变化会被发现。它不证明 Java、Go、Rust、C/C++、容器镜像、签名服务、远程依赖、缓存、制品库、CI runner 或跨平台编译已经可重复；这些需要在目标工具链和代表性环境中重新采集。

## 综合练习：写出一条可复现构建契约

假设团队发现同一个候选在预发布和生产环境重新构建后摘要不同，但两套实例都通过健康检查。请写出处理方案，至少回答：

1. 两次构建要保留哪些候选、依赖、工具链、环境、缓存和外部输入证据；
2. 如何区分时间戳差异、未知依赖漂移和工作区污染；
3. 在不能立即做到逐字节相同的情况下，发布门禁采用什么语义比较和来源证明；
4. 是否应该停止当前发布，如何从已知摘要制品恢复；
5. 数据库迁移和混合版本窗口是否允许直接部署旧制品。

合理方案会先停止继续提升并保存两套制品，不会因为“都能启动”就把它们视为同一版本。修复非确定输入后重新构建，或明确采用语义比较和来源证明，最终由发布政策决定是否放行。

## 小结

可重复构建是对完整输入闭包和执行过程的约束，不是对 Git 提交的另一种叫法。逐字节摘要相同、语义等价和来源可追溯是不同结论，必须在构建前写进门禁。

构建要从干净状态开始，固定依赖、工具链、时间、区域设置、随机数、路径、网络和缓存，并为每次 attempt 保存清单和制品。摘要不同时先保留证据并定位差异；构建一次后提升同一制品，才能避免不同环境重新构建带来的隐性漂移。下一章将把源码、制品摘要和发布引用接入明确的发布与提升决策。
