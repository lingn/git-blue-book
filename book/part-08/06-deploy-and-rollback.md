# 部署与回退：把 rollout 状态和恢复动作分开

上一章把发布 tag、制品摘要和审批记录连成了提升前的证据。本章继续向运行环境推进，回答三个更容易被混淆的问题：部署请求是否被接受，实例是否真的加载了目标制品，出现异常时应该撤回哪一种状态。

这里的部署是厂商无关的运行控制面模型。平台可以把它实现为任务定义、工作负载、发布、环境或 rollout，但都必须能回答同一组问题：请求针对哪个不可变制品，当前有多少实例处于哪个批次，健康门槛是什么，谁能暂停或继续，旧实例何时被围栏，回退后如何证明已经恢复。Git 可以保存源码和部署脚本，却不能替运行平台停止流量、撤销消息或恢复数据库。

本章以 Git 2.49.0、Bash 和本地隔离目录为实验基线，核对日期为 2026-08-23。真实平台的 rollout 字段、暂停权限、金丝雀流量、健康探针、并发上限、审计、计费和回退 API 会随产品、版本、角色和套餐变化；采用本章模型时，应把这些控制面事实登记到 `docs/FACT-REGISTER.md`，并在目标环境重新核对。

## 进入条件和退出能力

进入本章前，读者应理解候选 commit、构建清单、制品 digest、发布引用和数据库兼容窗口。读完后，应能：

- 区分部署请求、rollout 状态、实例实际 digest 和流量观察；
- 为滚动、金丝雀、蓝绿和手动暂停写出厂商无关的状态转换和停止条件；
- 在实例仍有旧版本、健康检查滞后或异步任务未完成时，判断能否继续扩大流量；
- 选择制品回退、配置回退、源码 `revert`、数据库向前修复或数据恢复，而不是笼统地说“回滚”；
- 为回退保存旧制品、旧配置、数据库版本、消息兼容性和运行观测证据；
- 说明本地实验能证明哪些数据面不变量，哪些结论必须由平台控制面、数据库和运行系统补证。

## 部署有四个不同的事实

“发布成功”至少由四类事实组成，不能用一个页面状态代替：

| 事实 | 问题 | 典型证据 | 可能的假阴性或假阳性 |
| --- | --- | --- | --- |
| 部署请求 | 系统是否接受了哪个制品、配置和目标 | 请求 ID、制品 digest、配置版本、策略版本 | 请求接受但没有实例变化 |
| rollout 状态 | 新旧批次如何替换、当前是否暂停 | 批次 ID、实例计划、暂停原因、流量比例 | 控制面完成但观测滞后 |
| 实例实际版本 | 进程或任务加载了什么字节 | 实例 build identity、镜像 digest、任务定义、启动日志 | 只读启动参数，未读运行进程 |
| 流量和业务结果 | 用户请求是否经过新版本且满足门槛 | 版本维度错误率、延迟、业务指标、探针 | 探针通过但关键路径失败 |

一次部署记录至少要保存：

```text
deployment_id
environment / cluster / region
release_tag / source_commit / artifact_digest
configuration_version / database_schema_version
rollout_strategy / batch_plan / health_policy
requested_by / approved_by / deployer_identity
state_history / pause_reason / stop_reason
instance_observations / traffic_observations
rollback_target / rollback_reason / completed_at
```

清单和日志不能包含 token、私钥、完整环境变量或未经脱敏的内部地址。`deployment_id` 应稳定且不可复用，状态历史追加写入，不能用最后一次页面值覆盖先前的失败和暂停。

## 部署请求必须绑定不可变输入

部署入口不应接收 `main`、`latest` 或一个可重新解析的版本字符串作为唯一输入。请求至少携带已经通过上一章门禁的制品 digest，并引用源码提交、构建清单和允许的配置版本：

```text
artifact_digest = sha256:<approved-output>
source_commit = <candidate-commit>
build_manifest_digest = sha256:<manifest>
configuration_version = <immutable-config-id>
database_compatibility = <declared-window>
rollout_strategy = canary | rolling | blue-green | manual
```

运行平台在受理时应重新查询制品摘要和清单，而不是相信调用者上传的文件名。平台受理和部署器读取之间如果存在竞态，应通过内容寻址、写后只读或等价的不可变语义消除覆盖风险。

一个最小的本地校验片段如下。它只读取受保护清单和制品文件，不执行清单内容：

```bash
manifest_file="${MANIFEST_FILE:?MANIFEST_FILE is required}"
artifact_file="${ARTIFACT_FILE:?ARTIFACT_FILE is required}"
expected_digest="${EXPECTED_ARTIFACT_DIGEST:?EXPECTED_ARTIFACT_DIGEST is required}"
expected_commit="${EXPECTED_SOURCE_COMMIT:?EXPECTED_SOURCE_COMMIT is required}"

test -r "$manifest_file"
test -r "$artifact_file"
if command -v sha256sum >/dev/null 2>&1; then
  actual_digest="$(sha256sum "$artifact_file" | awk '{print $1}')"
else
  actual_digest="$(shasum -a 256 "$artifact_file" | awk '{print $1}')"
fi
manifest_digest="$(awk -F= '$1 == "artifact_digest" {print substr($0, index($0, "=") + 1)}' "$manifest_file")"
manifest_commit="$(awk -F= '$1 == "source_commit" {print substr($0, index($0, "=") + 1)}' "$manifest_file")"
test "$actual_digest" = "$expected_digest"
test "$manifest_digest" = "$actual_digest"
test "$manifest_commit" = "$expected_commit"
```

前置条件是清单和制品来自上一阶段的受保护存储，期望值来自审批记录，当前执行主体拥有只读核对权限。成功只说明输入可以进入 rollout；它不说明实例已启动、流量已切换或健康门槛已经满足。文件不存在、摘要失配、清单重复键或来源提交不符时应拒绝请求。恢复办法是保留失败请求和摘要，重新取得已批准的制品，不能修改清单来迁就现有字节。

## Rollout 状态机和停止条件

把部署写成状态机能避免“按钮变绿”掩盖中间状态。一个通用状态集合如下：

```text
requested
  -> admitted
  -> preparing
  -> canary_or_first_batch
  -> observing
  -> progressing
  -> completed

preparing / observing / progressing
  -> paused
  -> stopped
  -> rolling_back
  -> rolled_back | rollback_failed | inconclusive
```

状态转换应是条件更新，包含当前版本、目标版本、批次代数和期望旧状态。重复的继续、暂停或回退请求必须幂等；如果另一个执行者已经推进了代数，旧请求应被拒绝，而不是覆盖新计划。

发布策略的差别在于流量和实例替换顺序，不在于是否需要证据：

| 策略 | 先做什么 | 适用风险 | 必须补的证据 |
| --- | --- | --- | --- |
| 滚动 | 按批次替换旧实例 | 需要保持容量和混合版本兼容 | 每批实际 digest、剩余旧实例、容量余量 |
| 金丝雀 | 让小比例或指定流量进入新实例 | 希望先观察真实请求 | 流量选择器、暴露比例、版本维度指标和观察窗口 |
| 蓝绿 | 保留完整的旧环境，切换入口流量 | 需要快速切回旧环境 | 两套环境健康、入口切换记录、旧环境围栏 |
| 手动暂停 | 在门槛处等待人工批准 | 高风险或不可逆迁移 | 暂停原因、批准主体、有效期和继续条件 |

任何策略都必须定义硬停止条件，例如实例启动失败、实际 digest 不符、错误率超过阈值、关键业务指标回退、容量低于余量、数据库兼容性未知、消息积压超过上限或旧实例无法被围栏。停止后不应自动扩大流量；自动回退也必须有已知良好目标和验证步骤。

健康门槛至少分为四层：进程存活、依赖就绪、协议兼容和业务结果。只看进程存活会放过连接池、权限、schema、消息格式或关键交易失败。门槛还要有观察窗口和最小样本量，避免刚启动的少量请求把偶然成功误判成稳定。

## 运行版本核验和旧实例围栏

控制面显示目标 digest 只表示计划或任务定义中的值。部署器必须从实际实例或等价可信运行时读取 build identity，并按实例、批次和区域聚合：

```text
expected artifact digest
  == task definition digest
  == container/image or package digest
  == process build identity
  == observed traffic version
```

等号链中任一项缺失，都只能把状态标成 `inconclusive`，不能推断成功。应用版本端点可以返回非敏感的 `build_identity` 和 `artifact_digest`，但不能暴露环境变量、令牌或密钥。探针响应也应带版本维度，否则全局健康率无法回答新批次是否安全。

在 rollout 完成前，旧实例有两个边界：它们可能仍接收流量，也可能仍执行长任务。围栏至少包含：

- 停止把新请求路由到旧实例，保留正在处理的请求超时和排空策略；
- 标记旧实例代数，拒绝它们继续消费需要新协议的消息；
- 等待长任务完成、转移或明确取消，记录任务状态和幂等键；
- 在删除旧实例前再次读取实际 digest，保存终止原因和时间；
- 回退时禁止旧批次和新批次同时无界扩张，设置单一流量写入权威。

主线继续前进不会改变已部署实例。部署记录必须引用固定的 `source_commit` 和 `artifact_digest`，不能在事后用 `main` 当前值补齐运行版本。

## 四种 rollout 的暂停与恢复

### 滚动部署

滚动部署每次只替换一部分实例。下一批开始前，前一批必须同时满足实际 digest、容量、依赖就绪和业务门槛。若旧实例数量已经低于可承受余量，继续替换会把一次局部故障扩大为容量事故。

暂停时保留批次计划、已替换实例、流量和观察窗口。恢复前重新核对目标制品和配置版本，不能直接重放一个已经过期的“继续”按钮。回退可按相反顺序恢复已知良好制品，但必须确认当前 schema 和消息格式仍兼容。

### 金丝雀发布

金丝雀不是“部署一台机器”这么简单。要固定流量选择规则、比例或请求数、观察窗口、对照组和最小样本量。内部管理员流量、重试流量和缓存命中可能让金丝雀指标失真；应记录这些过滤条件，并把关键业务结果与技术指标一起观察。

金丝雀失败时先停止扩大流量，再决定让当前少量实例继续承接、恢复旧制品还是切换到蓝绿旧环境。不要在没有保留指标和请求样本的情况下删除金丝雀实例，否则无法判断是版本问题、流量选择问题还是数据问题。

### 蓝绿切换

蓝绿发布同时保留两套环境，入口切换是一个独立的控制面动作。切换前要分别确认两套实例实际 digest、配置、schema、消息消费者和外部连接；切换后继续观察新环境，并为旧环境设置不可接收新流量的围栏。旧环境不能因为“暂时不用”就立刻删除，它是回退目标和取证来源。

切回旧环境只改变入口和允许的运行版本，不会自动撤销新版本已经写入的数据或发送的消息。切回后仍要核对旧环境是否能读写当前 schema，并处理重复消费和幂等问题。

### 手动暂停

高风险迁移、权限变化和外部依赖切换可以在每个门槛处暂停。暂停记录要包含原因、待补证据、批准主体、有效期和继续条件。暂停不是无限期冻结，超过有效期应自动转为 `stopped` 或 `inconclusive`，重新评估候选和配置。

## 回退动作不是同一个按钮

事故处理中至少区分以下动作：

| 动作 | 解决的问题 | 不能解决的问题 | 典型前置检查 |
| --- | --- | --- | --- |
| 制品回退 | 新二进制、镜像或包有缺陷 | 已写入的数据、已发消息和外部副作用 | 旧制品 digest 可取，兼容当前 schema、配置和协议 |
| 配置回退 | 错误开关、路由、限流或依赖地址 | 制品本身的逻辑缺陷 | 旧配置版本和 secret 仍有效，变更可审计 |
| 源码 `revert` | 让共享历史表达反向变化 | 已部署版本、数据库和外部系统 | 反向提交可评审、可构建，且不会掩盖事故现场 |
| 数据库向前修复 | 新版本已经改变 schema 或数据 | 不能自动恢复被删除的原始数据 | 已演练 SQL、备份点、校验查询和停止条件 |
| 数据恢复 | 丢失或损坏的数据回到某个恢复点 | 恢复点之后的合法写入和跨系统副作用 | RPO/RTO、跨服务一致性、写入冻结和重放方案 |

制品回退通常是最快的运行动作，但不是默认的唯一动作。若新版本执行了不可逆迁移，旧制品可能无法启动；若已经发送新消息，切回旧消费者可能无法理解；若外部支付或通知已经发生，Git 的 `revert` 不会撤销它们。回退方案应在发布前用兼容矩阵和演练结果标注“可回退”“需向前修复”或“需数据恢复”。

推荐决策顺序是：先停止扩大影响并固定证据，再确认当前实例、配置、schema、消息和外部副作用，选择最小且可验证的动作，最后核对恢复后的运行版本和业务结果。不要先改 tag、重写分支或删除实例来制造“看起来已经回到旧版本”的界面状态。

## 数据库迁移和异步任务的边界

数据库迁移应按 expand/contract 或等价阶段设计：先增加可选结构和兼容读写，再切换应用，观察一段时间，最后清理旧结构。每个阶段都要声明旧制品、新制品和回退动作。不可逆步骤必须在部署审批前显式标记，并准备向前修复、校验和停止条件。

长任务和异步消息会延长 rollout 的混合版本窗口。任务应携带启动时的 `artifact_digest` 或协议版本，消费者在不兼容时拒绝或转移，而不是静默按新代码重试。回退时要处理：

- 正在运行的任务是否允许完成，还是需要可恢复地取消；
- 重试消息是否会被旧消费者重复处理；
- 新版本写入的数据是否已满足旧版本的读取约束；
- 任务结果和外部副作用是否有幂等键、去重记录和补偿流程。

Git 提交可以保存迁移脚本、任务协议和回退手册，但不能证明数据库实际执行到了哪一步。运行记录必须额外保存 schema 版本、迁移批次、任务积压和重放结果。

## 失败分流与恢复

| 症状 | 先固定 | 安全动作 | 不要做的事 |
| --- | --- | --- | --- |
| 请求已接受但没有实例变化 | deployment ID、调度事件、权限和配额 | 保持状态为 `admitted` 或 `inconclusive`，排查调度 | 重复点击制造多个 rollout |
| 控制面显示完成，实例仍是旧 digest | 任务定义、实例 build identity、流量和批次 | 暂停并修复观测或 rollout，必要时围栏旧批次 | 改 Git 分支或 tag |
| 金丝雀错误率超过门槛 | 版本维度指标、样本量、请求类型和时间窗 | 停止扩大流量，保存样本，按预案回退 | 只看全局平均值继续发布 |
| 新旧实例都健康但消息持续失败 | 消息 schema、消费者版本、重试和积压 | 暂停消费者或转移队列，执行兼容修复 | 直接删除失败消息 |
| 旧制品无法启动 | schema、配置、依赖和启动日志 | 恢复兼容配置或执行已演练的向前修复 | 未经验证地强行降级 |
| 回退后仍有新版本流量 | 路由缓存、入口切换、实例代数和长连接 | 设置旧批次围栏，重新读取实际流量版本 | 只重启一台实例 |
| 运行版本正确但业务数据异常 | 数据库迁移、写入时间线、外部副作用 | 停止写入并按数据恢复/补偿方案处理 | 用 `revert` 代替数据修复 |

恢复记录要保留失败 rollout，不要覆盖为“已完成”。每次重试都生成新的 attempt，引用原始 deployment ID 和新的状态原因。若观测缺失，状态应为 `inconclusive`，直到补齐实例和流量证据；不确定不是成功的另一种写法。

## 隔离实验与真实边界

在仓库根目录运行：

```bash
bash scripts/verify-deploy-rollback.sh
```

前置条件是 Bash、Git 2.28 或更高版本，以及 `sha256sum` 或 `shasum`。实验使用 `mktemp`、虚构身份、临时 Git 仓库和普通目录模拟实例，不读取用户级 Git 配置、不连接网络，也不修改本书仓库。

实验验证：

1. 从两个源码提交生成两个固定摘要的制品，并把目标 digest 写入部署记录；
2. 把新制品放入 canary 实例，故意写入失败健康状态，确认 rollout 停在 `paused` 而不会扩大到全部实例；
3. 从已知良好制品恢复实例，核对实际文件摘要、状态历史和回退原因；
4. 验证配置版本可以独立回退，源码分支继续前进不会改变已部署 digest；
5. 为一个携带旧 digest 的长任务设置围栏，确认回退后它被标记为需要重放或人工处理，而不是静默运行。

成功输出为：

```text
Deployment state machine, canary stop, rollback verification, and stale-task fencing passed.
```

本实验只证明本地文件摘要、状态转移和 Git 引用之间的逻辑不变量。它不证明真实实例探针、流量切分、容器编排、蓝绿入口、数据库事务、消息队列、权限、审计、通知或 RPO/RTO；这些必须在目标平台和专用测试环境中演练。

## 综合练习：决定一次发布是否继续

某次金丝雀部署的控制面显示新制品已完成 10% 流量切换，实例启动探针全部通过，但版本维度的支付失败率升高，队列中还有由新版本产生的消息，数据库已经执行了第一步 expand 迁移。请写出处理方案，至少回答：

1. 先固定哪些 deployment、实例、流量、消息和数据库证据；
2. 哪个状态转换应立即发生，哪些动作必须暂停；
3. 制品回退、配置回退、向前修复和消息处理的顺序；
4. 如何证明回退后没有旧实例继续接收新流量，长任务和重试消息如何处理；
5. 哪些结论不能由 Git 仓库和本地实验单独证明。

合理方案会先暂停扩大流量，保留新旧版本和指标，确认 expand 迁移是否保持旧制品兼容，再决定回退制品、配置或执行向前修复。它不会因为进程探针通过就宣布发布成功，也不会删除消息或修改发布 tag 来掩盖现场。

## 小结

部署请求、rollout、实例实际 digest 和流量结果是四类不同事实。滚动、金丝雀、蓝绿和手动暂停只是替换顺序不同，都需要不可变制品、版本维度观察、健康门槛、容量余量和明确停止条件。

回退也不是一个 Git 命令。制品回退、配置回退、源码 `revert`、数据库向前修复和数据恢复作用在不同状态上，必须按当前 schema、消息、长任务和外部副作用选择。先固定证据，再执行最小动作，最后从运行实例和业务指标验证恢复，才能把“页面变绿”变成可审计的恢复结论。

下一章将把数据库迁移的阶段、兼容矩阵和不可逆步骤单独展开，并与发布审批和恢复演练连接起来。
