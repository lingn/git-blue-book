# Monorepo 拓扑治理：用构建图和所有权决定边界

Monorepo 不是“把所有代码放进一个目录”这么简单，多仓库也不是天然的独立性。真正的拓扑决策同时改变变更原子性、构建图、权限边界、发布契约、历史规模、路径过滤和故障恢复。只按仓库大小或团队习惯选型，通常会把成本转移到 CI、依赖升级、权限审批和事故排查。

本章承接[稀疏与部分工作流](04-sparse-partial-workflows.md)、[Submodule 与 subtree](03-submodule-and-subtree.md)和第六篇的评审/所有权模型。前两章解释如何取得内容，本章回答组织应该把内容放在哪个边界，以及怎样证明一次变更覆盖了所有受影响组件。它不指定某家构建系统、包管理器或托管平台；具体路径过滤、CODEOWNERS、缓存和计费能力必须按目标产品版本单独核对。

本章以 Git 2.49.0、Bash 和本地文本构建图 fixture 为验证基线，核对日期为 2026-08-23。实验只验证提交路径、依赖闭包、所有权规则和候选状态，不运行真实编译器、构建系统、评审平台或权限目录。

## 进入条件和退出能力

进入本章前，读者应理解 commit/tree、pathspec、稀疏检出、制品摘要、submodule gitlink、subtree 普通 tree、代码评审和 CI 候选。读完后，应能：

- 用变更原子性、依赖图、所有权、发布节奏和恢复目标比较 monorepo、多仓库包、submodule 与 subtree；
- 从构建图生成或核对受影响组件集合，而不是只按 changed paths 触发检查；
- 设计路径所有权、共享库变更和跨团队审批的最小权限边界；
- 判断一次提交是否包含了需要原子更新的服务、schema、生成器和配置；
- 在仓库拆分或合并时保存 OID、版本契约、所有权和发布连续性证据；
- 说明本地构建图实验不能证明真实构建、权限、评审和组织协作事实。

## 拓扑选择先回答五个问题

| 问题 | 观察指标 | 更偏向的边界 |
| --- | --- | --- |
| 哪些变化必须原子提交？ | 共享 API、schema、生成器和消费者是否同步修改 | 同仓库或同一版本化发布单元 |
| 谁应该独立批准和访问？ | 数据敏感性、客户隔离、职责分离、外部协作者 | 多仓库或明确的权限分区 |
| 构建和测试的依赖闭包多大？ | 受影响组件数量、图深度、缓存命中和 CI 时延 | 构建图明确的 monorepo，或稳定包契约 |
| 发布节奏是否一致？ | 版本、回退、兼容窗口和支持周期 | 同步发布单元或独立制品仓库 |
| 事故和恢复如何执行？ | 证据采集、备份、权限回收、RPO/RTO | 责任边界清晰、可独立恢复的仓库/服务 |

四种常见模型的比较如下：

| 模型 | 变更原子性 | 依赖身份 | 权限与恢复 | 主要风险 |
| --- | --- | --- | --- | --- |
| Monorepo | 高，多个组件可在一个 commit 中更新 | 同一 commit/tree 加构建图 | 统一治理，规模和权限分区更复杂 | CI 影响面过大、所有权模糊、历史/工作区膨胀 |
| 多仓库 + 包/制品 | 低于源码原子性，由版本契约协调 | 包版本或制品 digest | 每个仓库可独立治理和恢复 | 兼容矩阵、发布滞后、依赖漂移 |
| Submodule | 父仓库固定外部 commit，但更新跨仓 | gitlink OID | 权限和备份必须递归 | 未发布 gitlink、递归认证、非原子 push |
| Subtree | 当前候选含依赖普通 tree | 当前仓库 commit/tree | 当前 clone 自包含，来源关系需另存 | 同步冲突、对象增长、split 历史复杂 |

没有一种模型同时最大化原子性、独立权限、独立发布和最小运维。决策记录要写明放弃了什么，以及由哪个版本契约、审批门禁或恢复演练补偿。

## 构建图是路径过滤的上游事实

只看一个提交改了哪些路径，无法知道哪些组件需要检查。构建图至少包含：

```text
component_id / source_roots
direct_dependencies / generated_inputs
test_targets / artifact_targets
runtime_protocols / schema_dependencies
owners / approvers / release_unit
```

图的边应有来源和版本。静态声明、构建文件解析、运行时依赖、人工例外和生成器输入可能得到不同图，发布门禁要记录采用哪一个，以及未知边如何处理。图缺失或解析失败时默认扩大检查集，不能把“没有找到依赖”当成“没有依赖”。

### 变更闭包不是 changed paths

假设一次提交修改 `libs/task-sdk`。直接路径只有一个目录，但依赖图可能包含 manager、worker、CLI、迁移任务和测试夹具。受影响集合应是：

```text
directly changed components
  + reverse dependency closure
  + generated artifacts and schema consumers
  + release-unit companions
  + policy and build-definition owners
```

反向闭包要有终止和循环处理，组件重命名、条件依赖、平台矩阵和可选插件不能靠一条 glob 规则解决。路径过滤只适合在依赖图完整、规则经过回归、未知边采用保守策略时减少检查。否则“检查被跳过”本身就是供应链和发布风险。

### 生成文件和配置是图中的节点

生成器、schema、接口描述、版本文件、容器定义和 CI 配置经常位于独立目录，却影响很多组件。它们要进入图的输入节点，并在变更时触发所有消费者。将生成文件提交到 Git 也不能省略生成器版本和输入校验；提交的只是一个结果快照。

## Monorepo 的所有权不是一张目录通讯录

所有权至少分三层：

1. **路径责任**：谁维护源代码、测试、生成器和文档；
2. **变更批准**：哪些团队必须审查特定路径、依赖边或敏感配置；
3. **运行责任**：谁负责制品、部署、告警、数据和回退。

一个团队可以拥有路径却没有生产发布权限，也可以负责运行而不拥有共享库源码。所有权记录要有稳定主体 ID、有效期、替代者和审计来源，不能只写一个人名或聊天群。

共享目录需要更严格的规则：代码所有者、消费者代表、架构/安全审批和运行负责人可能同时参与。审批系统如果只按 changed paths 计算 reviewer，必须额外消费构建图和敏感边界；无法解析时暂停合并或升级到保守审批集。

权限分区也要和 Git 数据面分开验证。Monorepo 中隐藏目录、稀疏检出和本地 ignore 不是访问控制；拥有仓库读取权限的人可能通过对象、历史、归档或构建日志取得未展开内容。真正需要隔离的秘密或客户数据不应只靠目录规则隐藏，应使用独立存储或仓库边界。

## CI 和缓存要按组件与候选绑定

Monorepo 的 CI 优化通常包含路径过滤、依赖图、远程缓存和并行批次。每一层都必须记录来源：

| 机制 | 必须绑定 | 常见误判 |
| --- | --- | --- |
| 受影响组件选择 | candidate、构建图 digest、规则版本 | 只看路径导致漏测共享依赖 |
| 组件缓存 | candidate/tree、工具链、依赖锁、输入闭包 | 只按组件名命中旧输出 |
| 并行批次 | 组件集合、图代数、合并队列候选 | 目标分支变化后旧结果仍可用 |
| 增量构建 | 输入摘要、生成器、外部依赖和缓存来源 | 缓存命中被当作来源证明 |
| 发布制品 | release unit、artifact digest、配置/schema 窗口 | 每个服务各自构建造成版本漂移 |

缓存命中不能绕过所有者审批、候选过期和来源验证。图或规则变化时，缓存键必须失效，或者证明旧结果仍覆盖新输入。合并队列把多个候选组合成临时 tree 时，影响集合和缓存命中都要绑定组合后的候选，而不是单个功能分支。

## 原子变更与独立发布的边界

共享 API、消息协议和 schema 有三种典型策略：

| 策略 | 做法 | 适用边界 | 失败时如何恢复 |
| --- | --- | --- | --- |
| 同仓原子变更 | 在一个 commit/候选中更新生产者、消费者和迁移 | 变更耦合高、团队可共同治理 | revert 或整组制品回退，数据仍需单独处理 |
| 兼容窗口 | 先发布能读旧/新格式的版本，再切换和清理 | 需要独立发布或滚动部署 | 配置/制品回退，必要时向前修复 |
| 版本契约 | 独立仓库发布不可变包/API，消费者锁版本 | 权限、节奏和恢复必须独立 | 依赖版本回退，保留兼容矩阵 |

“能在一个 monorepo commit 中修改”不等于“必须同时部署”。构建图和运行协议应把源码原子性与运行发布单元分开描述。反过来，多个仓库的同名版本也不提供原子性；发布记录要保存每个仓库的候选、制品和兼容窗口。

## 拆分、合并和迁移要保持可追溯

### Monorepo 拆成多个仓库

先生成路径、提交和所有权映射，确定哪些历史、tag、notes、LFS、评审和 CI 证据需要保留。拆分后每个仓库的初始 commit OID 通常会重写，不能只写“从某目录复制”。需要保存：

- 源提交/tree 与目标提交/tree 的映射；
- 原路径到新仓库路径、owner、构建目标和制品的映射；
- 跨仓库依赖版本、发布顺序和最终切换时间；
- 源仓库写入冻结、客户端切换和回退窗口；
- 旧历史查询、签名、审计和备份的保留方式。

### 多仓库合并为 Monorepo

合并要防止路径冲突、作者/签名归属、敏感历史和对象体积失控。即使使用 subtree 或历史重写，源仓库的 issue、评审、权限和发布记录也不会自动成为一个 Git tree。合并后应重新建立所有权、构建图、CODEOWNERS、缓存、CI、制品和恢复策略，不要以“提交都在”作为迁移完成条件。

### OID 变化不是事实丢失的唯一指标

历史重写后，新的 commit OID 不等于旧历史不存在。迁移记录应保存旧/new OID map、路径和作者映射，并说明哪些外部事件仍以旧 OID 为键。任何自动链接或审计查询都要支持双向查找或明确停止条件。

## 组织级指标和治理门禁

Monorepo 治理至少持续观察：

- 组件数量、依赖图节点/边、循环和未解析边；
- changed paths 与实际受影响组件的漏测/误触发比例；
- 构建 p50/p95、缓存命中和重跑率；
- 共享目录变更的审批等待、冲突率和回退次数；
- 所有权缺失、过期 owner、孤儿组件和紧急例外；
- 仓库对象、tracked paths、refs、LFS/制品、备份和恢复时间；
- 拆分/合并后的 OID 映射查询成功率和客户端切换失败。

指标必须绑定候选、组件和时间窗，不要用全仓库平均值掩盖一个高风险服务。策略每次变更都要有 audit/canary 阶段、回退版本和例外到期时间。

## 故障分流与恢复

| 症状 | 先固定 | 安全动作 | 不要做的事 |
| --- | --- | --- | --- |
| 共享库变更只触发一个服务 | candidate、构建图版本、反向依赖闭包、路径规则 | 阻止发布，扩大检查并修复图 | 直接把路径 glob 加长当永久修复 |
| 所有者审批缺失或过期 | owner snapshot、路径/依赖边、主体有效期 | 状态为 `inconclusive`，重新审批 | 让任意 reviewer 代替所有权 |
| 增量缓存命中但输出不一致 | cache key、输入摘要、生成器和候选 | 隔离缓存，干净构建并比较摘要 | 删除清单或覆盖可信制品 |
| Monorepo 拆分后依赖版本漂移 | OID map、包/制品清单、切换时间线 | 冻结一端写入，按最终同步重建 | 直接把两个分支 merge 在一起 |
| 稀疏工作区漏掉共享配置 | sparse 规则、构建图、输入清单 | 扩大范围或使用完整 runner | 把范围外本地文件复制进构建 |
| 一个团队需要独立访问敏感目录 | 真实访问主体、审计、外部副本和权限边界 | 改用仓库/存储隔离，重新设计发布契约 | 把 sparse/ignore 当保密机制 |

恢复后重新计算受影响闭包、所有权和制品摘要。变更图或 owner 证据不完整时，保留原候选并生成新的 attempt，不要覆盖旧检查结果。

## 隔离实验与真实边界

在仓库根目录运行：

```bash
bash scripts/verify-monorepo-topology.sh
```

前置条件是 Bash、Git 2.49 或兼容实现、`awk`、`grep`、`git diff-tree` 和可写临时目录。实验使用一个临时 Git 仓库、文本构建图、所有权快照和虚构组件，不连接真实构建系统、评审平台、权限目录或制品库。

实验验证：

1. 共享库路径变化会沿反向依赖闭包触发 manager 和 worker，而文档变化只触发文档组件；
2. 构建图缺边时状态为 `inconclusive`，不会把未发现消费者当作无消费者；
3. 同一候选可以原子包含共享库和两个消费者的变化，提交路径、候选 tree 和制品来源保持一致；
4. owner 快照缺失或过期时合并门禁拒绝，不能用 sparse/ignore 伪造权限隔离；
5. 主线前进不会改变已经记录的候选闭包、制品摘要和部署组件集合。

成功输出为：

```text
Monorepo dependency closure, ownership gates, atomic-change evidence, and topology decision boundaries passed.
```

实验只证明本地构建图和 Git 路径状态机。它不执行真实编译器、构建缓存、CODEOWNERS/评审平台、身份目录、制品库、运行服务或迁移切换；生产结论必须在目标组织和工具链中重新采集。

## 小结

Monorepo 的价值来自变更、依赖和治理能够在一个可审查候选中被看见，不来自目录数量。多仓库、submodule 和 subtree 各自把原子性、权限、发布和恢复成本放在不同位置。

先建立构建图和所有权，再决定路径过滤和 CI 范围；共享输入变化按反向闭包扩大检查，图或 owner 不完整时保守拒绝。拆分、合并和版本契约都要保存 OID/路径映射、发布顺序和回退路线，才能让仓库拓扑变化成为可追溯的工程决策。
