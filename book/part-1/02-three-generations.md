# 从本地版本、集中式到分布式

版本控制工具并不是一开始就长成 Git 的样子。理解几种方案的差异，可以帮助我们看清 Git 为什么要把完整历史放在每位开发者手中。

## 第一种方案：历史只在自己的电脑上

最简单的版本控制系统在本机保存文件的多个版本。相比手工复制，它能自动编号、比较变化，也能恢复旧内容。

它解决了个人历史混乱的问题，却没有真正解决协作。另一位开发者需要拿到你的文件和历史，双方也缺少共同的权威位置。

## 第二种方案：大家连接同一台中央服务器

集中式版本控制把项目历史放在中央服务器上。开发者从服务器取出文件，完成修改后再把结果交回服务器。

可以把它想象成一间公共档案室：

```text
开发者 A  ─┐
开发者 B  ─┼─> 中央版本库
开发者 C  ─┘
```

这种方案让团队第一次拥有共同历史和统一权限管理。它也带来明显边界：很多历史操作依赖服务器；网络或服务器不可用时，开发者能够完成的工作会受到限制；中央仓库还是关键故障点。

## 第三种方案：每个人都拥有完整仓库

分布式版本控制不只把当前文件交给开发者，还把完整的项目历史复制到本地。每个人的电脑上都有一个能够独立工作的仓库：

```text
本地仓库 A  <──> 共享仓库 <──> 本地仓库 B
```

共享仓库仍然很有价值，它为团队提供稳定的交换位置。但它不再是唯一保存历史、也不是完成每一步操作的必要条件。

本书把**分布式版本控制**定义为：每个参与者都可以持有完整仓库，在本地查看和创建历史，再与其他仓库交换已有记录。

## “分布式”不等于“没有中心”

团队通常仍会约定一个主要共享仓库，用于代码评审、持续集成和发布。Git 所说的分布式，是技术上没有某一份仓库天然高人一等；团队选择哪个仓库作为中心，是协作规则，而不是工具强制。

这个区别以后非常重要：你在本地创建的历史不会自动出现在共享仓库；从共享仓库取得的新历史也不会自动改写你正在做的工作。交换和整合是两个可以分开的动作。

## 三种方案解决问题的范围

| 方案 | 个人历史 | 多人共享 | 离线查看完整历史 | 每人拥有完整仓库 |
| --- | --- | --- | --- | --- |
| 手工副本或本地版本 | 有限 | 困难 | 可以 | 不适用 |
| 集中式版本控制 | 支持 | 支持 | 通常受限 | 否 |
| 分布式版本控制 | 支持 | 支持 | 支持 | 是 |

## 小结

Git 属于分布式版本控制系统。它不是取消共享仓库，而是让“记录本地历史”和“把历史分享给团队”成为两件独立的事情。下一章会看到，Git 为什么在 2005 年被创造出来，以及当时的约束如何塑造了它。
