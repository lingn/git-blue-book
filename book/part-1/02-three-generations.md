# 从本地版本、集中式到分布式：仓库权威在哪里

版本控制方案的差异，不只是命令名称不同。真正要比较的是：历史保存在哪里，谁有权更新，离线时能做什么，多个工作线怎样合并，服务器或网络故障后能否继续工作。

## 进入条件与完成标准

本章不要求预先知道 Git 命令。读完后，应能用历史位置、协作边界、故障模式和治理成本比较三类方案，并解释为什么 Git 可以有共享仓库却不依赖共享仓库完成每一个本地动作。

## 第一类：本机副本或本地版本

最简单的方案在一台电脑上保存多个文件版本，可能由手工复制、编辑器历史或一个本地工具管理：

~~~text
工作区 -> 本地版本 1
       -> 本地版本 2
       -> 本地版本 3
~~~

它可以解决个人误删和误改，比较集中在单台设备上。缺点也很明确：

- 版本之间的目的和父关系常靠文件名或时间猜测；
- 多文件变化难以作为一个整体审查；
- 多人同时修改没有共享的合并模型；
- 历史通常没有稳定的作者、权限和审计边界；
- 设备损坏时本地历史可能一起丢失。

这种方案适合短期个人材料，不适合需要可追溯协作的软件仓库。

## 第二类：集中式版本控制

集中式系统把主要历史和权限放在中央服务器：

~~~text
开发者 A ─┐
开发者 B ─┼─> 中央版本库
开发者 C ─┘
~~~

它带来一个清晰的共享权威。服务器可以统一：

- 保存主历史；
- 管理用户和权限；
- 检查提交和锁；
- 提供团队的审计与备份入口。

代价是本地工作依赖服务器的程度更高。不同产品的离线能力不同，但完整历史、提交和分支操作通常不能像 Git 那样在每位开发者本地独立完成。网络、权限或中央服务不可用时，能够记录和协作的范围会缩小。

集中式并不等于不支持分支或合并，它只是把更多状态和操作放在一个共享服务上。是否适合某个组织，要看网络可靠性、权限集中要求、历史规模和团队工作方式。

## 第三类：分布式版本控制

分布式版本控制让每个参与者拥有一个完整或可工作的仓库副本：

~~~text
本地仓库 A <──> 共享仓库 <──> 本地仓库 B
     │                         │
     └── 可以离线创建历史       └── 可以离线查看历史
~~~

在 Git 中，本地仓库通常包含对象、引用、提交图、index 和工作区。查看历史、创建提交、建立分支、比较快照等动作不要求先访问服务器。服务器的主要作用变成交换对象和引用，并承载评审、CI、发布和治理控制面。

“完整”要看克隆方式。浅克隆、部分克隆、稀疏检出和 LFS 会限制本地历史、对象或工作区，不能把受限副本写成完整仓库。第九篇和第十三篇会分别处理这些边界。

## 分布式不等于没有中心

团队仍然可以约定一个共享仓库作为主线入口：

~~~text
本地记录历史 -> 评审和检查 -> 共享仓库 -> 发布
~~~

这个仓库是组织规则选择的权威，并非 Git 协议规定它天然高于其他仓库。镜像、备份、个人派生仓库和灾备副本可以各有用途，但必须明确：

- 哪个引用是写入权威；
- 哪些仓库只读或只用于恢复；
- 谁可以向哪些引用推送；
- 评审、CI、制品和部署绑定哪一个候选；
- 主库不可用时如何提升、围栏和回切。

把共享平台称为 origin 只是本地命名约定，不能从名字推导权限和权威。

## 五个比较维度

| 维度 | 本地副本 | 集中式 | 分布式 |
| --- | --- | --- | --- |
| 历史主要位置 | 单台设备 | 中央服务器 | 多个本地和共享仓库 |
| 离线查看历史 | 通常可以 | 取决于本地缓存 | 通常可以，受克隆范围影响 |
| 离线创建提交 | 可以但协作弱 | 常受服务器约束 | 核心能力 |
| 共享权威 | 文件名或个人约定 | 服务器 | 团队约定的一个或多个仓库 |
| 合并和审查 | 手工 | 服务器或客户端 | 本地 Git 加平台控制面 |
| 设备故障恢复 | 依赖外部备份 | 依赖服务器备份 | 依赖多副本和备份治理 |
| 权限和审计 | 很弱 | 集中管理 | 传输、平台和仓库分层管理 |

表格只给出机制差异。实际选择还要考虑仓库规模、网络、合规、迁移成本和运维能力。

## Git 的两个独立动作

Git 把“本地记录”和“共享历史”分成两步：

1. 在本地对象库中创建提交和引用；
2. 通过 fetch、push 等动作与另一个仓库交换对象和 refs。

因此网络暂时不可用时，开发者仍可提交和查看本地历史；网络恢复后再协商如何合并和发布。这种独立性也意味着本地提交不会自动出现在共享仓库，远端更新也不会自动覆盖本地工作。

远程跟踪分支是本地对远端的观察点，不是服务器本身。后面的远程篇会把这个区别具体化。

## 分布式带来的新责任

每个开发者拥有更多历史，意味着每个副本都可能包含：

- 尚未公开的代码和提交；
- reflog、不可达对象和临时 stash；
- 本地配置、hooks、filters 和凭据来源；
- 远程跟踪引用和旧版本缓存；
- 构建脚本、依赖和生成物。

分布式提高了离线能力和恢复机会，也扩大了秘密泄漏、旧副本重新污染和权限治理的范围。组织需要备份、访问回收、历史清理、签名和审计规则来管理这些副本。

## 什么时候哪种方案更合适

如果只是一个人短期保存一份文档，本地版本或带历史的文件服务可能已经足够。如果多人长期维护软件，需要把多文件变化作为可评审单元，需要分支和精确恢复，版本控制系统更合适。

选择 Git 的理由通常包括：

- 需要离线提交和完整本地历史；
- 需要频繁创建轻量分支；
- 需要在多个仓库之间交换对象；
- 需要通过提交图保留合并和恢复关系；
- 愿意承担多副本、权限、凭据和治理成本。

关键不是“分布式永远更好”，而是把工作约束与方案能力逐项对齐。

## 小结

本地副本解决个人保存，集中式方案提供单一共享权威，分布式方案把历史能力分布到多个仓库。Git 仍可使用中心化托管，但本地记录、远端交换、评审和发布是不同层。理解仓库权威、离线能力和副本责任，才能准确解释 Git 后面的命令行为。
