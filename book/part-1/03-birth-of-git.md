# Git 的诞生：在大规模协作中同时追求速度和可验证性

Git 不是因为命令行更酷才出现。它是在 2005 年 Linux 内核社区失去原有协作工具后，为一组很具体的约束快速设计出来的。理解这些约束，有助于解释 Git 为什么重视内容寻址、本地操作、提交图和廉价分支。

## 进入条件与完成标准

本章只讨论公开历史背景和设计约束，不把后来的托管平台功能倒推成 Git 诞生时就存在的能力。读完后，你应能把 Git 的关键机制和当时的问题对应起来，也能指出这些机制的边界。

## 2005 年的协作压力

Linux 内核是一个规模大、贡献者多、提交频繁的开源项目。此前社区使用 BitKeeper 进行分布式协作，免费使用安排结束后，项目需要迅速找到新的历史管理方案。

当时的要求不是“能保存几个文件”：

- 读取和比较大量历史不能慢到阻塞日常开发；
- 分支和合并要足够便宜，普通贡献者也能建立独立工作线；
- 开发者要能在本地查看和创建历史，不把每次操作都押在中央服务器上；
- 传递提交和补丁时要能检测内容是否被意外损坏；
- 多个仓库之间要能交换部分或全部历史；
- 工具本身要能被大型开源项目持续维护。

这些约束共同推动了 Git 的早期设计。Linus Torvalds 在 2005 年启动了 Git，之后 Junio C Hamano 长期负责主要维护。历史细节可以通过 Git 项目和 Linux 内核社区资料核对，本书关注它们对工程模型的影响。

## 内容寻址：把完整内容变成坐标

Git 使用对象类型、内容长度和内容计算对象 ID。相同对象内容可以复用，内容任何变化都会得到不同 ID。这个设计带来三项能力：

1. 对象可以在不同仓库之间按 ID 传输和去重；
2. 对象内容与 ID 不一致时能够被完整性检查发现；
3. commit、tree 和 blob 可以组合成清晰的快照关系。

哈希校验主要回答“对象内容是否与标识一致”，不能回答“作者是否诚实”“谁获准合并”或“代码是否安全”。签名、认证、授权和供应链证明属于其他控制层。

## 本地优先：网络用于交换，而不是每次记录

Git 把创建对象、写提交、查看历史和建立分支放在本地。远程操作负责交换对象与引用：

~~~text
本地创建 commit
       |
       v
本地审查和测试
       |
       v
fetch/push 与其他仓库交换
~~~

这解释了 Git 的离线能力，也带来新责任：本地仓库可能持有未公开代码、临时对象、stash、reflog、凭据来源和旧远程状态。分布式不是免治理，反而要求组织管理副本、访问、备份和泄漏响应。

## 历史是一张有向图

commit 记录父提交，多个提交连接成图。分支只是指向图中某个节点的可移动引用，合并提交可以有多个父节点。Git 不依赖版本号或目录副本判断历史关系，而是沿父链接计算祖先、共同祖先和可达性。

因此可以：

- 快速判断一个分支是否包含另一个提交；
- 在不同工作线上并行开发；
- 用 merge 保留集成节点；
- 用 rebase 生成以新父提交为起点的对象；
- 用 reflog 和其他 refs 寻找误移动的历史入口。

图模型也解释了为什么提交不可原地编辑，以及为什么改写共享历史会改变所有人的坐标。

## 便宜分支：让隔离成为日常操作

Git 分支主要是一个 ref，不是项目目录的完整副本。创建分支通常只需要写入一个指向当前提交的名字，真正的文件和对象可以继续共享。

这降低了试验和并行开发的成本，但分支便宜不等于合并没有代价。合并仍然要处理：

- 共同祖先和两侧变化；
- 内容、路径、模式和二进制冲突；
- 测试、构建、数据库和配置兼容；
- 评审、CI、制品和部署候选；
- 共享历史和回滚责任。

Git 只提供数据面基础，团队还需要约定分支命名、保护、评审和发布流程。

## 补丁和仓库交换

Git 的对象和提交关系支持多种交换方式：

- 在两个仓库之间传输可达对象；
- 通过 fetch 更新本地远程跟踪 refs；
- 通过 push 请求远端引用更新；
- 以补丁或提交 ID 迁移少量变化；
- 在本地使用 bundle、mirror 或备份恢复历史。

交换动作不等于整合动作。fetch 只改变本地对远端的认知，merge/rebase 才改变当前工作历史；push 先传对象，再请求服务器更新 ref。后面的章节会分别解释协议、认证和引用规则。

## 为什么命令有历史包袱

Git 使用多年后，命令同时承载了低层对象操作和高层工作流。早期命令可能一条命令做多个职责，例如 checkout 既能切换分支，也能恢复路径。现代 Git 增加 switch 和 restore，让意图更明确；旧命令仍存在是为了兼容已有脚本和习惯。

命令历史并不影响核心模型。每次操作仍可以问四件事：

~~~text
是否写入新对象
是否移动引用
是否修改 index
是否覆盖工作区
~~~

只要把这四件事说清，旧命令和新命令都可以被准确审查。

## Git 机制的边界

Git 的设计解决了历史记录和仓库交换，但不自动解决：

- 平台账号、SSO、令牌和组织权限；
- 评审审批、必需检查和合并队列；
- 构建输入、制品摘要和部署实例；
- 数据库迁移、异步消息和外部副作用；
- LFS、子模块服务和制品库配额；
- 备份、区域故障和组织级恢复。

这些系统可以围绕 Git OID 建立证据链，但不能由一个 commit 或标签单独证明。

## 设计约束如何映射到今天

| 早期约束 | Git 机制 | 当前工程边界 |
| --- | --- | --- |
| 大历史要快 | 对象复用、pack、图索引 | 需要测量、维护和容量预算 |
| 低成本分支 | ref 指向提交 | 合并和评审仍有业务成本 |
| 本地可工作 | 本地对象和 refs | 多副本需要权限和备份治理 |
| 内容可校验 | 内容寻址和 fsck | 完整性不等于来源可信 |
| 仓库可交换 | Git 协议和 ref 更新 | 认证、授权和平台规则另算 |
| 多人并行 | DAG、merge、rebase | 共享历史改写需协调 |

## 小结

Git 的起点是一组大规模协作约束：速度、廉价分支、本地优先、内容完整性和仓库交换。内容寻址、提交图和引用正是这些约束的工程答案，同时也明确了 Git 的边界。理解设计原因后，后面看到快照、对象、分支和远程命令，就能从状态变化推导行为，而不必依赖命令口诀。
