# Git 的诞生：为大规模协作重新设计

## 2005 年的问题

Linux 内核是一个规模巨大、参与者众多、变化频繁的开源项目。它曾使用商业分布式版本控制工具 BitKeeper 协作。2005 年，免费使用安排结束，Linux 内核社区需要迅速寻找新的版本管理方案。

当时已有其他版本控制工具，但 Linux 内核协作提出了非常苛刻的要求：

- 处理大量文件和提交时必须足够快；
- 分支和合并必须便宜，不能成为少数人才敢做的高成本操作；
- 每个人都应拥有完整历史，不依赖中央服务器完成日常记录；
- 内容损坏或历史被篡改时，应当能够被发现；
- 工作方式要支持通过补丁和不同仓库交换变化。

Linus Torvalds 因此开始设计 Git。Git 很快能够管理自身源码，之后由 Junio C Hamano 长期担任主要维护者。这个起点解释了 Git 的很多性格：它首先是为高强度软件协作设计的历史管理系统，而不是为了把命令做得像文件管理器一样直观。

## Git 名字背后的设计重点

Git 的早期设计可以概括成几个决定。

### 内容优先

Git 根据内容计算标识。相同内容能够得到稳定的识别结果，内容一旦改变，标识也会改变。后面讲底层对象时，我们会具体解释这套机制。

### 本地优先

查看历史、创建提交、建立分支等核心动作都可以在本地完成。网络主要用于仓库之间交换已有历史。

### 历史是一张图

一次记录知道自己从哪些旧记录发展而来。大量记录连接起来形成历史。分支和合并都建立在这张关系图上，而不是建立在目录复制上。

### 分支应该便宜

Git 的分支主要是一个会移动的名字，不需要复制一套完整文件。因为创建和切换成本很低，开发者可以为一个功能、修复或实验建立独立工作线。

## 为什么 Git 看起来不够直观

Git 的命令接口在多年发展中承担了很多不同场景。一些老命令同时负责多种事情，例如 `checkout` 既能切换分支，也能恢复文件。现代 Git 增加了职责更单一的命令，本书会优先介绍它们。

更重要的是，Git 操作的不是简单的“文件版本号”，而是内容、提交和指向提交的名字。只背命令时，这套模型像额外负担；理解模型以后，许多异常情况反而能够推导出来。

## 小结

Git 的诞生不是为了增加一套命令，而是为了在速度、完整性、离线工作和大规模合并之间取得新的平衡。下一章进入它最关键的选择：把项目内容保存成快照。
