# Git 保存的是快照

## 两种理解变化的方法

假设一个文件最初有三行，后来第二行被修改。记录变化有两种直觉。

第一种是保存“把第二行从旧内容改成新内容”这条差异。只要从起点依次应用所有差异，就能还原最终内容。

第二种是每到一个重要节点，就记录当时整个项目是什么样子。Git 的工作模型更接近第二种：每次提交都指向一份完整的项目快照。

## 快照不是每次都复制全部文件

“完整快照”描述的是逻辑视图，不代表 Git 每次都会笨重地复制所有文件。没有变化的内容可以被重复引用；发生变化的内容会形成新的记录。Git 在存储和传输阶段还会进一步压缩。

因此可以同时成立：

- 从一次提交出发，Git 能看到当时完整的项目树；
- 相同文件内容不需要在每次提交中重复保存。

本书把**快照**定义为：项目在某个历史节点上的完整内容视图，包括被记录的目录、文件内容和必要的文件属性。

## 一个三次提交的例子

项目只有 `README.md` 和 `app.txt` 两个文件：

```text
提交 A：README v1，app v1
提交 B：README v1，app v2
提交 C：README v2，app v2
```

从读者视角看，B 是一份完整快照。对 Git 来说，B 可以继续引用 A 中未变化的 `README v1`，只为 `app v2` 保存新内容。C 则复用 `app v2`。

这也解释了为什么同一份内容无论出现在哪个目录或提交中，都可以被 Git 识别并复用。

## Git 是否保存空目录

Git 跟踪的是文件内容和由这些文件构成的目录结构，不单独保存空目录。如果项目运行时需要一个空目录，常见做法是在里面放置一个有意义的占位文件，例如说明该目录用途的 `README.md`。所谓 `.gitkeep` 只是社区约定的文件名，并不是 Git 的特殊功能。

## 快照与“差异”并不冲突

Git 保存快照，但仍然很擅长显示差异。比较两个快照，就能计算出文件新增、删除和修改了哪些行。后面正式学习差异查看时，要记住差异是比较结果，不代表提交只保存了那几行补丁。

## 常见误解

### “提交就是一份压缩包”

提交会指向项目快照，但提交本身还包含作者、时间、说明和父提交等信息。它不是一个可以简单等同于压缩包的文件。

### “改动一个大文件，每次都会完整占用一份空间”

工作模型层面应当把每次提交看作完整快照。实际存储怎样复用文件内容、怎样把相似版本压缩，下一章会在介绍 Git 对象后展开。

## 小结

Git 的每次提交都代表项目的一份完整视图。差异是两个视图的比较结果。下一章把快照、提交、历史和仓库连接成第一个完整模型。
