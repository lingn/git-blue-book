# 仓库、对象、历史与提交

前面已经出现了快照和历史节点。本章为它们给出稳定定义，并说明它们怎样组成一个仓库。

## 提交：带上下文的历史节点

一次**提交**记录以下信息：

- 一份项目快照；
- 作者和创建时间等身份信息；
- 一段说明本次变化目的的消息；
- 一个或多个父提交，用来表示它从哪里发展而来。

第一条提交没有父提交。普通的后续提交通常有一个父提交。把两条工作线合并时，新提交可能有两个父提交。

每个提交都有一个由其内容计算得到的标识，通常显示为一串十六进制字符。日常界面经常只展示前几位，只要在当前范围内能够唯一识别即可。后面会把这种标识称为对象 ID 或提交 ID。

## Git 怎样把一份项目快照装起来

先不记名词，想一个很普通的项目目录：

```text
my-project/
├── README.md
└── src/
    └── app.txt
```

Git 要保存这份快照，至少要回答三个问题：

1. 每个文件里面具体写了什么？
2. 文件分别放在哪个目录、叫什么名字？
3. 这份目录状态是谁在什么时候、因为什么原因记录下来的？

Git 没有把整个项目粗暴地装进一个大压缩包，而是让不同类型的对象各自回答一个问题。它们一旦写入，就不会在原地改内容；新的变化会产生新的对象。

### 第一个盒子：blob 只装文件内容

可以把 **blob** 先理解成“只装文件内容的盒子”。例如，`README.md` 里面是：

```text
这是项目说明。
```

Git 会为这段内容保存一个 blob。这个盒子只关心内容，不知道文件叫 `README.md`，也不知道它位于哪个目录。

这看似奇怪，却很有用：如果 `docs/README.md` 恰好也是完全相同的内容，两个路径可以共用同一个 blob。文件改了一行，内容变了，就会得到另一个 blob。

### 第二张清单：tree 记录目录关系

光有内容盒子还不够，Git 还需要知道“哪个名字对应哪个盒子”。**tree** 可以先理解成“一层目录的清单”。它记录：

- 文件名、文件属性，以及它对应的 blob；
- 子目录名，以及代表子目录的另一个 tree。

对于上面的项目，根目录清单大致是：

```text
根目录清单（root tree）
├── README.md -> README 内容的 blob
└── src       -> src 目录的 tree
                 └── app.txt -> app.txt 内容的 blob
```

所以，文件名不在 blob 里，而在 tree 的目录条目里。`src` 也是一个目录条目，它指向下一层 tree；这就是 Git 能表示多层目录的原因。

### 第三张记录卡：commit 说明这份快照

现在，Git 已经有了文件内容和目录结构，但还缺少“这是什么时候记录的、为什么记录”。**commit** 可以先理解成“一张提交记录卡”。它会指向项目根目录的 tree，并记录：

- 这次提交的父提交（如果有）；
- 作者、提交者和时间等信息；
- 提交说明。

因此，commit 不直接把每个文件的内容再抄一遍，而是从根 tree 一层层找到所有文件。

### 三者合在一起

把刚才的三个比喻换回正式名称，关系就是：

```text
commit（提交记录卡）
└── root tree（根目录清单）
    ├── README.md -> blob（README 内容）
    └── src       -> tree（src 目录清单）
                    └── app.txt -> blob（app.txt 内容）
```

这就是“一个提交指向一份完整快照”的内部组成方式：commit 找到根 tree，tree 找到文件路径，blob 提供文件内容。没有变化的文件可以继续使用原来的 blob；变化的文件使用新的 blob。标签是给这些对象取稳定名字的另一种机制，等到后面的标签章节再单独说明。

## 内容寻址

Git 根据对象类型、长度和内容计算对象 ID，再用这个 ID 查找对象，这叫内容寻址。内容变化会得到不同 ID；父提交或提交说明变化，也会使 commit 对象 ID 变化。

这个机制让 Git 能检查对象内容是否与 ID 一致，并复用相同内容。它不等于访问控制、作者身份认证或密码学签名；仓库权限和签名是另外的安全层。

日常工作不需要手工操作对象数据库。先掌握“blob 保存内容、tree 组织路径、commit 连接快照与历史、可读名字标记对象位置”，后续命令的状态变化就可以从这套模型推导。

## 从存储实现看：先完整记录，再整理压缩

前面的“重复引用”首先发生在文件级别：没有变化的文件继续引用已有 blob；只改文件名而没有改内容时，也不必重新保存文件内容。

如果一个文件的内容确实变化，Git 会把变化后的完整内容视为一个新 blob。即使只改了一行，新 blob 在逻辑上仍然包含整个新版文件，而不是只包含这一行补丁。刚写入仓库时，这类对象通常以**松散对象**存在：每个对象单独保存，并对自身内容进行压缩。此时，旧版和新版中相同的字节仍可能各自占用空间。

Git 还会把许多对象整理进一种称为 **packfile** 的文件。整理时，它可能选择一个完整对象作为基础，把另一个相似对象保存成一组差量指令。例如：

```text
基础对象：app v1 的完整内容
app v2：复制 v1 的前半段 + 插入新内容 + 复制 v1 的后半段
```

这种方式称为 **delta compression（差量压缩）**。它处理的是字节，不是面向读者的逐行差异。基础对象也不保证是更早的版本；Git 会根据相似度、大小和读取成本选择存储方案。

需要区分两层压缩：

- 松散对象的压缩减少一个对象内部的重复；
- packfile 中的差量压缩减少多个相似对象之间的重复。

无论物理上是完整保存还是以差量保存，对象身份都由还原后的完整内容决定。存储方式改变，不会改变提交 ID，也不会把 Git 的快照模型变成“每次只保存补丁”。

## 没有手动整理，Git 会不会自动做

会，但不保证每次提交后都做。Git 的部分日常命令会在写入仓库数据后检查是否需要自动维护；只有松散对象或 packfile 等数量达到一定条件时，维护任务才真正运行。为了不拖慢日常操作，小仓库长期保持一批松散对象也很正常。

克隆或获取远程历史时，对象通常也已经通过 packfile 传输。因此，即使开发者从未手动执行过仓库整理命令，也不能据此判断仓库一定没有 packfile 或差量压缩。

Git 提供 `git gc`、`git repack` 和 `git maintenance` 等维护命令。这里只需要知道它们负责整理和优化仓库存储，不需要现在执行；后面的日常提交也不依赖读者手工运行它们。

## 历史：提交连接成的关系图

提交不是按文件名排成一摞副本。父提交关系把它们连接起来：

```text
A <- B <- C
```

这里 C 的父提交是 B，B 的父提交是 A。箭头指向过去。这个方向以后能帮助你理解：一个分支位于哪次提交，以及两条历史有没有共同起点。

## 仓库：内容与历史的容器

本书把**仓库**定义为：Git 保存对象数据库、提交历史、分支等名字以及配置的地方。

一个 Git 项目通常同时包含两类内容：

```text
项目目录
├── 可以直接编辑的文件
└── Git 管理的仓库数据
```

可以直接编辑的文件构成日常工作的视图。仓库数据负责保存已记录的历史。下一篇会给这两个区域更准确的名字，并增加一个用于准备下次提交的中间区域。

## Git 不会自动记录每次保存

编辑器保存文件，只是改变当前文件。Git 不会把每次按下保存键都变成历史节点。开发者需要主动选择哪些变化属于同一件事，再创建提交。

这是一项重要能力：一次提交应表达一个可以解释、验证和必要时撤销的意图。例如，“修复价格计算舍入错误”比“下班前保存一下”更适合作为历史节点。

## 提交一旦创建就不再原地变化

提交标识由内容和元数据共同决定。改变文件、说明或父提交，都会得到一个新的提交，而不是把旧提交原地涂改。

后面会学到多种修改或迁移已有提交变化的操作，它们底层都可能生成新提交。这个事实是区分本地历史整理和已公开历史风险的基础。

## 第一个工作模型

到这里，可以用一句话描述 Git：

> Git 在仓库中保存不可变的提交；每个提交指向项目快照，并通过父提交关系连接成历史。

这句话还没有覆盖分支、远程仓库和恢复机制，但已经足够支持下一篇的首次操作。

## 小结

- 快照描述某个节点上完整的项目内容。
- 提交把快照、身份、说明和父提交放在一起。
- 父提交关系把提交连接成历史。
- 仓库保存这些内容和关系。
- 改变已有提交会创建新提交，不会原地修改旧提交。
