# 一次提交在仓库里怎样组成

上一章把提交解释为项目在某个历史节点上的完整快照。本章继续追问：文件内容、目录结构和提交说明分别存在哪里，Git 又怎样从一个名字找到这份历史。

这一模型会贯穿后面的暂存、分支、合并、变基和恢复。日常开发不需要直接修改对象数据库，但需要知道命令在改变对象、引用、暂存区还是工作区。

## 仓库不只是一组提交

普通 Git 项目通常同时有工作区和仓库数据：

```text
my-project/
├── README.md             当前可以编辑的文件
├── src/
│   └── app.txt
└── .git/                 Git 仓库数据
    ├── objects/          对象数据库
    ├── refs/             分支、标签等引用
    ├── HEAD              当前检出位置
    ├── index             暂存区的主要存储文件
    └── config            仓库级配置
```

这张图只列出本章需要的部分，真实 `.git` 目录还会包含日志、锁文件、合并或变基的临时状态等数据。裸仓库没有可编辑的工作区，常用于服务器端远程仓库；它的仓库数据直接位于目录根部，不包在 `.git/` 下面。

本书后续使用以下工作定义：

- **对象数据库**保存不可变的 Git 对象。
- **引用**给某个对象 ID 一个可移动或固定的名字。
- **暂存区**准备下一次提交要采用的路径和对象。
- **工作区**是当前检出的、可直接编辑的文件视图。

四者不能互相替代。对象已经写入数据库，不代表它已经进入某个提交；提交对象已经存在，也不代表仍有分支能找到它。

## 四类对象各自保存什么

Git 的核心对象包括 blob、tree、commit 和 tag。对象写入后以对象 ID 寻址，不能在原对象上改内容。

### Blob 保存文件内容

blob 保存一段字节，不保存文件名、所在目录、修改时间或完整的文件权限。两个路径的内容逐字节相同，在同一种仓库对象格式下会得到同一个 blob 对象 ID。

```text
README.md ──┐
            ├──> blob 8f3a...
docs/copy.md ┘
```

文件改动后，Git 为新内容写入另一个 blob。旧 blob 不会被改写。文件名和可执行位由 tree 记录，因此仅重命名文件而不改内容时，新的 tree 可以继续指向原 blob。

### Tree 组织一层目录

tree 是一层目录的清单。每个条目记录名称、Git 关心的模式和所指对象 ID。普通文件条目指向 blob，子目录条目指向另一个 tree。

```text
root tree
├── 100644 README.md  -> blob A
└── 040000 src        -> tree B
                        └── 100644 app.txt -> blob C
```

`100644` 表示普通非可执行文件，`100755` 表示普通可执行文件，`040000` 表示子 tree。Git 的 tree 不是通用文件系统元数据备份，它不保存文件修改时间，也不保存 POSIX 权限的每一位。空目录没有条目，因此不会单独进入快照。

### Commit 把快照接入历史

commit 对象至少指向一个根 tree，并保存作者、提交者、时间、提交说明和父提交列表。根提交没有父提交，普通提交通常有一个父提交，合并提交可以有多个父提交。

```text
commit C
├── tree T
├── parent P
├── author ...
├── committer ...
└── message ...
```

commit 不保存“本次修改了哪几行”的补丁。Git 展示提交差异时，会比较该提交与父提交所指的两份快照。commit 也不保存创建它时所在的分支名；分支是对象之外的引用。

作者和提交者是两组独立字段。作者表示变化最初由谁完成，提交者表示谁在当前历史中创建了这个 commit。应用补丁、变基或代他人提交时，两者可能不同。邮箱字段是提交元数据，不等于经过验证的平台身份。

### Tag 对象为目标附加发布信息

带附注标签会创建 tag 对象。它记录目标对象、目标类型、标签名、标签创建者、说明，并可包含签名。通常还有一个 `refs/tags/...` 引用指向该 tag 对象。

轻量标签不同：它只有一个 `refs/tags/...` 引用，直接指向 commit 或其他目标，不创建 tag 对象。后文谈标签签名和发布审计时会继续区分这两种形式。

## 一个提交如何找到完整快照

假设项目包含根目录的 `README.md` 和 `src/app.txt`，对象关系大致如下：

```text
refs/heads/main
        │
        v
    commit C2  ----> parent C1
        │
        v
    root tree T2
      ├── README.md ----> blob R1
      └── src ----------> tree S2
                            └── app.txt ----> blob A2
```

从分支引用出发，Git 先找到 commit，再沿根 tree 和子 tree 找到路径及文件内容。若 `README.md` 从 C1 到 C2 没有变化，T2 可以继续指向原来的 blob R1；`app.txt` 改变后，S2 指向新 blob A2。

这个关系说明了三件事。提交代表完整快照，未变化内容可以复用，历史连接来自 commit 的父字段。提交图的可达性、分支移动和合并基点将在第三篇展开。

## 对象 ID 标识完整对象

Git 计算对象 ID 时，会把对象类型、内容长度和完整内容一起纳入输入。对象类型或任意内容变化，都会得到不同 ID。commit 的 tree、父提交、身份、时间和说明都是其内容，因此只改提交说明也会生成另一个 commit ID。

仓库的对象格式决定使用哪一种哈希算法。现有仓库通常使用 SHA-1，也可以用 SHA-256 格式创建新仓库。两种格式的对象 ID 长度不同，书中的示意值不会固定写成“永远是 40 个十六进制字符”。跨对象格式互操作还受 Git 版本与协议能力约束，迁移章节会单独处理。

命令可以接受足以在当前解析范围内唯一识别对象的缩写。仓库增长后，原来足够短的前缀可能产生歧义；脚本、审计和跨系统记录应保存完整对象 ID，不要假设固定的缩写长度。

内容寻址能发现对象内容与 ID 不一致，也能复用相同对象。它不能证明作者身份、授权过程或代码安全。签名、平台身份验证、权限和评审属于另外的控制层。

## 引用是名字，不是对象

记住长对象 ID 不适合日常工作。引用把名字映射到对象 ID，例如：

```text
refs/heads/main       -> commit C2
refs/tags/v1.0.0      -> tag T 或 commit C1
```

分支引用会在新提交创建后向前移动。`HEAD` 通常是符号引用，内容类似 `ref: refs/heads/main`，表示当前检出了哪个分支；分离 `HEAD` 时，它可以直接记录一个提交 ID。

引用可以移动或删除，对象本身仍保持不变。删除分支删除的是名字，不是立即擦除该分支曾指向的所有 commit、tree 和 blob。对象能保留多久取决于是否仍可达、reflog、其他引用和仓库维护策略，不能把“删分支后暂时还能找回”当作永久备份。

## 暂存区连接工作区与对象数据库

暂存区也叫 index，它主要记录下一份快照中各路径对应的对象 ID 和模式。执行 `git add README.md` 时，Git 会读取工作区文件、准备对应 blob，并更新 index 中 `README.md` 的条目。

这带来两个容易忽略的状态：

- blob 可以已经写入对象数据库，但还没有任何 commit 引用它；
- 同一路径在 index 中准备了一版内容，工作区随后又被编辑成另一版。

执行 `git commit` 时，Git 根据 index 写出 tree，再创建 commit，并更新当前分支引用。未跟踪且没有加入 index 的文件不会进入这次提交。第二篇会用 `status`、`diff` 和 `add` 逐步观察这些变化。

## 不可变不等于永远可恢复

“对象不可变”表示修改会产生新对象，不表示所有旧对象都永久保留。下面几类情况都会留下暂时没有分支指向的对象：

- `git add` 写入 blob 后又重新暂存别的内容；
- amend 或 rebase 生成新 commit，旧 commit 不再位于当前分支上；
- 分支被删除或 reset 到更早位置；
- 接收对象的操作中途失败。

只要还能通过其他引用、reflog 或已知对象 ID 找到它们，恢复通常较直接。对象长期不可达后，仓库维护可能清理它们。具体保留时间受配置和执行方式影响，事故现场应先停止会触发清理或继续改写历史的操作，再建立恢复引用。

## 松散对象与 packfile 不改变逻辑模型

对象刚写入本地仓库时通常以松散对象保存，每个对象单独压缩。随着对象增多，Git 可以把许多对象整理进 packfile，并让相似对象使用差量表示以节省空间。

packfile 中的 delta 是物理存储方案。它基于字节相似性选择基础对象，不承诺按文件版本的时间顺序组织，也不是提交差异的逐行补丁。读取对象时，Git 还原完整内容并按同一个对象 ID 呈现。repack、传输或重新压缩不会改变对象的逻辑身份。

`git gc`、`git repack` 和 `git maintenance` 会整理对象和辅助数据，有些日常命令也可能按阈值触发自动维护。小仓库中存在松散对象很正常。事故恢复期间不要为了“修复仓库”随意运行清理命令，清理可能缩短找回不可达对象的机会。

## 可重复观察实验

仓库提供一组隔离实验，用真实对象验证本章结论。

**前置条件**：Git 2.28 或更高版本、Bash 和 `mktemp`。在本书仓库根目录执行，不需要网络、平台账号或管理员权限。

```bash
./scripts/verify-object-model.sh
```

脚本会在系统临时目录创建仓库并配置虚构身份。它依次验证相同内容复用 blob、tree 组织路径、commit 指向根 tree、修改提交说明会生成新 commit，以及新旧 commit 的 tree 保持一致。默认退出时删除临时仓库，不改变本书工作区或历史。

成功时只输出：

```text
Object model experiment passed in isolated repository.
```

对象 ID、临时路径和提交时间由运行环境决定，脚本通过关系断言验证结果，不把某组固定哈希当作预期输出。断言失败、Git 命令不可用或临时目录无法创建时，脚本以非零状态退出；默认仍会清理已经创建的实验目录。

需要手工查看对象时，可以保留实验目录：

```bash
KEEP_OBJECT_LAB=1 ./scripts/verify-object-model.sh
```

脚本会额外打印绝对路径。把第一行引号中的说明文字替换为该路径：

```bash
lab_path="replace-with-the-printed-absolute-path"
git -C "$lab_path" log --graph --decorate --oneline --all
git -C "$lab_path" cat-file -p HEAD
git -C "$lab_path" ls-tree -r HEAD
```

`cat-file` 显示 commit 的原始字段，`ls-tree` 显示 tree 中的路径、模式和对象 ID。它们是只读观察命令。检查完成后，只删除脚本打印的那个临时目录；不要把占位符、空变量、仓库根目录或其他宽泛路径交给递归删除命令。

## 用这套模型判断命令

遇到 Git 操作时，可以分别确认四件事：是否写入新对象，是否移动引用，是否改写 index，是否覆盖工作区。比如 `git commit` 写入 tree 和 commit、移动当前分支，但通常不改工作区；`git reset --hard` 会移动引用、重置 index 并覆盖工作区，风险明显更高。

后续章节会把每条命令的状态变化映射到这四类位置。命令名称可能相近，作用位置不会因此变得含糊。
