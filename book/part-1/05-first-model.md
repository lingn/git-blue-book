# 仓库、对象、历史与提交

前面已经出现了快照和历史节点。本章为它们给出稳定定义，并说明它们怎样组成一个仓库。

## 提交：带上下文的历史节点

一次**提交**记录以下信息：

- 一份项目快照；
- 作者和创建时间等身份信息；
- 一段说明本次变化目的的消息；
- 一个或多个父提交，用来表示它从哪里发展而来。

第一条提交没有父提交。普通的后续提交通常有一个父提交。把两条工作线合并时，新提交可能有两个父提交。

每个提交都有一个由其内容计算得到的标识，通常显示为一串十六进制字符。日常界面经常只展示前几位，只要在当前范围内能够唯一识别即可。后面会把这种标识称为对象 ID 或提交 ID。

## 对象数据库怎样组成快照

仓库内部并不是为每条提交保存一个项目压缩包。Git 使用几类不可变对象组合内容：

- **blob 对象**保存文件内容，不保存文件名；
- **tree 对象**保存一层目录结构，把文件名和模式关联到 blob，把子目录名关联到其他 tree；
- **commit 对象**指向项目根 tree，同时记录父提交、作者、提交者和说明；
- **tag 对象**可以为另一个对象保存带创建者和说明的稳定标记。

假设项目有 `README.md` 和 `src/app.txt`：

```text
commit
  -> root tree
       -> README.md -> blob
       -> src       -> tree
                        -> app.txt -> blob
```

因此文件名属于 tree 的目录条目，文件内容属于 blob。同样内容出现在不同路径时，可以指向同一个 blob。某个文件没有变化时，新提交的 tree 也可以继续引用已有对象。

## 内容寻址

Git 根据对象类型、长度和内容计算对象 ID，再用这个 ID 查找对象，这叫内容寻址。内容变化会得到不同 ID；父提交或提交说明变化，也会使 commit 对象 ID 变化。

这个机制让 Git 能检查对象内容是否与 ID 一致，并复用相同内容。它不等于访问控制、作者身份认证或密码学签名；仓库权限和签名是另外的安全层。

日常工作不需要手工操作对象数据库。先掌握“blob 保存内容、tree 组织路径、commit 连接快照与历史、可读名字标记对象位置”，后续命令的状态变化就可以从这套模型推导。

## 历史：提交连接成的关系图

提交不是按文件名排成一摞副本。父提交关系把它们连接起来：

```text
A <- B <- C
```

这里 C 的父提交是 B，B 的父提交是 A。箭头指向过去。这个方向以后能帮助你理解：一个分支位于哪次提交，以及两条历史有没有共同起点。

## 仓库：内容与历史的容器

本书把**仓库**定义为：Git 保存对象数据库、提交历史、分支等名字以及配置的地方。

一个 Git 项目通常同时包含两类内容：

```text
项目目录
├── 可以直接编辑的文件
└── Git 管理的仓库数据
```

可以直接编辑的文件构成日常工作的视图。仓库数据负责保存已记录的历史。下一篇会给这两个区域更准确的名字，并增加一个用于准备下次提交的中间区域。

## Git 不会自动记录每次保存

编辑器保存文件，只是改变当前文件。Git 不会把每次按下保存键都变成历史节点。开发者需要主动选择哪些变化属于同一件事，再创建提交。

这是一项重要能力：一次提交应表达一个可以解释、验证和必要时撤销的意图。例如，“修复价格计算舍入错误”比“下班前保存一下”更适合作为历史节点。

## 提交一旦创建就不再原地变化

提交标识由内容和元数据共同决定。改变文件、说明或父提交，都会得到一个新的提交，而不是把旧提交原地涂改。

后面会学到多种修改或迁移已有提交变化的操作，它们底层都可能生成新提交。这个事实是区分本地历史整理和已公开历史风险的基础。

## 第一个工作模型

到这里，可以用一句话描述 Git：

> Git 在仓库中保存不可变的提交；每个提交指向项目快照，并通过父提交关系连接成历史。

这句话还没有覆盖分支、远程仓库和恢复机制，但已经足够支持下一篇的首次操作。

## 小结

- 快照描述某个节点上完整的项目内容。
- 提交把快照、身份、说明和父提交放在一起。
- 父提交关系把提交连接成历史。
- 仓库保存这些内容和关系。
- 改变已有提交会创建新提交，不会原地修改旧提交。
