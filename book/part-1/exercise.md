# 综合场景：三种版本管理方案怎么选

一家小团队正在维护产品报价工具。团队提出三种方案：

1. 每天下班把项目目录复制成带日期的压缩包。
2. 使用集中式版本控制，所有历史保存在公司服务器。
3. 使用 Git，每位开发者保留完整仓库，并约定一个共享仓库交换提交。

不要急着选“功能最多”的方案。先逐项判断它们能解决什么。

## 场景一：误删文件，需要昨天的版本

三种方案都可能恢复。压缩包需要人工找到正确日期并取出文件；版本控制系统能从历史中定位版本，通常还可以直接比较删除前后的变化。

结论：备份能应对数据丢失，但版本控制提供更明确的变化上下文。

## 场景二：需要知道一行计算逻辑为什么改变

压缩包只能帮助比较内容，通常没有作者和变化目的。集中式版本控制与 Git 都可以通过提交说明和历史追踪变化，前提是团队写了有意义的提交。

结论：工具提供记录能力，历史是否可理解还取决于提交质量。

## 场景三：服务器临时不可访问，但需要记录两个本地修改

压缩包仍可使用。集中式工具能否完整提交取决于具体工具和工作方式。Git 可以在本地创建提交，等网络恢复后再与共享仓库交换历史。

结论：Git 把本地记录与远程分享分开了。

## 场景四：两人同时修改同一个文件

压缩包没有协作模型，只能人工对比。集中式版本控制和 Git 都能识别双方变化，并在自动整合不了时要求人作出决定。

结论：版本控制不会替人理解业务意图，但会把无法自动决定的地方准确暴露出来。

## 场景五：某次错误修改已被后续三个正确版本采用

直接恢复整个旧压缩包会同时丢掉后续正确变化。版本控制系统可以尝试只撤销那次错误变化，并保留之后的工作。本书第五篇会完整讲解这类操作。

## 参考判断

如果只是个人短期保存一个文档，带历史的云盘或备份可能足够。如果多人长期维护软件，需要可审查历史、并行工作和精确恢复，版本控制更合适。需要离线完成完整历史操作、频繁建立分支并在多个仓库之间交换变化时，Git 的分布式模型更有优势。

关键不是“Git 永远最好”，而是先识别问题，再判断方案是否覆盖记录、比较、恢复和协作四种能力。
