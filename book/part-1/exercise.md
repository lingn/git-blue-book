# 综合场景：三种版本管理方案怎么选

一家小团队正在维护一个跨语言的报价工具。团队需要保存源码、测试、配置和发布说明，还要处理离线开发、并行修改和线上回退。有人建议每天复制目录，有人建议使用集中式版本控制，也有人建议使用 Git。

本练习不要求先选出“最先进”的工具，而是把需求拆成可验证的能力，再比较方案边界。

## 练习边界

- 讨论对象：本地副本、集中式版本库、分布式 Git 仓库；
- 读者基础：不要求会 Git 命令；
- 判断维度：记录、比较、恢复、协作、权限、离线、故障和治理；
- 输出目标：一份能向团队解释取舍的决策记录；
- 不做的事：不把任何平台套餐、界面或公司流程写成通用事实。

## 1. 把需求写成验收问题

先不要看工具，把团队需求写成问题：

~~~text
R1：能否识别当前可信版本和它的父版本？
R2：能否比较两个版本的多文件变化？
R3：能否只撤销一次错误修改而保留后续工作？
R4：两个人同时修改时，能否保留双方历史并暴露冲突？
R5：网络不可用时，能否继续记录本地历史？
R6：能否审查谁在什么上下文创建了一个变化？
R7：设备或服务器损坏后，能否从其他副本恢复？
R8：规则、权限、CI 和发布是否有独立的控制面？
~~~

R1 至 R3 是个人历史能力，R4 至 R5 是协作和离线能力，R6 至 R8 是工程治理与恢复能力。不要用“工具功能很多”替代这些问题。

## 2. 场景一：误删文件，需要昨天的版本

目录副本可以通过日期找到一份文件，但要确认它和其他文件是不是同一批版本。集中式和 Git 都能从历史节点读取文件，但恢复动作仍要确定路径和版本。

比较证据：

| 方案 | 可以证明什么 | 不能自动证明什么 |
| --- | --- | --- |
| 目录副本 | 某个时间存在一份字节 | 它是否和其他文件同一版本 |
| 集中式 | 服务器历史中的文件版本 | 本地是否有完整离线历史 |
| Git | commit tree 中的路径和父关系 | 从未记录的未跟踪字节 |

如果误删的文件从未进入版本历史，Git 也无法保证找回。备份和文件系统快照仍然需要保留。

## 3. 场景二：知道某行逻辑为什么改变

目录副本通常只有时间和文件名，作者、父关系和变更意图需要另写文档。集中式和 Git 可以记录提交、作者和差异，但历史是否可理解仍取决于提交质量。

验收时不要只看“有历史”：

~~~text
候选版本：完整对象 ID
父版本：完整对象 ID
变化路径：精确路径
变化说明：提交正文或关联记录
验证：测试、构建和运行证据
~~~

Git 的 blame、log 和 pickaxe 可以缩小调查范围，但它们只提供本地对象线索，不能自动证明业务责任或线上根因。

## 4. 场景三：服务器暂时不可访问

目录副本还能在本地复制，但多人协作需要另行同步。集中式工具能否完整提交取决于客户端缓存和产品设计，中央服务不可用时，提交、锁和权限可能都无法完成。

Git 的本地仓库可以继续：

- 创建 commit；
- 比较本地快照；
- 创建分支；
- 运行本地测试；
- 记录尚未分享的工作。

网络恢复后再通过 fetch、merge、rebase 和 push 交换历史。离线能力不等于自动同步，团队仍需处理远端并发和权限。

## 5. 场景四：两人同时改同一文件

目录副本只能人工比较。集中式和 Git 都可以计算变化，但自动合并仍可能无法判断业务意图。

可靠系统应保留：

~~~text
共同祖先
开发者 A 的变化
开发者 B 的变化
最终选择
验证和责任记录
~~~

Git 的三方合并在不能自动决定时产生冲突状态，让人选择最终 tree。没有冲突并不代表业务正确，配置、schema 和 API 的不重叠改动也可能组合出错误行为。

## 6. 场景五：错误修改之后已有三个正确版本

恢复整份旧目录会丢掉后续正确内容。版本控制可以根据提交图选择回退范围：

~~~text
A <- 错误 B <- 正确 C <- 正确 D <- 正确 E
~~~

如果 E 已经共享，通常追加一个反向提交抵消 B 的效果，保留 C、D、E 的历史。Git revert 只改变源码 tree，数据库、消息和运行实例需要单独回退或向前修复。

## 7. 场景六：多人和自动化都需要权限

目录副本没有稳定的引用和接收规则。集中式系统通常把权限集中在服务器。Git 的对象和引用是分布式的，权限要在传输、接收端、托管平台、CI、制品和部署系统分别实现。

比较时要问：

- 谁可以读取完整历史；
- 谁可以更新哪些 refs；
- 哪些分支要求评审和检查；
- 机器人使用什么身份；
- 凭据泄漏后怎样撤销和清理；
- 审计记录是否覆盖 old/new OID 和主体。

“每个人有完整仓库”不是授权答案，反而要求更严格的副本和秘密治理。

## 8. 场景七：设备或服务器损坏

备份关注恢复点和恢复时间，版本控制提供历史结构。成熟方案通常组合：

~~~text
本地工作副本
共享 Git 仓库
镜像或 bundle
对象和文件系统备份
LFS、制品、平台数据备份
恢复演练和验收清单
~~~

一个本地 clone 不是完整灾备计划。浅克隆、部分克隆、LFS、子模块、评审数据、CI 和制品可能不在其中。恢复后要验证 refs、对象闭包、外部 payload、权限和运行版本。

## 9. 决策矩阵

| 需求 | 本地副本 | 集中式 | 分布式 Git |
| --- | --- | --- | --- |
| 个人短期保存 | 可以 | 可以 | 可以 |
| 多文件变化作为单元审查 | 弱 | 强 | 强 |
| 完整离线历史 | 取决于工具 | 通常受限 | 通常支持，受克隆范围影响 |
| 廉价分支和本地合并 | 弱 | 依产品 | 强 |
| 单一共享权限中心 | 弱 | 较强 | 需要平台和组织治理 |
| 多副本恢复 | 依赖备份 | 依赖服务器备份 | 依赖镜像、备份和副本管理 |
| 线上制品和运行证据 | 没有 | 需外部系统 | 需外部系统 |
| 多仓库迁移和协作 | 手工 | 受服务器约束 | 需管理 refs、身份和副本 |

结论应写成约束匹配，而不是工具排名。例如“需要离线创建提交、廉价分支和精确回退，因此选择 Git；通过受保护远程、CI、制品和备份弥补多副本治理成本”。

## 10. 选择后的验证计划

如果选择 Git，第一阶段不应只验证 git status 是否能用，而要验证：

1. 新仓库能创建基线提交；
2. 工作区、index 和 HEAD 的变化可以解释；
3. 分支、合并和冲突可以在临时仓库复现；
4. 远程 fetch、push 和非快进拒绝有测试；
5. 误删提交可以从 reflog 或 bundle 恢复；
6. CI、制品、部署和数据库证据有独立记录；
7. 权限回收、秘密泄漏和灾难恢复有演练。

使用本书实验：

~~~bash
./scripts/verify-object-model.sh
./scripts/verify-all.sh
~~~

全量脚本只证明仓库声明的本地实验和链接门禁通过，不能代替目标组织的真实平台与恢复演练。

## 小结

选择版本控制方案时，先把需求写成记录、比较、恢复、协作、离线、权限和灾备问题，再比较工具边界。本地副本保存状态，集中式方案提供共享服务器，分布式 Git 把历史能力分布到多个仓库。Git 也需要中心化平台和组织治理，但本地记录与远程分享的分离，让工程团队可以在离线、并行和故障场景下保持可追溯性。
