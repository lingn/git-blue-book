# 权限不是角色名：入职、转岗、离职与紧急访问

一个工程师从支付团队转到数据团队，原来的组织成员关系没有删除；外包人员的合同已经结束，账号仍在一个继承写权限的组里；发布机器人换了 owner，却继续使用前任保管的长期令牌。平台页面可能把这些主体都显示为 “Member”，真正的问题却是：它们现在还能通过哪些路径，以谁的身份，对哪些仓库执行什么动作。

权限治理不能停在“给用户一个 Developer 角色”。有效权限来自身份目录、组织和团队继承、仓库直接授权、应用安装、部署 key、机器人、分支规则、环境审批与临时例外的合成结果。入职、转岗和离职改变的是这条授权链，删除一个页面上的成员不等于链条已经断开。

本章延续[机器身份](../part-10/02-machine-identities.md)中的“主体 × 资源 × 动作 × 上下文 × 时间”模型，把重点放在组织级授权生命周期。实验使用 Git 2.49.0、本地 bare 仓库、虚构主体和合成 receive hook；它验证清单对账、负例状态与服务端拒写的 Git 边界，不连接身份目录或托管平台，也不冒充真实平台角色、会话撤销和审计日志。

进入本章前，读者应理解远程认证、受保护引用、机器身份、仓库生命周期和写入围栏。读完后，应能：

- 从多个授权入口计算主体的有效访问，而不是只看仓库成员页；
- 为入职、转岗、离职和外部协作者定义有时限、有 owner 的状态转换；
- 把自然人、机器主体、群组、凭据、会话与审计事件分开处置；
- 设计最小角色、直接授权例外、权限认证和漂移门禁；
- 为 break-glass 建立有限动作、双人批准、到期与事后复盘；
- 区分 `pass`、`fail` 与 `inconclusive`，不把采集失败解释成没有权限。

## Git 保存对象和引用，不保存组织授权

Git commit 的 author、committer 和签名者是对象内容或其密码学证明；接受 push 的服务端 actor 属于认证与授权控制面。四者可以完全不同。把 `user.email` 改成管理员邮箱不会获得仓库权限，服务端接受管理员推送也不代表 commit 中的 author 就是管理员本人。

协议端只会呈现允许当前会话读取或更新的引用，并返回成功或拒绝。组织成员、团队继承、SAML/SCIM 状态、应用安装、令牌 scope、管理员绕过和审计保留都不是 Git 对象的一部分。迁移或恢复了所有 refs，也不会自动恢复正确权限。

因此权限证据至少来自四层：

| 层 | 需要固定的事实 | 不能替代什么 |
| --- | --- | --- |
| 身份目录 | 稳定 principal ID、雇佣/合同状态、团队、manager、禁用时间 | 不能证明平台会话已撤销 |
| 托管平台 | 组织、群组、直接成员、应用、key、角色、规则与绕过 | 不能证明云环境或制品库权限 |
| Git 数据面 | 服务端实际接受/拒绝的 clone、fetch、push 与 ref 更新 | 不能解释授权来自哪条策略 |
| 审计与运行系统 | actor、会话、来源、旧/新 OID、API、CI run、部署事件 | 不能单独证明当前权限已收敛 |

这些层要通过稳定 principal ID、仓库资产 ID、会话/事件 ID 和对象 OID 连接。显示名和邮箱可变，也可能重复，不能作为唯一关联键。

## 有效访问是授权图的并集，再与门禁求交

一个主体对仓库的有效能力可以近似写成：

```text
候选授权 = 组织继承 ∪ 团队授权 ∪ 仓库直授 ∪ 应用/Key 授权 ∪ 临时例外
有效能力 = 候选授权 ∩ 主体有效状态 ∩ 资源/动作/上下文/时间门禁
```

并集意味着“删掉一条授权”经常不够。工程师退出仓库直授列表后，仍可能通过父组织、嵌套团队或应用获得写权限；删除个人令牌后，SSH key、活跃 Web 会话、deploy key 或机器人共享 secret 仍可能可用。

交集也意味着“拥有仓库写角色”不保证任何写入都成功。受保护 ref、required checks、签名要求、合并队列、环境审批和服务端 hook 还会限制具体动作。反过来，能更新一个功能分支不证明不能修改 main；只测试正向路径会漏掉权限扩大。

### 用能力矩阵代替模糊角色名

角色名由厂商和版本定义，组织策略应先写成能力矩阵，再映射到平台：

| 主体 | 资源 | 允许动作 | 上下文 | 时限 |
| --- | --- | --- | --- | --- |
| 普通开发者组 | 所属仓库 | 读、写个人/功能 ref、发起评审 | 不可直接更新受保护主线 | 在职且团队关系有效 |
| 维护者组 | 指定仓库 | 管理评审、合并已满足门禁的候选 | 不可自行修改组织级策略 | 任期与季度认证有效 |
| 发布机器人 | 指定仓库与制品库 | 创建不可变发布 tag、发布既有制品 | 受信任 workflow、已批准候选 | 单次短期会话 |
| 外部协作者 | 指定仓库 | 完成合同所需的最小读/写 | sponsor 有效、禁止继承无关资源 | 固定到期日 |
| Break-glass | 事故涉及的资产 | 明确列出的恢复动作 | 事故单、双人批准、全程告警 | 分钟/小时级窗口 |

若平台最小角色仍包含多余动作，要用受保护引用、独立 namespace、服务端代理或仓库拆分补偿，并登记残余风险。不能把平台可选的最小角色直接称为业务上的“最小权限”。

## 权威登记与观测快照必须分开

权限登记表达批准的意图，平台快照表达某个时点采集到的事实。最小登记可包含：

```text
principal_id
principal_kind
principal_status
principal_owner
repository_id
action_set
grant_source
valid_from
valid_until
approval_case
last_certified_at
```

观测快照还要记录平台/实例、采集时间、API 版本、调用主体、分页游标、采集范围、原始响应摘要和错误。若调用主体看不到企业级继承、应用权限或隐藏成员，快照只能是“不完整”，不能成为“无其他权限”的证据。

对账时保留授权来源，不只输出扁平角色：

```text
principal-42 -> team-payments -> repository-asset-123 -> write_feature_ref
principal-42 -> temporary-exception-778 -> repository-asset-123 -> bypass_review
```

第二条路径到期时，即使第一条仍有效，也必须单独撤销例外。只保存最终的 `write` 会丢失审批、到期和撤销入口。

## 入职：从职责模板开始，不从复制同事开始

入职授权的前置条件是身份目录已有稳定 principal、雇佣/合同状态生效、直属团队与负责人确认。不要复制某位资深同事的全部团队和直接权限；那会把历史例外、管理员能力和临时项目一起复制。

安全流程是：

1. 从岗位/团队模板生成候选能力，而不是候选平台角色；
2. 由资源 owner 确认仓库集合和动作，敏感资产增加独立批准；
3. 通过群组授予常规权限，避免无法归因的仓库直授；
4. 为外部人员、临时项目和高风险动作设置到期日；
5. 首次登录后验证 SSO/MFA、最小读写路径和反向拒绝路径；
6. 保存审批、最终有效权限和平台事件 ID。

验证不能只做一次 clone。至少在专用测试仓库检查：应读仓库可读、不应读仓库被拒；功能 ref 可按策略更新、受保护 main 不能直接更新；不需要的 secrets、环境、package 和管理员设置不可访问。生产主线不是权限探针。

## 转岗：先建立新职责，再撤掉旧能力

转岗通常需要短暂重叠来完成交接，但“先加后忘记删”会永久积累权限。转岗单应同时携带新旧职责、重叠窗口和旧权限撤销时间：

```text
REQUESTED
  -> NEW_ACCESS_PROVISIONED
  -> HANDOVER_VERIFIED
  -> OLD_ACCESS_REVOKED
  -> EFFECTIVE_ACCESS_CERTIFIED
```

先确保新团队可接管 on-call、评审、发布和恢复职责，再删除旧团队、仓库直授、规则绕过、环境、云角色和秘密访问。若员工仍需支持旧系统，应创建有资源、动作和到期日的过渡授权，而不是保留原维护者角色。

转岗也会改变资产 owner。必须联动上一章的仓库登记、CODEOWNERS 路由、机器人 owner、例外批准人、break-glass 联系人和备份恢复负责人。只改身份目录中的 department 字段不会自动完成这些转移。

## 离职：目标是切断所有有效会话和授权路径

离职不是在平台删除用户这一项动作。根据风险和离职类型，流程应在预定时间或立即触发：

1. 禁用身份目录主体并阻止新会话；
2. 撤销 SSO、个人令牌、SSH/GPG key 关联、应用授权、活跃 session 和 refresh token；
3. 删除组织/团队/仓库直授、管理员与规则绕过；
4. 轮换已知共享 secret、部署 key、恢复码和离职者可读取的根凭据；
5. 转移 issue、评审、on-call、CODEOWNERS、机器人和仓库 owner 职责；
6. 检查最后活动、异常下载、fork、镜像与离职窗口内的 ref/API 更新；
7. 从普通权限与反向测试证明旧主体不能再读写，并保存失败证据；
8. 在延迟系统、缓存和下游服务超过传播窗口后再次认证。

删除 SSH 公钥不会结束已有 HTTPS token；禁用平台账号也不撤销一枚独立 deploy key；轮换共享密码若没有更新合法消费者，会把安全处置变成生产事故。清单必须按每类身份和凭据分别记录执行者、结果、失败和恢复。

历史 commit、tag 签名和评审记录不应因离职被改成新人身份。它们描述过去发生的事件；权限回收处理未来能力。若数据保护要求匿名化或删除个人数据，应走独立合规流程，不能通过改写作者字段伪造历史责任。

## 外部协作者需要 sponsor、范围和硬到期

外部主体与员工的差异不只是邮箱域名。每项授权至少绑定内部 sponsor、合同/项目、仓库、动作、数据分类、允许的本地副本、到期日和删除/返还义务。

到期应默认撤销，而不是发邮件等待 sponsor 回复后无限续期。续期是一次新的风险确认，要检查实际使用、范围和数据处理要求。若平台角色通过上级 group 继承，要确认外部主体不会因加入一个方便的团队读到同 namespace 的其他仓库。

合同结束后，平台拒绝访问只证明服务端入口关闭。开发者 clone、fork、导出、CI artifact 和本地凭据仍需按协议处置；Git 无法证明对方所有副本已经删除。

## 机器主体随工作负载退出，不随员工账号苟存

机器身份的凭据选择、OIDC 和最小权限已在第十篇说明。本章关注它与组织生命周期的联动：

- 每个机器 principal 必须有当前 owner、备用 owner、用途、运行位置和退出触发器；
- Owner 离职不应直接让生产机器人停摆，但必须触发接管和根凭据复核；
- 工作负载下线时撤销应用安装、deploy key、token、webhook、runner、云角色与 secret，而不只删除 workflow 文件；
- 最后使用时间只能发现候选闲置，不能证明没有 schedule、灾备或季度发布依赖；
- 机器人不应通过人的维护者团队继承权限，也不应用个人邮箱作为恢复渠道；
- 自动轮换要验证旧值确实拒绝、新值只到达合法消费者，不能只记录“生成成功”。

对共享机器人逐步拆分时，先建立“哪个 workload 使用哪枚凭据”的观测，再按动作迁移。直接撤销一枚无人能盘清消费者的共享 token 可能中断生产；继续保留则扩大事故面。两者都要求明确风险 owner 和时限。

## 直接授权与管理员权限应当成为有期限的例外

群组授权让入转离能沿身份目录传播，也便于 owner 认证。仓库直授适合短期诊断、外部协作或平台限制场景，但必须有理由、批准、到期和替代方案。没有到期的直授会逐渐成为第二套组织结构。

管理员和策略修改权限要与日常代码维护分开。能合并代码不应自然获得修改 required checks、安装应用、查看所有 secrets 或删除仓库的能力；否则被保护规则拦下的人可以先删除规则再操作。

高风险控制建议满足职责分离：申请人不能单独批准自己的管理员权限；资源 owner 不能独自关闭组织级安全策略；执行 break-glass 的人不能删除对应审计。小团队无法完全分离时，应明确补偿控制，例如实时告警、事后独立复核和更短会话。

## Break-glass 是一次受控状态转换

Break-glass 不应常驻在管理员团队，也不应作为 CI 失败时的快捷按钮。一次紧急授权至少经历：

```text
SEALED
  -> REQUESTED
  -> APPROVED
  -> ACTIVE
  -> REVOKED
  -> REVIEWED
```

请求记录事故等级、目标资产、允许动作、当前/目标 ref OID、被绕过规则、申请人与批准人；激活产生唯一会话和硬到期，使用即通知独立渠道。执行结束立即撤销或轮换取用材料，再对服务端最终 refs、平台变更、CI/部署和审计完整性复核。

若紧急更新 Git ref，仍应使用显式期望旧值，防止覆盖事故期间的新提交；若平台只能提供宽管理员角色，要在代理、网络、会话录制或人工双控层限制动作。紧急通道不可用时的恢复路径也要演练，避免事故中临时创建一个无人审计的全局管理员。

## 定期认证要问“为什么仍需要”，不是“页面上还在吗”

认证周期按数据分类、生产影响和权限强度分层。每次认证至少比较：

- 身份目录状态与平台有效主体；
- 批准的能力矩阵与组织/团队/仓库直授并集；
- 外部协作者、临时授权和 break-glass 的到期状态；
- 机器 owner、最后使用、根凭据、运行位置和撤销入口；
- 管理员、规则绕过、secret/environment、应用安装和 deploy key；
- 仓库业务/技术 owner、CODEOWNERS 路由和实际可响应人员；
- 最近权限变更、拒绝事件、批量 clone/download 和异常来源；
- 上次发现的例外是否修复、延期或过期。

Owner 点一下 “Approve all” 不是有效认证。报告应把新增、删除、权限扩大、过期、未知来源和采集缺口分开，让 owner 对具体差异作决定。零变化也要保留采集范围与证据摘要，否则无法证明本次真的看到了完整集合。

## `pass`、`fail` 与 `inconclusive` 不能合并成布尔值

一个可靠的对账器至少返回三态：

- `pass`：声明和观测范围完整，且没有违反策略的有效授权；
- `fail`：存在已确认的离职残留、过期外部访问、越权、无 owner 机器身份或未批准例外；
- `inconclusive`：API 无权限、分页中断、身份不存在、来源无法解析或快照超时，无法证明结果。

`inconclusive` 不是较轻的 pass。对管理员、删除、生产发布等高风险转换，应失败关闭并升级采集问题；低风险只读仓库可以按明确时限人工复核。策略应记录为何选择，而不是让工具遇到空输出默认返回零成员。

修复顺序也不同：fail 先围栏或撤销已知越权，再分析影响；inconclusive 先保护高风险动作、修复可见性和采集完整性，不应在证据未知时批量删除可能仍服务生产的机器身份。

## 平台实施必须做正向与反向验收

平台角色、嵌套组、SSO/SCIM、会话撤销、审计字段、保留期和套餐均会变化。实施时按厂商、云/自托管版本、许可、权限和核对日期登记，下列是厂商无关验收矩阵：

| 验收路径 | 期望 | 证据 |
| --- | --- | --- |
| 普通开发者读所属仓库 | 成功 | 服务端 actor、仓库 ID、操作时间 |
| 普通开发者直接更新 main | 拒绝 | 拒绝事件、main 旧 OID 不变 |
| 已离职主体读取和写入 | 均拒绝 | 各凭据/协议反向测试与会话状态 |
| 发布机器人创建规定 tag | 成功 | tag OID、actor、CI run、批准候选 |
| 发布机器人修改 main/策略 | 拒绝 | Git/API 两条拒绝证据 |
| 外部协作者访问到期 | 拒绝 | 到期时间、授权路径消失、反向测试 |
| Break-glass 在批准窗口执行限定动作 | 成功 | 事故单、会话、旧/新 OID、实时告警 |
| Break-glass 缺批准或过期 | 拒绝 | 拒绝原因与无状态变化证明 |

`git ls-remote --exit-code <url> refs/heads/main` 可以验证当前凭据是否能从一个 Git 入口读取指定 ref，但成功不能证明写权限，失败也可能来自网络、TLS/SSH、认证或 ref 不存在。写测试只使用专用测试 ref；管理策略、API、LFS、package 和环境权限必须在对应控制面另测。

## 常见失败与恢复

| 症状 | 常见原因 | 安全动作 |
| --- | --- | --- |
| 用户已移出仓库，仍能 push | 仍在父团队、直接授权、应用或活跃会话中 | 先冻结高风险 ref，枚举完整授权链和服务端 actor，再逐项撤销 |
| 离职后 CI 大面积失败 | 自动化借用了个人身份或共享 secret | 恢复时建立专用低权限机器主体；不要重新启用离职账号作为长期方案 |
| 外部协作者到期后仍能读取 | 上级组继承、到期只在工单未在平台执行 | 立即撤销入口，审查下载/clone 事件和副本处置，修复自动到期流程 |
| 删除旧团队后无人能发布 | 未盘点隐含职责和机器人 owner | 暂停发布，按已知好配置恢复最小发布身份，完成职责接管后再清理 |
| Break-glass 每周都在使用 | 常规流程不可靠，紧急身份变成旁路 | 收回常驻权限，修正常规门禁；把历史使用当作控制失效调查 |
| 权限报告显示零管理员 | API token 看不到企业继承或分页失败 | 标记 inconclusive，阻断高风险变更，修复采集权限后重跑 |
| 角色相同但两个用户能力不同 | 直接 grant、组继承、规则 bypass 或会话上下文不同 | 输出逐路径有效授权，不以显示角色做最终比较 |
| 撤销 token 后旧操作仍成功 | 还有 SSH key/session，或撤销传播尚未完成 | 识别实际认证入口，按最坏情况围栏，超过传播窗口后再次反向验证 |

## 合成实验：权限快照、过期门禁与服务端拒写

本书提供 `scripts/verify-access-lifecycle-governance.sh`。在仓库根目录执行：

```bash
bash scripts/verify-access-lifecycle-governance.sh
```

脚本只在 `mktemp` 目录创建本地工作仓库、bare 远端、虚构主体清单和 receive hook，结束时自动删除。它使用固定的合成核对时刻，不依赖本机身份或当前日期。

实验验证：

1. 完整快照中的自然人、外部协作者、机器主体和 break-glass grant 通过结构门禁；
2. 已禁用主体仍有有效团队关系时返回明确 fail，而不是因为其他字段偶然失败；
3. grant 引用身份目录中不存在的主体时返回 inconclusive，不把未知主体当作已撤销；
4. 普通开发者只能推送功能 ref，不能直接更新 main；
5. 已离职主体的 push 被服务端拒绝，目标 ref 不出现；
6. 发布机器人只能创建约定的 release tag，不能修改 main；
7. Break-glass 只有事故单匹配且未过期时才能更新 main，缺批准或过期后服务端 OID 保持不变。

合成 hook 通过环境变量表示认证主体，只用于证明“在接收端按主体、ref、时间和批准做拒绝”这一机制。真实 Git 服务不会信任客户端自报的环境变量；必须从已认证会话取得 actor，并验证管理员/API/LFS/合并等所有写入口。实验不证明 SSO/SCIM、嵌套组、会话撤销、审计保留或任何 GitHub/GitLab 权限语义。

## 小结

权限治理的对象不是一个角色名，而是从主体到资源和动作的全部有效路径。入职要从职责模板和反向测试开始；转岗要显式结束旧能力；离职要同时处理身份、授权、凭据、会话和共享秘密；外部访问与例外必须有硬到期；机器主体随工作负载退出；break-glass 是有审批、有边界、可撤销、要复盘的状态转换。

Git 可以证明某个会话的 ref 读写结果和对象状态，不能证明组织授权已经完整收敛。权威声明、平台快照、身份目录和服务端审计必须独立保存并对账。下一章将处理规则集与例外：怎样把这些权限边界和分支保护写成可评估、可逐步推广而不会一次阻断全组织的策略。
