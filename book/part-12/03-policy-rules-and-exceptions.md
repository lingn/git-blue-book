# 规则不是开关：作用域、渐进执行与例外治理

组织决定“所有生产仓库都必须经过评审”后，平台团队创建了一条全局规则。第二天，一批镜像仓库无法同步，旧项目的检查名称对不上，紧急修复也找不到合法入口。团队于是给管理员永久绕过权限，几周后没人再知道哪些仓库真正受保护。

问题不在于规则太严格，而在于把策略发布当成了一个开关。组织级规则需要确定作用域、组合语义、证据输入、执行阶段、例外生命周期、漂移监测和回退条件。否则同一句“开启分支保护”，在不同仓库、身份和平台版本上会产生不可预测的有效行为。

第六篇的[受保护引用与例外](../part-06/08-protected-refs-and-exceptions.md)解释一次主线更新为什么需要评审、检查与服务端裁决；第八篇的[触发与 checkout](../part-08/01-triggers-and-checkout.md)和[候选提交](../part-08/02-candidate-commits.md)解释事件、路径策略、候选和检查结果怎样避免过期。本章不重复这些语义，而是回答另一个问题：当组织有数百或数千个仓库时，怎样把这些要求组合成可解释、可分批推广、可审计和可撤销的策略系统。

本章使用厂商无关模型。GitHub、GitLab 和自建平台在规则继承、优先级、绕过、评估模式、审计字段、版本、权限与套餐上并不相同；任何产品映射都必须登记核对日期。随章实验使用 Git 2.49.0、本地 bare 仓库、TSV 策略和合成 `pre-receive` hook，只验证规则求值、ref 更新与拒写边界，不冒充托管平台规则集。

进入本章前，读者应理解仓库资产 ID、有效权限、受保护引用、required checks、机器身份和 break-glass。读完后，应能：

- 为规则定义稳定身份、适用对象、证据、效果、模式和版本；
- 让组织基线、风险分类与仓库规则以明确语义组合；
- 识别优先级覆盖、空匹配和候选仓库自授权等危险设计；
- 用 draft、audit、warn、enforce 和 retired 管理规则状态；
- 通过 canary、反向测试、指标和停止条件渐进推广；
- 把例外限制到一条规则、一个资源/动作/主体和有限时间；
- 对声明策略、平台观测与实际拒绝行为做三方对账和安全回退。

## 一条可治理规则不只是布尔值

规则至少包含以下字段：

| 字段 | 要回答的问题 |
| --- | --- |
| `rule_id` | 哪条稳定规则产生了决定；改名后是否仍可追踪 |
| `policy_version` / digest | 使用了哪一份不可变策略内容 |
| owner | 谁负责风险目标、故障响应和退役 |
| scope | 哪些仓库、refs、动作、主体和上下文适用 |
| predicate | 哪些事实使规则命中 |
| evidence | 评审、检查、签名、身份、old/new OID 等输入来自哪里 |
| effect | 要求、拒绝、限制参数，还是只记录观察 |
| mode | draft、audit、warn、enforce 或 retired |
| failure policy | 证据缺失/超时/采集失败时 fail closed 还是升级处理 |
| exception policy | 是否允许例外、谁批准、最长多久、需要什么补偿控制 |
| rollout | 哪个 cohort、何时扩大、停止与回退条件是什么 |

`rule_id` 应保持稳定，语义变化由版本和摘要表示。只保存可读名称会让“Require review”被原地修改后仍看似同一规则。策略决定和审计事件都要记录版本；否则无法重放某次 push 当时为什么被接受。

规则 owner 不是平台管理员的默认别名。业务/安全 owner 决定风险要求，平台 owner 负责可靠实现，仓库 owner 处理适用性与例外；三者可能是不同团队。

## 求值输入和结果都必须可以重放

一次策略求值可抽象为：

```text
decision = evaluate(
  policy_version,
  repository_snapshot,
  principal_and_session,
  action,
  old_object,
  proposed_object,
  review_and_check_evidence,
  active_exceptions,
  evaluation_time
)
```

输出不应只有 `allow=true`。最小决定记录包括：

- 仓库稳定资产 ID、平台 locator 与数据分类快照；
- actor、认证会话、动作、目标 ref、old/new OID；
- 命中的 rule ID、各自模式和证据版本；
- 未命中规则的作用域解释；
- 使用的例外 ID、批准、有效期与补偿证据；
- `allow`、`deny`、`would_deny` 或 `inconclusive`；
- 求值时间、策略 digest、执行器版本和关联审计事件。

`would_deny` 表示规则在 audit/warn 阶段发现了不满足，但没有阻止动作。它不是 pass。若报表只统计实际拒绝，审计模式会错误显示为“零违规”。

`inconclusive` 表示输入不完整或执行器无法判断。高风险动作不能把 API 超时、检查身份未知或策略版本缺失当成没有违规；如何失败关闭取决于动作风险，但未知状态必须保留下来。

## 作用域从稳定资产事实中选择

常见作用域包括：

- 全组织基线；
- 业务域、法律实体或数据驻留区；
- 数据分类、生产等级、互联网暴露和恢复等级；
- 仓库资产 ID 或受控仓库集合；
- ref namespace、路径所有权、动作和主体类型；
- rollout cohort、平台实例和能力版本。

优先使用上一章登记的稳定 `repository_id` 和独立控制面的分类。仓库名称、namespace、topic、README 标签或候选分支内 YAML 都可能被修改；若它们直接决定是否受保护，能提交代码的人可能让仓库退出规则。

动态 scope 要保存求值时的成员快照。例如“所有 `data_class=regulated` 的 active 仓库”今天包含 80 个资产，明天分类修正后可能是 83 个。没有快照，无法判断规则遗漏是当时分类错误还是后来集合变化。

### 空匹配必须报警

规则部署成功但 scope 匹配零仓库，通常不是安全的零事件。它可能是字段拼错、namespace 改名、采集权限不足或平台语法变化。规则应声明预期规模范围；低于下限、突然下降或全集采集不完整时返回 inconclusive/告警，而不是“0 个不合规”。

同样，过宽匹配要停止推广。一个原计划覆盖 20 个 canary 的规则突然命中 2,000 个仓库，不能因为配置语法合法就继续 enforce。

## 组合语义应是明确的代数，不是“最后一条赢”

组织基线、风险分类和仓库规则可能同时适用：

```text
组织基线：主线至少一名独立审批者
受监管分类：主线还需要可信签名和两人审批
仓库规则：release/* 还需要发布检查
```

安全默认是累积要求：三个 scope 的要求取并集；布尔禁止按 deny-dominant 组合；最小审批数取更严格值；允许的主体/动作取交集。仓库级规则可以更严格，不能靠更高“优先级”静默取消组织基线。

优先级只应处理明确定义的同类参数或确定诊断顺序。例如两个规则分别要求 1 人和 2 人审批，可以明确取 `max(1, 2)`；一个要求 tag 不可变、另一个允许覆盖，则不是排序问题，而是策略冲突，应阻止发布并要求 owner 处理。

以下组合必须在设计时逐项定义：

| 规则类型 | 推荐组合方式 | 危险实现 |
| --- | --- | --- |
| 必需检查集合 | 并集，并固定报告者身份 | 后一条规则覆盖整张列表 |
| 最少审批数 | 取最大值 | 仓库自行改回 0 |
| 允许主体 | 取交集或显式授权路径并集后再过门禁 | 用一个全局管理员通配符覆盖限制 |
| 禁止删除/强推 | 任一禁止即禁止，例外另建对象 | “最具体 allow”取消基线 deny |
| 规则模式 | 每条规则独立 audit/enforce | 仓库 audit 让组织 enforce 失效 |
| 证据不可用 | 按动作风险与规则 failure policy | 空结果默认 success |

若平台有自己的优先级和继承算法，先在测试组织验证，再把实际映射登记为易变事实。不能把本章推荐语义当成平台已经提供的保证。

## 策略状态本身是一台状态机

可用的规则发布过程：

```text
DRAFT
  -> VALIDATED
  -> AUDIT
  -> WARN
  -> ENFORCE_CANARY
  -> ENFORCE_BROAD
  -> RETIRED
```

- `DRAFT`：尚未进入实际求值，只能评审 schema、scope 和测试；
- `VALIDATED`：静态检查、单元/回放测试和冲突检查已通过；
- `AUDIT`：对真实事件求值并生成 would-deny，不阻止；
- `WARN`：仍不阻止或只阻止明确低风险路径，但把问题送达 owner；
- `ENFORCE_CANARY`：只对选定 cohort 阻止；
- `ENFORCE_BROAD`：按批准 scope 强制执行；
- `RETIRED`：不再参与新决定，但版本和历史事件继续保留。

不是每个平台都原生支持这些模式。可以在外部策略服务、报告流水线或影子规则中实现 audit，但必须说明哪个层真正拥有拒绝权。客户端 lint 只能提前反馈，不能代替接收端或平台控制面。

从 audit 进入 enforce 不是按日历自动触发。至少满足：scope 可见且规模合理；would-deny 已归因；必需检查稳定报告；owner 和支持渠道可响应；反向测试通过；合法例外已到位；回退版本已验证。

## 渐进推广需要 cohort、指标和停止条件

Canary 不应只挑“肯定不会失败”的空仓库。样本要覆盖活跃服务、库、镜像、归档候选、LFS/submodule、机器人写入和不同风险等级，同时排除未经批准的生产破坏。

推广指标至少分开：

- 规则命中仓库与事件数、未分类/不可见资产数；
- would-deny 的规则、主体、动作与根因分布；
- 真正策略违规、配置误报、检查基础设施故障和 owner 无响应；
- 合法变更成功率、P50/P95 等待时间、队列长度和重试；
- 例外新增、使用、过期、续期和未撤销数量；
- 执行器延迟、超时、fail-open/fail-closed 次数；
- 反向测试中本应拒绝却被接受的严重漏控。

“拒绝数下降”可能只是开发者停止使用正规入口或管理员转而绕过，不能单独证明成熟。要同时看旁路、直接 push、策略修改、人工发布和未受管仓库。

停止条件要在发布前写好，例如：错误拒绝超过阈值；关键检查报告者不可用；scope 扩大超出批准范围；审计事件缺失；出现本应拒绝却接受的更新；回退演练失败。达到条件后冻结扩大范围，必要时回到上一已知好版本，而不是临时给所有人绕过。

## 例外不是优先级更高的 allow 规则

例外应作为独立、有生命周期的治理对象：

```text
exception_id
rule_id
repository_id
principal_id / principal_kind
action / ref_scope
valid_from / valid_until
reason / approval_case
requester / approvers
compensating_controls
usage_budget
revocation_status
```

它只豁免列出的规则，不删除其他累积要求。某仓库因 CI 基础设施故障临时豁免 `ORG-CI-001`，仍然需要评审、禁止强推和签名；把例外实现成 `allow_all=true` 会把不相关控制一起移除。

例外的最小流程：

```text
REQUESTED -> RISK_REVIEWED -> APPROVED -> ACTIVE
                                      -> EXPIRED
                                      -> REVOKED
                                      -> REVIEWED
```

申请人不能单独批准自己的高风险例外。批准人要看到受影响规则、实际失败证据、替代方案和补偿控制。有效期使用硬截止时间，过期默认拒绝；续期是新决定，不能静默移动日期。

每次使用例外都记录 actor、事件、old/new OID、被豁免 rule ID、补偿证据和结果。零使用例外应在短期后删除；频繁使用说明基础规则、检查可靠性或工作流设计有问题，不应无限续期。

### Break-glass 与普通例外不同

普通例外解决已知、有限、可计划的策略不适配；break-glass 处理事故中常规控制面不可用或恢复动作无法等待。两者都要限资源/动作/时间，但 break-glass 还要求取用即告警、独立保管、最短会话和事故复盘。不要把“紧急”字段加到永久管理员白名单后就称为 break-glass。

## 策略即代码的信任边界在候选仓库之外

把规则写成代码能获得评审、版本、测试和回滚，但存放位置决定谁能授权谁。若应用仓库的候选提交能同时修改代码、required checks 列表和验证脚本，再由同一候选运行并批准自己，策略就失去外部约束。

组织策略仓库或控制面至少需要：

- 与受管仓库分离的写权限和 CODEOWNERS；
- 策略 schema、scope、冲突、空匹配和例外字段验证；
- 固定解析器/执行器版本及其供应链；
- 对已知事件的 allow/deny/would-deny/inconclusive 回放测试；
- 双人评审、签名或来源证明，以及不可变发布 digest；
- 部署前后的目标平台快照、审计关联和回退版本；
- 防止执行器读取候选仓库中可修改的信任根。

Git commit 或 tag 签名只能证明策略对象由某个 key 签署，仍要验证 key 到 principal、principal 到组织授权以及发布流程。详见第十篇签名章节。

## 对账要比较声明、平台观测和行为探针

只有策略仓库显示最新 commit 不足以证明规则正在执行。至少形成三角验证：

1. **声明**：批准的 policy version、scope、mode、exceptions 和 rollout；
2. **观测**：平台当前规则、继承关系、绕过主体、检查映射和配置摘要；
3. **行为**：专用测试仓库的正向/反向操作及服务端审计。

声明与观测 digest 不同是 drift；API 无权限、分页中断或平台不提供完整读取接口是 inconclusive；配置相同但反向测试被接受，说明执行入口、scope 或旁路仍有缺口。三者任一异常都不能只靠重新推送策略掩盖。

漂移修复要先判来源：批准的人工紧急变更、平台默认迁移、控制器失败、恶意修改或采集错误需要不同处置。控制器自动覆盖未知人工变更可能抹掉事故现场；高风险漂移先冻结策略修改和相关写入口，保存快照与审计，再决定恢复声明还是接受新状态。

## 安全回退是恢复上一份策略，不是关闭保护

每次推广前保存：上一已知好版本、目标 scope、平台观测摘要、正反向测试、已存在例外和回退负责人。回退也要经过条件检查：确认当前策略版本仍是预期值，避免覆盖推广期间另一个合法变更。

回退目标应是上一份可工作的最小保护，而不是把组织规则全部 disabled。若新 required check 名称错误导致无法合并，可以恢复旧检查映射；不应顺手允许直接 push、强推和删除。

规则回退后保留失败版本、would-deny/deny、错误影响和已使用例外。删除失败记录会使后续无法判断哪些提交在保护降级窗口进入主线。修复完成后从 audit/canary 重新推广，不直接跳回全量 enforce。

## 服务端 hook 只能覆盖它真正看到的入口

`pre-receive` 可以检查一次 receive-pack 中的 old OID、new OID 和 ref，并整体拒绝 push；它适合演示非快进、tag 不可变和自建 Git 服务的接收门禁。它看不到或不天然管理平台合并审批、Web/API 管理操作、LFS、package、issue、release、环境和云部署。

Hook 还运行在服务端信任边界，代码、依赖、超时、资源消耗和日志本身需要治理。不要从待检查的候选分支加载 hook；不要在 hook 内运行无界构建；外部策略服务不可用时要有明确 failure policy。托管平台是否允许自定义服务端 hook、在哪个版本/套餐可用，属于厂商事实。

本地 `receive.denyNonFastForwards` 等配置可以拒绝一类更新，却没有组织 scope、评审证据、例外审批和跨仓 rollout 语义。它们是执行机制，不是完整策略控制面。

## 平台落地前的验证矩阵

在专用测试组织/仓库验证并登记产品、版本、许可、权限和日期：

| 路径 | 必须回答 |
| --- | --- |
| Scope | 改名、转移、新仓库、fork、归档和默认分支变化后是否仍命中 |
| 组合 | 组织、群组、项目、仓库和 ref 规则怎样合并；冲突如何报告 |
| 身份 | 管理员、应用、deploy key、机器人和外部协作者是否可绕过 |
| 评审/检查 | 新提交或基线变化后证据是否过期；同名检查由谁报告 |
| 模式 | audit/warn 是否真的不阻断并保留 would-deny；enforce 是否覆盖全部入口 |
| 例外 | 能豁免哪条规则、最长多久、过期/撤销传播多快、每次使用是否留痕 |
| 失败 | API/策略服务/CI 不可用时 fail-open/closed 行为是什么 |
| 审计 | actor、rule/version、old/new OID、例外和策略修改能否完整关联 |
| 回退 | 能否恢复上一版本而不制造无保护窗口或覆盖并发配置 |

平台 UI 文案和截图只能帮助定位，不能作为长期语义。若读 API 不能看到完整继承或绕过集合，必须把结果标成 inconclusive，并用管理员导出、行为测试或厂商支持补证。

## 常见失败与恢复

| 症状 | 常见原因 | 安全动作 |
| --- | --- | --- |
| 全局规则启用后大量仓库不能合并 | 未先 audit；检查名称、历史仓库和机器人入口不同 | 停止扩大 scope，恢复上一策略版本；按根因修复后从 canary 重来 |
| 仓库规则看似更具体，却取消组织保护 | 平台/自研执行器采用 last-wins | 冻结策略变更，恢复累积/deny-dominant 语义并增加冲突测试 |
| 规则显示部署成功但覆盖为零 | Scope 字段拼错、资产分类缺失或读取不全 | 标记 inconclusive，修复资产与采集；不要按零违规发布 |
| required check 永久 pending | 检查改名、跳过、报告者身份或候选绑定变化 | 恢复旧映射或正确报告；不要把所有检查设为可选 |
| 例外过期后仍可绕过 | 例外被复制成永久 allowlist、缓存或会话未收敛 | 先围栏高风险入口，撤销授权和会话，审查过期后的所有使用 |
| 所有事故都申请同一例外 | 例外范围过宽或常规恢复路径失效 | 拆分规则/动作，修复基础设施；限制续期并复盘历史影响 |
| 策略仓库是最新的，平台仍旧 | 部署失败、平台人工漂移或观察 API 不完整 | 比较声明/观测/行为，保全审计后按来源修复 |
| 回退时关闭了全部保护 | 没有上一已知好版本或只提供总开关 | 恢复最小基线，审查降级窗口提交，再建立可版本化回退 |

## 合成实验：规则组合、推广、例外与漂移

本书提供 `scripts/verify-policy-rules-and-exceptions.sh`。在仓库根目录执行：

```bash
bash scripts/verify-policy-rules-and-exceptions.sh
```

脚本在 `mktemp` 目录创建虚构仓库登记、规则与例外 TSV、本地工作仓库和 bare 远端，使用固定合成时间。它不读取用户 Git 配置，不连接网络，不修改蓝皮书仓库。

实验验证：

1. 组织审批/CI 规则与受监管分类签名规则累积适用，仓库规则不能降低组织基线；
2. 签名规则处于 audit 时，缺签名事件允许但产生 `would-deny`；提升为 enforce 后同一证据被拒；
3. 内部普通仓库不命中受监管分类规则，证明 scope 不是全局误套；
4. 有效例外只豁免指定 CI 规则，缺审批仍被拒，过期后不再生效；
5. 未知仓库或不可见观测返回 inconclusive，观测 digest 漂移返回 fail；
6. 本地 hook 在 audit 模式允许非快进 main 并记 would-deny，enforce 后拒绝且 ref 不移动；
7. 有效单规则例外可临时允许一次更新并留下记录，缺事故单或过期后再次拒绝。

Hook 通过合成环境变量接收例外信息，真实服务绝不能信任客户端自报 actor、批准或证据。实验只证明确定性求值、Git ref 状态和接收端拒绝机制，不证明 GitHub/GitLab 的规则优先级、评估模式、管理员绕过、API、合并、LFS 或审计语义。

## 小结

组织规则的成熟度不取决于开了多少开关，而取决于每次决定能否回答：哪一版策略、为什么命中、哪些证据满足、哪条例外生效、执行器是否完整看见现场，以及怎样安全回退。

规则组合要有明确代数，仓库不能靠“更具体”取消组织基线；推广要经过 audit、canary 和停止条件；例外只豁免一条明确要求并硬到期；策略仓库、平台观测和行为探针必须持续对账。下一章将进入审计日志与证据留存，解决“平台记录很多事件”为什么仍不等于能完成调查、合规证明和长期验证。
