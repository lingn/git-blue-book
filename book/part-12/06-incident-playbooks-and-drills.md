# 恢复能力要靠演练证明：组织级故障手册与改进闭环

文档里写着“主站故障时切换到灾备”，事故发生后却没人知道谁可以宣布故障、谁有权围栏写入、备份密钥由谁保管、业务是否接受丢失最后三次 push。技术命令可能都正确，组织仍会因为决策权和信息流不清而停在原地。

组织级故障手册的目标不是列出更多 Git 命令，而是让正确角色在信息不完整、时间受限和系统持续变化时，按证据进入下一状态；遇到超出假设的现场能停止、升级和保全证据。恢复演练则验证这套人、权限、平台、数据和通信链条真实可用，而不是让参与者背诵文档。

第十一篇的[故障转移与安全回切](../part-11/06-disaster-failover-and-failback.md)承担副本滞后、donor、recovery namespace、条件提升与旧主围栏等技术主线；本篇前五章分别建立仓库生命周期、权限、规则、审计和容量控制。本章把它们组合成组织行动，不重复每条恢复命令。

本章以 Git 2.49.0、本地 bare 仓库和合成事件包验证有限的 Git 数据面门禁。真实演练必须使用获批测试组织/环境，按平台、版本、许可、权限、故障域和核对日期记录；本地实验不模拟 DNS/TLS、身份、数据库、LFS、CI、对象存储、人员响应或真实 RPO/RTO。

进入本章前，读者应理解现场保护、灾难恢复状态机、break-glass、策略例外、审计调查包、容量门禁和单一写入权威。读完后，应能：

- 区分故障手册、操作 runbook、检查单和通信模板的职责；
- 按业务影响、完整性、安全与控制面风险宣布和升级事件；
- 建立事件指挥、技术恢复、安全、证据、通信和业务决策角色；
- 用有门禁的状态机编排围栏、证据、恢复点、候选验收和开放写入；
- 为 Git、LFS、评审、CI、身份、审计、制品与依赖分别记录恢复状态；
- 设计桌面、组件、端到端与受控故障转移演练；
- 定义失败注入、停止条件、观察员证据和安全边界；
- 把演练发现转成有 owner、截止、验证和风险接受的改进闭环。

## Playbook、runbook、检查单不是同一份文档

| 载体 | 解决的问题 | 适合内容 | 不应承担 |
| --- | --- | --- | --- |
| Playbook | 某类事件怎样分流、决策和协作 | 触发、严重度、角色、状态机、场景分支、停止/升级 | 每个平台命令的全部参数 |
| Runbook | 在已确认前提下怎样执行一个技术步骤 | 权限、位置、命令/API、预期、失败、验证、恢复 | 业务风险接受和跨团队优先级 |
| Checklist | 高压下防止漏掉已知关键项 | 宣告、围栏、证据、验收、开放、交接 | 解释未知故障或替代判断 |
| 通信模板 | 向不同受众稳定传递事实 | 影响、已知/未知、动作、风险、下次更新时间 | 内部秘密、未经证实归因 |

把所有内容塞进一份数百页 runbook，事故时找不到入口；只留五行 checklist，又无法解释分支条件。Playbook 链接版本化 runbook，检查单从 playbook 的门禁生成，通信模板引用同一事件状态。

每份文档记录 owner、版本/digest、适用平台/资产、前置知识、最近演练、下次复核和替代联系人。链接到“当前页面”但不固定版本，会让复盘无法知道事故时执行的是哪一版。

## 严重度来自影响和风险，不来自告警颜色

宣布事件前先区分：

- **可用性**：开发者/CI 无法 clone、fetch、push、评审或下载 LFS/制品；
- **完整性**：refs、对象、LFS、评审、制品或备份可能丢失、损坏或分叉；
- **机密性/身份**：token、key、审计数据或私有源码可能泄漏；
- **控制面**：权限、规则、默认分支、审计、队列或平台数据库异常；
- **容量/性能**：磁盘、配额、锁、队列或尾时延导致退化/拒写；
- **供应链**：CI 依赖、签名、runner、cache、制品来源或发布身份失陷。

同一事件可能跨多类。平台不可用但数据健康，可以优先恢复服务；对象损坏伴随复制仍在运行，应先停止传播；凭据泄漏时切换区域却沿用同一 secret 会把攻击面一起迁移。

严重度至少考虑：受影响资产/用户、生产与发布影响、数据丢失上限、未授权能力、传播速度、恢复可逆性、合规/公开披露和当前未知项。一个低流量但持有生产基础设施的仓库，commit 数少也可能是最高严重度。

### 宣告要允许“证据不足但风险足够”

不必等根因确认才宣布。可以写：

```text
已知：主平台 Git push 在两个区域失败；只读 clone 部分成功
未知：最后三个 ref update 是否已复制，LFS 与审计 checkpoint 未核对
当前风险：若开放 standby 写入可能造成分叉
动作：宣布 SEV-1，围栏全部写入，保全主/备 checkpoint
下一次更新：20 分钟后或恢复点选择完成时
```

未知项不是措辞缺陷，而是决策输入。通信不能把“正在核对”写成“无数据丢失”，也不能用推测责任人填补 actor 缺口。

## 角色按决策权分开，不让一个人同时操作、批准和记录

最小角色：

| 角色 | 主要责任 | 不应默认兼任 |
| --- | --- | --- |
| Incident Commander（IC） | 严重度、目标、优先级、状态转换、停止/升级和交接 | 亲自执行所有命令 |
| Technical/Recovery Lead | 组织技术诊断、候选恢复和验收计划 | 单独接受超 RPO 损失 |
| Git/Data Recovery Operator | 在隔离环境执行 refs/对象/备份 runbook | 批准自己的高风险提升 |
| Platform/Infrastructure Lead | 网络、存储、数据库、平台、LFS 和故障域恢复 | 擅自打开写入 |
| Security/Identity Lead | 凭据撤销、污染边界、break-glass 和来源信任 | 为可用性跳过证据保全 |
| Evidence/Scribe | 时间线、决策、命令、输出、缺口和交接 | 修改原始证据或推断结论 |
| Communications Lead | 内部、客户、管理层和合规沟通节奏 | 发布未获批准的归因/细节 |
| Business/Asset Owner | 接受 RPO/业务降级、恢复优先级和后续风险 | 指挥底层技术操作 |

小组织可以一人承担多个角色，但必须明确冲突和补偿控制。至少把“执行破坏性恢复”“批准数据损失/开放写入”“保管审计记录”分开，或安排实时双人复核。

角色登记使用稳定 principal/团队和备用联系人，不只写某个可能离职的姓名。事故频道不可用、身份系统故障或公司通讯中断时，备用联系路径要独立取得并定期演练。

### RACI 表不能替代指挥结构

RACI 能说明常态责任，却不回答事故中谁有最终决定权、如何交接、信息多久更新。Playbook 明确：当前 IC、各 workstream lead、批准矩阵、交接确认和单一决策日志。多个“共同 IC”会制造相互矛盾的命令。

## 事件状态机把技术步骤包在组织门禁里

一个最小组织状态机：

```text
DETECTED
  -> DECLARED
  -> WRITES_FENCED
  -> EVIDENCE_PRESERVED
  -> RECOVERY_OBJECTIVE_APPROVED
  -> CANDIDATE_VALIDATED
  -> PROMOTED_READ_ONLY
  -> WRITES_OPEN
  -> STABILIZED
  -> REVIEWED
```

各状态与第十一篇技术状态相容，但增加人、证据和控制面条件。不能从 DETECTED 跳到 WRITES_OPEN，也不能因为 RTO 计时逼近目标就把 incomplete 验收改成 pass。

### DETECTED → DECLARED

门禁：事件 ID、初始影响/分类、IC 与 scribe、通信频道、受影响资产/故障域、下一更新时间。若告警可能含敏感信息，建立受限安全/证据频道和对外脱敏频道。

### DECLARED → WRITES_FENCED

围栏清单按入口而非页面：Git SSH/HTTPS、平台 merge/API、tag/release、LFS、package、CI 写回、机器人、webhook 重试、mirror/replication、管理员旁路。完全失联的旧端记录其网络/凭据/自动加入风险，防止恢复在线后双写。

围栏本身可能扩大业务影响，IC 决定；安全/恢复 lead 验证反向测试。只看到 maintenance banner 不算完成。

### WRITES_FENCED → EVIDENCE_PRESERVED

固定主/备 refs 与 checkpoint、平台/身份/审计/CI/LFS/制品状态、容量与进程、围栏结果。原件、逻辑快照和恢复副本分离；每个采集保存时间、权限、查询、退出码、摘要与缺口。

若持续写入或自动维护仍在改变现场，标记采集不一致，重新围栏；不要覆盖失败采集。

### EVIDENCE_PRESERVED → RECOVERY_OBJECTIVE_APPROVED

明确每个数据面的 RPO/RTO、候选来源、预计丢失、不可逆动作和批准人。业务 owner 接受业务损失，安全 lead 接受来源信任/凭据策略，技术 lead确认候选可验证；任何一方的 unknown 写入决策日志。

“恢复最新”不是目标。最新副本可能损坏/污染，较旧备份可能丢业务事件。选择理由要能复盘。

### RECOVERY_OBJECTIVE_APPROVED → CANDIDATE_VALIDATED

技术 runbook 在隔离环境验证 Git refs/对象/HEAD/tree/tag/signature、LFS/submodule、平台数据、权限/规则、审计、CI/制品和容量。每项为 pass/fail/inconclusive/not_applicable，并说明依据。一个 Git `fsck` 通过不能覆盖外部数据面。

Unexpected OID、alternate/promisor 外部依赖、审计空窗、容量不足或服务检查失败触发停止条件，状态保持不前进。

### CANDIDATE_VALIDATED → PROMOTED_READ_ONLY

只有旧权威仍围栏、控制面 generation/checkpoint 符合预期时提升。先只读启动，验证普通客户端、权限、规则、审计、LFS/制品和业务查询；记录平台实际 endpoint/版本/证书，不只改 DNS。

### PROMOTED_READ_ONLY → WRITES_OPEN

IC 基于验收包批准。开放按最小范围/canary 进行：专用测试 ref、普通成员、机器人、评审/CI/制品链和反向拒绝。失败立即重新围栏，不在未知状态持续写入。

### WRITES_OPEN → STABILIZED → REVIEWED

确认单一权威、旧主 quarantine、新复制 checkpoint、告警/队列/机器人稳定、凭据例外回收、数据损失通知与下一班交接。Stabilized 不是关闭事件；复盘、改进行动和遗留风险进入 REVIEWED。

## 恢复清单按数据面分别打状态

| 数据面 | 恢复点/验收 |
| --- | --- |
| Git | 全约定 refs、symbolic HEAD、对象格式、connectivity、关键 tree/tag/notes |
| LFS/大对象 | pointer 清单、payload OID/size、空 cache 水合、锁/权限 |
| 评审/项目数据 | issue/MR、审批、评论、附件、ID 映射、默认分支 |
| 身份/权限 | 人/机器 principal、规则绕过、break-glass、会话/凭据撤销 |
| CI/CD | 候选 checkout、workflow 版本、runner、secret/environment、检查报告者 |
| 制品/发布 | tag、release、package/image、digest、provenance、部署状态 |
| 审计 | raw cursor/sequence、schema、actor/request、查询与保留 |
| 备份/复制 | 恢复点、下一 checkpoint、独立故障域、恢复后首个成功备份 |
| 容量/性能 | Git/LFS/制品/scratch、错误率、尾时延和维护冻结 |

每行都有 owner、evidence link、status 和开放阻断级别。`not_applicable` 要有理由；`inconclusive` 不能由项目经理为了进度改成 pass。

恢复范围可以分阶段，例如先恢复只读 Git、后恢复评审，最后发布。但对外说明哪些功能/数据仍不可用，不能把部分恢复写成平台完全恢复。

## 通信是控制回路，不是事后公关

不同受众需要不同细节：

- 响应团队：精确 OID、endpoint、日志、命令、风险和任务；
- 开发团队：哪些操作暂停、客户端不要做什么、预计下次更新；
- 业务/管理层：影响、可接受损失决策、恢复阶段与风险；
- 安全/法务/合规：机密性、证据、通知义务和批准；
- 外部用户：已确认影响、可用替代、更新时间，不泄漏攻击细节。

固定节奏但允许关键状态即时更新。每条更新包含事件 ID、时间/时区、当前状态、已知/未知、最近完成、正在做、风险/阻塞和下次更新时间。

不要在多个聊天、工单和状态页分别维护互相矛盾的“真相”。决策日志是权威；通信从中生成，敏感字段按受众脱敏。口头/电话决定由 scribe 回填并由决定者确认。

## 停止条件比“成功路径”更重要

技术人员在计时压力下容易连续尝试。Playbook 在执行前定义必须暂停并升级的条件：

- 候选 OID/refs 与批准恢复点不符；
- 检查发现 missing/corrupt、未知 replace/alternate/promisor；
- 旧端或其他入口仍接受写入；
- 审计/证据采集出现无法解释缺口；
- 身份、规则或 break-glass 不能按预期限制；
- LFS/平台/制品与 Git 恢复点不一致；
- Scratch/磁盘/配额低于任务安全余量；
- 条件提升 expected generation/OID 不匹配；
- 参与者或观察员认为演练可能影响未授权生产范围；
- 关键角色/批准人失联，或通信渠道无法使用。

停止不是演练失败，而是安全控制成功。记录触发条件、当时状态、采取的围栏和恢复方式；只有 IC/授权人基于新证据批准后继续。

## 演练不是只有“切一次灾备”

由低风险到高保真：

1. **文档走查**：Owner 检查链接、权限、联系人、前提和版本；
2. **桌面演练**：给定场景/注入，参与者口头做决策，验证角色、通信和分支；
3. **组件技术演练**：从空环境恢复 bundle/LFS/审计分区或轮换机器身份；
4. **集成演练**：在专用环境恢复 Git + 平台 + CI + 制品并跑端到端验收；
5. **受控故障转移**：获批生产或等价环境，真实围栏、提升、开放和回切；
6. **突发/混沌演练**：在成熟控制下减少预告，验证检测与决策；绝不是未经授权破坏生产。

桌面演练不能证明命令、凭据和备份可用；组件演练不能证明跨团队通信；一次成功生产切换也不能覆盖对象损坏、安全事故和审计丢失。演练组合按风险覆盖矩阵设计。

### 选择场景而不是重复同一种可用性故障

建议轮换：

- 平台入口不可用但主数据健康；
- Standby 落后且开发 clone 持有新 commit；
- 错误 force push/删除 refs，mirror 已传播；
- Pack/对象损坏，自动复制必须停止；
- LFS payload/制品缺失但 Git `fsck` 通过；
- 员工 token 泄漏并伴随机器人共享凭据；
- 规则误配导致全组织无法合并；
- Git/LFS/审计容量耗尽或维护锁死；
- 审计 collector 漏页/时区错误；
- 迁移 cutover 后新旧端双写；
- 身份/密钥控制面不可用，break-glass 失效。

场景要关联资产等级、过去事故和架构变化，不只追求戏剧性。

## Inject 用来验证判断，不是捉弄参与者

每个 inject 写明：注入时间/触发条件、参与者看到的信息、真实底层状态、预期能力、观察点和停止条件。例如：

```text
当团队准备提升 standby 时注入：审计 checkpoint 显示最近一次 push 未复制，
但一台 CI checkout 持有候选 commit。期望：停止提升；保全 CI donor；
进入 recovery namespace 验证，不直接把 donor main 设为权威。
```

观察员不应随意改变“真相”让参与者必败。Inject 之间保持因果一致，关键证据可被参与者通过正常渠道发现。需要测试未知情况时，答案可以是“当前无法确认”，期望动作是围栏/升级而非猜中谜底。

预先准备控制组：演练负责人、平台安全/生产保护人、终止口令、影响监控、恢复脚本和数据销毁。若演练触发真实事故，立即停止演练，由真实 IC 接管，演练日志作为现场证据保留。

## 演练成功不只看 RTO

记录：

- 检测、宣告、围栏、证据、恢复点批准、候选验收、只读、开放和稳定耗时；
- 每数据面的实际 RPO、不可恢复事件和置信度；
- 状态门禁是否按证据执行，是否出现无审批跳步；
- 角色响应、交接、通信准确性和更新节奏；
- 权限/凭据能否取得和及时回收；
- Runbook 步骤成功率、手工修正、不可用命令和版本漂移；
- Stop condition 被触发时是否真的暂停；
- 旧主围栏、单一权威和回切安全性；
- 演练产生的临时数据、凭据、refs、费用和清理结果。

RTO 很短但选择了错误恢复点、跳过证据或留下双写，是失败。RTO 超标但 stop condition 阻止了数据破坏，说明安全控制有效，同时暴露需改进的恢复效率。

指标用于改善系统，不用于惩罚个人。若参与者担心“用时太长”而隐藏未知/绕过门禁，演练会训练错误行为。

## 改进行动必须闭环到能力，不止写复盘

复盘区分：事件/演练时间线、影响、技术/组织促成条件、有效控制、失败控制、未知、决策权衡和改进。避免“某人忘了执行”作为终点；追问为什么检查单、自动化、权限或观察没有阻止。

每项行动包含：

```text
action_id / risk
owner / backup_owner
due_at / priority
acceptance_evidence
dependencies / funding
status / blocked_reason
verified_by / verified_at
residual_risk / risk_acceptor / expires_at
```

“更新文档”只有在新版本经评审并用场景重演验证后才完成；“增加监控”要证明触发和到达 on-call；“修复备份”要从空环境恢复。关闭工单不能替代能力证据。

无法按期修复的残余风险由有权 owner 接受，写明补偿控制和到期；不能无限延期。高严重度发现进入下一次演练 scope，验证真正解决而不是换了描述。

## 演练计划本身需要治理

年度/季度计划按资产与场景风险覆盖，不要求所有仓库逐一做完整生产切换。共享平台做故障域演练，关键资产做端到端恢复，普通资产用分层抽样与 owner 认证；任何仓库仍要有可执行退出/恢复路径。

计划记录上次/下次日期、场景、层级、参与角色、环境、版本、成功条件、发现和未覆盖项。重大平台迁移、身份/备份架构、对象格式、LFS、规则或组织 owner 变化后，不等常规周期，触发相关演练。

演练数据使用虚构身份/仓库或批准的脱敏副本；临时 token、DNS、refs、制品和云资源有清理/保留清单。不要把生产秘密复制进“测试灾备”，也不要在销毁演练环境时删除需要保留的审计证据。

平台提供哪些沙盒、备份恢复、审计、故障转移和管理员能力属于易变事实。演练前登记版本、许可、权限、费用、支持窗口和厂商限制；未经验证的 API/UI 步骤不能成为唯一恢复入口。

## 常见失败与恢复

| 症状 | 常见原因 | 安全动作 |
| --- | --- | --- |
| 所有人都在执行命令，没人做决定 | 无单一 IC，角色与 workstream 混乱 | 暂停破坏性动作，指定 IC/scribe，重建目标和状态 |
| 事故迟迟不宣布 | 团队等根因或害怕严重度升级 | 按影响/风险先宣告，未知项显式；后续可降级 |
| 页面维护模式已开但仍有 push | 围栏清单只覆盖 UI | 冻结全部 Git/API/LFS/机器人入口，反向测试并保留事件 |
| 为追 RTO 直接提升最新副本 | 未批准 RPO、未知复制滞后或污染 | 保持只读，固定 checkpoint/候选，业务/安全/技术联合决策 |
| 候选 `fsck` 通过就开放 | LFS、平台、权限、审计、CI/制品未验收 | 重新围栏，按数据面矩阵补证；unknown 不改 pass |
| 演练中发现真实生产影响 | 环境/权限/路由隔离失效 | 触发终止口令，真实事件接管；保全演练与生产证据 |
| Break-glass 账号取不到或过宽 | 从未演练、恢复因子失效、常驻管理员 | 停止高风险步骤，按替代批准路径处理；事后修复并再演练 |
| 旧主恢复后自动接受写入 | Quarantine/复制/负载均衡回归未控制 | 围栏两端，盘点独有 refs/事件，重新选择权威 |
| 复盘列了几十项却无人完成 | 无 owner/验收/预算/优先级 | 按风险收敛行动，绑定能力证据和下一次演练 |
| 文档演练通过，真实恢复失败 | 只做桌面，没验证凭据/备份/命令 | 降级“已验证”声明，安排组件和端到端技术演练 |

## 合成实验：组织状态机、停止条件与单一权威

本书提供 `scripts/verify-organizational-recovery-drill.sh`。在仓库根目录执行：

```bash
bash scripts/verify-organizational-recovery-drill.sh
```

脚本在 `mktemp` 下创建虚构角色/决策/行动登记、本地 primary/standby 和恢复 bundle。它使用固定事件时间和合成控制面，不连接平台或人员系统。

实验验证：

1. 缺少 active IC/scribe 的角色表不能通过 DECLARED 门禁；
2. 状态机拒绝从 DETECTED 直接跳到 WRITES_OPEN；
3. Primary 围栏后 push 被拒，refs 保持已保存恢复点；
4. Standby 落后时候选验证失败并保持状态，不因 RTO 跳步；
5. 从 bundle 恢复批准 OID 后，`fsck`、refs、审计/外部/容量合成门禁全部满足才可验证；
6. 审计状态 inconclusive、unexpected OID 或控制面 generation 不匹配时停止提升；
7. 条件提升成功后先保持只读，开放写入后新提交只进入新权威，旧主继续拒写；
8. 复盘行动缺 owner/截止时不能进入 REVIEWED，补齐后状态链和证据包通过。

实验中的角色、审批、审计、外部系统和 control-plane generation 都是 fixture；本地 hook 只证明 Git 接收拒写。它不验证真实 DNS/TLS、数据库、身份、LFS、CI、制品、通信、值班响应、区域故障或 RPO/RTO。生产演练必须由组织授权并使用平台支持的围栏、提升和审计机制。

## 小结

恢复能力不是“有备份”和“有一份文档”，而是组织能在正确指挥权下围栏写入、保全证据、批准恢复目标、验证每个数据面、条件提升、只读验收、受控开放并持续围栏旧权威。未知和停止条件是系统的一部分，不是演练中的扣分项。

演练要逐级提高保真度，覆盖不同故障类别，使用一致 inject 与观察证据；成功标准同时看数据正确、门禁、通信、权限回收和 RPO/RTO。复盘行动只有通过新证据或下一次演练验证才算完成。至此第十二篇形成从资产生命周期、权限、规则、审计、健康容量到组织恢复演练的治理主链；下一篇将按症状建设故障排查手册。
