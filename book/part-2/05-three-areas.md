# 工作区、暂存区与提交

许多初学者第一次看到 Git 流程时都会问：文件已经保存，为什么不能直接提交，为什么中间还有一步？答案是 Git 允许你从当前所有修改中挑选一部分，组成一个意义清楚的历史节点。

## 三个区域

### 工作区

**工作区**是你当前能够直接查看和编辑的项目文件。刚创建的 `README.md` 就在工作区中。

### 暂存区

**暂存区**保存“下一次提交准备采用的内容”。它不是一个让文件暂时消失的文件夹，而是 Git 对下一份快照的准备结果。

Git 的英文信息常把它称为 index 或 staging area。两者在本书日常场景中指向同一个区域。命令输出里的 `staged` 表示内容已经进入暂存区。

### 提交历史

执行提交后，Git 根据暂存区创建不可变提交，并把它接入当前历史。提交完成并不删除工作区文件；三个区域在内容一致时，状态会显示干净。

## 内容怎样流动

正常流程可以画成：

```text
编辑文件              选择下次提交内容              创建历史节点
工作区  ─────────────>  暂存区  ───────────────────>  提交历史
```

第一步是编辑器完成的。第二步由下一章的 `git add` 完成。第三步由 `git commit` 完成。

注意，箭头表达的是内容选择和快照准备，不是把文件从一个目录搬到另一个目录。工作区文件始终留在项目中。

## 为什么暂存区有价值

假设你同时做了三件事：

- 修正文档错别字；
- 修改价格计算；
- 留下一段尚未完成的调试代码。

如果只能“提交当前全部内容”，这三件事会被迫混成一个历史节点。有暂存区后，可以先选择文档修正并提交，再选择价格修改；未完成调试代码继续留在工作区。

可选择不代表应该无限拆分。判断标准是：一次提交能否用一句明确的话说明目的，能否独立检查，必要时能否单独撤销。

## 同一个文件可以同时存在两种变化

一个文件的一版内容可以已经进入暂存区，之后你又继续编辑该文件。此时：

- 暂存区保存较早选择的内容；
- 工作区保存更新后的内容；
- 下一次提交只会采用暂存区中的版本。

这是很多“为什么我的最新修改没有被提交”问题的原因。解决办法不是猜，而是查看状态和差异。

## 暂存不是备份

暂存区是准备下次提交的工作区域，不应被当作长期备份。重要状态应形成有意义的提交。第五篇还会说明，某些强制恢复操作可能同时覆盖工作区或暂存区。

## 小结

从现在开始，遇到任何 Git 问题先问：变化位于工作区、暂存区还是提交历史？下一章将首次把 `README.md` 的内容从工作区选择进暂存区。
