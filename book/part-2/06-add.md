# 选择下次提交的内容：git add

## 操作前状态

继续使用 `git-first-lab`。此时 `README.md` 是未跟踪文件。先确认：

```bash
git status
```

然后把它的当前内容加入下一次提交：

```bash
git add README.md
```

`git add` 把指定路径的当前内容写入暂存区。这里的参数 `README.md` 是文件路径。命令成功时通常没有输出。

## 从对象模型看 `add`

第一篇讲过，Git 使用 blob 对象保存文件内容。执行 `git add README.md` 时，Git 会读取文件当前的完整内容，准备对应的 blob 对象，并让暂存区记录“下一份快照中的 `README.md` 应使用这个对象”。

因此，文件内容不是等到 `git commit` 时才第一次进入对象数据库。`git add` 已经完成了内容准备；如果仓库中已经存在内容完全相同的 blob，就可以直接复用它。文件后来继续被编辑，也不会自动改变暂存区中已经准备好的版本，必须再次执行 `git add` 才会更新。

## 用状态验证

```bash
git status
```

文件现在会出现在 `Changes to be committed` 下。简短状态类似：

```text
A  README.md
```

左侧的 `A` 表示暂存区准备新增这个文件。它没有被提交，只是下一份快照已经准备采用当前内容。

## `add` 不是只对新文件使用一次

打开 `README.md`，在末尾增加：

```markdown

这行是在第一次暂存之后添加的。
```

保存并运行 `git status`。同一个文件会同时出现在“将要提交”和“尚未暂存”两组中：暂存区有旧版本，工作区有新变化。

再次执行：

```bash
git add README.md
git status
```

现在暂存区更新为文件的最新内容，尚未暂存的变化消失。因此 `git add` 更准确的理解是“把路径当前内容更新进暂存区”，而不是“开始跟踪一次”。

## 路径范围决定选择范围

可以一次指定多个路径：

```bash
git add README.md notes.txt
```

也常见到：

```bash
git add .
```

`.` 表示当前目录及其下级路径。它很方便，也可能把日志、密钥、构建产物或未完成代码一并暂存。初学阶段优先明确列出文件，并在提交前查看 `git status` 和差异。

## 错误示范：把敏感文件加入暂存区

假设误把 `secrets.env` 加入暂存区。只取消暂存、保留本地文件，可以使用：

```bash
git restore --staged secrets.env
```

`git restore` 用于恢复文件状态；`--staged` 指定作用对象是暂存区。执行后检查 `git status`，文件会回到未跟踪或未暂存状态，磁盘上的文件仍在。

这个恢复命令在此处是一个明确场景用法。第五篇会系统讲解 `restore` 的不同作用范围。

如果敏感内容已经提交甚至推送，仅取消暂存远远不够。应立即停止传播、轮换凭据，并按照平台安全流程清理历史。

## 动手试试

确认当前只暂存了 `README.md`，并且状态中没有意外文件。不要只依据 `git add` 没有报错就认为选择正确；状态才是结果证据。
