# 不该进入仓库的文件：.gitignore

项目目录里经常出现不应进入版本控制的内容：构建产物、编辑器缓存、本地日志、临时文件，以及只适用于当前电脑的配置。逐次避开它们既容易出错，也会让状态输出充满噪音。

## 创建忽略规则

在仓库根目录创建 `.gitignore` 文件，写入：

```gitignore
# 本地日志
*.log

# 构建输出目录
build/

# macOS 文件管理器元数据
.DS_Store
```

规则含义：

- 以 `#` 开头的是注释；
- `*.log` 匹配以 `.log` 结尾的文件；
- `build/` 匹配名为 `build` 的目录及其内容；
- `.DS_Store` 匹配这个确切文件名。

保存后创建一个 `debug.log`，再运行：

```bash
git status
```

状态应显示新的 `.gitignore`，但不显示 `debug.log`。

## 忽略不等于删除

`.gitignore` 只影响 Git 是否把未跟踪路径报告为候选内容。它不会删除磁盘文件，也不是访问控制或加密机制。

更重要的是：忽略规则不会让已经被跟踪的文件自动退出历史。如果一个日志文件已经提交，后来把 `*.log` 加入规则，它仍会继续显示变化。

## 检查某个文件为什么被忽略

```bash
git check-ignore -v debug.log
```

`git check-ignore` 用于检查忽略规则；`-v` 会同时显示命中的规则来源和行号。成功匹配时输出类似：

```text
.gitignore:2:*.log debug.log
```

没有输出通常表示当前没有规则忽略它。

## 已跟踪文件怎样停止跟踪

假设 `local.env` 已经被提交，现在希望保留本地文件，但以后不再跟踪。仅在确认团队确实不应版本化该文件后执行：

```bash
git rm --cached local.env
```

`git rm` 通常表示从工作区和暂存区移除路径；`--cached` 把作用限制在 Git 准备的版本中，因此本地文件保留。随后需要把 `local.env` 加入 `.gitignore`，审查差异并提交这次删除记录。

这不会从旧提交中擦除秘密。如果文件曾包含真实凭据，应立即轮换凭据，再按专门的历史清理流程处理。

## 哪些文件通常应该提交

不要把“配置文件”一律忽略。团队共享的构建配置、数据库迁移、示例环境文件和锁定依赖版本的文件通常需要进入仓库。真正的本地密钥可以忽略，同时提交不含秘密的模板，例如 `.env.example`。

判断问题是：其他人仅凭仓库内容，能否知道项目如何构建和配置？

## 完成本章提交

暂存并检查忽略规则：

```bash
git add .gitignore
git status
git diff --staged
git commit -m "chore: ignore local generated files"
```

提交后运行 `git status`。`debug.log` 可以继续留在本地，但不应出现在状态中。
