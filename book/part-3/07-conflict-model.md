# 冲突不是报错：理解三方合并

## Git 为什么不能总是自动决定

假设共同祖先中的标题是：

```text
使用指南
```

功能分支把它改为“快速使用指南”，`main` 把它改为“项目使用手册”。Git 能看出两边都改了同一位置，却不知道哪个名称符合产品意图，也不知道是否应该组合成第三种写法。

这时 Git 停止自动合并，把决定交给人。**合并冲突**是一次尚未完成的合并状态，不是仓库损坏，也不是某位开发者一定做错了。

## 三方合并的三个输入

Git 比较：

1. 两条分支的共同祖先；
2. 当前分支的最新提交；
3. 要合入分支的最新提交。

```text
共同祖先 C
  ├── 当前一侧 V
  └── 合入一侧 N
```

它不是只比较 V 与 N 的最终文本。共同祖先让 Git 能判断某行是只有一边修改、两边以相同方式修改，还是两边以不同方式修改。

## ours 与 theirs 只描述合并视角

在普通 `git merge feature/title` 中：

- ours 是当前分支，也就是接收合并的一侧；
- theirs 是命令参数指定的 `feature/title`。

这些词不是“我的代码”和“同事的代码”。同一个人可以创建两边提交，而且在变基等其他操作中视角还会变化。处理冲突时优先使用分支名和业务意图，少用容易误导的人称。

## 冲突标记

发生内容冲突后，工作区文件会插入三种标记。完整片段依次是：`<<<<<<< HEAD`、当前分支内容、`=======`、合入分支内容、`>>>>>>> feature/title`。

标记含义：

- `<<<<<<< HEAD` 到 `=======` 是当前分支内容；
- `=======` 到 `>>>>>>> feature/title` 是合入分支内容；
- 标记本身不是最终文档内容，解决时必须删除。

不要机械选择上半段或下半段。正确结果可能保留一边、组合两边，或者写成双方都没有出现的新内容。

## 不只内容会冲突

常见冲突还包括：

- 一边修改文件，另一边删除；
- 两边把同一文件重命名到不同位置；
- 两边新增同名但内容不同的文件；
- 文件类型或权限变化无法直接组合。

`git status` 会用相应描述列出未解决路径。不同冲突需要不同业务决定，但处理闭环相同：理解两侧意图，形成最终文件，标记已解决，完成合并，验证结果。

## 解决冲突不是“让 Git 不报红”

删除标记并不等于解决正确。至少需要回答：

1. 共同祖先原本是什么？
2. 当前分支为什么修改？
3. 合入分支为什么修改？
4. 最终行为应同时满足哪些约束？
5. 用什么测试证明结果？
