# 远程仓库到底远在哪里

第三篇所有分支、合并和标签都发生在一个本地仓库中。团队协作还需要在仓库之间交换提交和引用。

## 远程仓库只是另一个仓库

本书把**远程仓库**定义为：当前仓库通过路径或网络地址访问、用于交换对象和引用的另一个 Git 仓库。

它可以位于 GitHub、GitLab 或公司服务器，也可以只是同一台电脑上的另一个目录。“远程”描述的是当前仓库与另一个仓库的关系，不保证它一定跨越互联网。

Git 在技术上没有强制指定哪一份仓库最权威。团队通常把某个平台仓库约定为评审、持续集成和发布入口，这属于协作规则。

## 必须区分的三层状态

远程协作最容易混淆三个位置：

```text
远程服务器上的 main
          |
          | 通过网络获取
          v
本地记录的 origin/main
          |
          | 由你决定怎样整合
          v
本地工作的 main
```

### 服务器上的分支

它是另一个仓库中的真实引用。除非执行网络操作，本地无法保证知道它此刻的位置。

### 本地远程跟踪分支

`origin/main` 是本地保存的引用，记录上一次成功通信时，名为 `origin` 的远程仓库中 `main` 位于哪里。它是快照，不是实时网络指针。

### 本地分支

`main` 是你可以切换、提交和合并的本地分支。获取远程更新不会必然移动它。

## 四个动作各自负责什么

- `clone`：第一次复制仓库并建立远程关系；
- `fetch`：只把远程新增对象和引用信息取到本地；
- `pull`：先获取，再把远程历史整合进当前分支；
- `push`：把本地对象和引用更新请求发送到远程。

后面会逐个引入。先建立边界：获取、整合和发布是不同动作。

## 登录平台与 Git 历史是两层问题

仓库地址决定连接目标，凭据决定你有没有读取或写入权限。提交中的 `user.name`、`user.email` 只是历史身份，不是登录账号。修改作者邮箱不会让推送获得权限，登录成功也不会自动改变提交作者。

## 小结

远程协作不是两台电脑上的目录自动保持一致，而是多个完整仓库显式交换对象和引用。下一章从第一次复制开始。
