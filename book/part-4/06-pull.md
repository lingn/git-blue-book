# git pull 实际组合了哪两步

## pull 不是单一同步动作

在当前分支执行：

```bash
git pull
```

通常等价于两个阶段：

1. 从配置的上游远程执行获取；
2. 把取得的上游历史整合进当前分支。

第一阶段类似 `fetch`，第二阶段根据配置使用合并或变基。正因为它组合了网络获取和历史整合，出现问题时只说“pull 失败”信息不够，需要判断失败发生在哪一阶段。

## 为什么初学时更适合拆开

```bash
git fetch origin
git log --oneline --graph --decorate --all
git merge origin/main
```

这三步让你先看到远程跟踪分支怎样变化，再明确把什么合入当前分支。等模型稳定后，`pull` 才是方便的缩写。

## 只接受快进

如果团队要求本地分支不自动生成合并提交：

```bash
git pull --ff-only
```

能直接快进时完成更新，存在分叉时拒绝。拒绝保留双方历史，让你先检查再选择方案。

可以为当前用户设置默认策略：

```bash
git config --global pull.ff only
```

这是个人策略设置，修改前先确认团队流程。它不适合替代对合并和变基的理解。

## 通过变基整合

你也会看到：

```bash
git pull --rebase
```

它在获取后变基本地提交，会重新生成提交。第十、十一章解释变基模型与风险；在那之前不要把它设为全局默认。

## 工作区不干净时

`pull` 可能因为本地修改会被覆盖而拒绝，也可能在某些配置下临时收纳修改。安全做法是先：

```bash
git status
git diff
```

让当前工作形成可靠提交或采用明确的临时保存方案，再整合远程变化。不要用 `reset --hard` 为拉取“清路”。

## 冲突发生在哪

获取本身只是下载对象，普通内容冲突发生在第二阶段的合并或变基。解决方法取决于所用整合方式。合并冲突可沿用第三篇流程；变基冲突要等理解提交重建后处理。

## 小结

`pull = fetch + integrate`。知道组合关系后，你可以在需要控制和排障时拆开执行，在关系清晰时使用快捷形式。
