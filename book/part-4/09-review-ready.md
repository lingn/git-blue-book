# 代码评审前整理什么

提交代码评审之前，目标不是让历史看起来绝对线性，而是让评审者能够看懂意图、检查变化并复现验证。

## 第一层：工作区是否完整

```bash
git status
git diff
git diff --staged
```

确认没有遗漏文件、调试代码、凭据或与本任务无关的变化。未跟踪文件也要逐项判断，不要只关注已修改文件。

## 第二层：分支准备提交什么

先获取主线最新记录：

```bash
git fetch origin
```

查看功能分支独有提交：

```bash
git log --oneline origin/main..HEAD
```

查看从双方共同起点以来，功能分支最终引入的文件差异：

```bash
git diff origin/main...HEAD
```

这里三点范围 `A...B` 在 `diff` 中表示：从 A 与 B 的共同祖先比较到 B。它适合回答“这个功能分支相对分叉起点最终改变了什么”。不要与上一章 `log A..B` 的两点范围混为一谈。

只看统计：

```bash
git diff --stat origin/main...HEAD
```

## 第三层：提交是否可审查

逐条检查：

- 一条提交是否表达一个明确意图；
- 提交说明是否解释目的；
- 是否混入纯格式化、生成物或无关重构；
- 每条提交是否至少处于可构建、可理解状态；
- 是否包含之后又完全撤销的试验噪音。

不是每条提交都必须只改一个文件，也不是提交越少越好。评审边界应跟随可独立理解和验证的意图。

## 第四层：验证结果

运行仓库规定的测试、构建、静态检查和格式检查。记录实际命令与结果，不要只写“本地验证通过”。

如果改动影响部署范围，还应说明受影响组件、配置变化、迁移顺序和回滚方式。Git 提交正确不等于运行部署安全。

## 不要为了整洁擅自改写共享分支

整理自己尚未分享的功能分支风险较低。已经有同事基于其工作的分支，改写提交会迫使他们处理不同历史。先确认分支所有权和团队规则。
