# 变基的本质：重新生成提交

## 为什么需要另一种整合方式

功能分支从 A 分出 F1、F2，同时主线增加 M：

```text
      F1 <- F2  feature
     /
A <- B <- M     main
```

合并会创建一个汇合提交。变基选择另一种表达：把功能分支的变化依次重新应用到 M 之后。

```text
A <- B <- M <- F1' <- F2'  feature
```

## “移动提交”只是表面说法

提交不可原地修改。F1' 和 F2' 有新的父提交，因此是新提交，也有新的 ID。原来的 F1、F2 不会被修改；只是功能分支改为指向新历史后，旧节点不再从该分支可达。

本书把**变基**定义为：选取一段提交所表达的变化，以新的起点和父关系重新应用，生成一段新提交历史。

## 变基改变什么，不改变什么

通常希望最终文件内容与合并方案相同，但历史形状不同：

- 提交 ID 改变；
- 父提交关系改变；
- 作者信息通常保留，提交者和提交时间可能变化；
- 冲突可能在逐个重放提交时多次出现；
- 原始分支的已有标签或其他引用不会自动跟随新提交。

## 黄金边界：是否已经共享

尚未推送、只有自己使用的功能提交，可以较安全地变基整理。已经推送并被同事拉取的提交，变基后会形成一套长得相似但 ID 不同的历史。

因此规则不是“永远不要变基公开分支”，而是：不要在没有协调的情况下改写别人已经依赖的历史。团队明确规定个人评审分支允许改写时，也要使用安全推送并通知评审者。

## 变基不是压缩提交的同义词

普通变基主要更换起点。交互式变基还能重排、合并、拆分或修改提交，但那是额外能力。第五篇在“修改多个本地提交”场景中再介绍，避免一次引入过多操作。

## 小结

合并保留两条已有历史并创建汇合点；变基根据原变化生成一条新历史。选择取决于共享边界和团队期望，不是简单的“干净历史优于真实历史”。
