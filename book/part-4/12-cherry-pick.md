# 只迁移需要的提交：git cherry-pick

## 场景：只需要一个修复

某个修复提交已经存在于 `develop`，发布分支只需要这个修复，不希望合并 `develop` 上其他未完成内容。

`git cherry-pick <提交>` 会读取指定提交引入的变化，并在当前分支上创建一条新提交。

## 工作模型

```text
develop: A <- B <- F

release: A <- R
```

在 `release` 上挑选 F 后：

```text
release: A <- R <- F'
```

F' 的变化来源于 F，但父提交不同，因此 ID 不同。`cherry-pick` 不是移动提交，也不会自动建立两个分支之后的同步关系。

## 安全操作顺序

先取得来源提交并核对：

```bash
git fetch origin
git show <修复提交ID>
```

切换到接收变化的目标分支：

```bash
git switch release/1.x
git status
```

确认分支和工作区后执行：

```bash
git cherry-pick <修复提交ID>
```

请替换占位符。成功后检查新提交、差异和测试。

## 冲突与恢复

如果目标分支上下文不同，可能冲突。处理流程：

```bash
git status
```

编辑并验证最终文件，然后：

```bash
git add <已解决文件>
git cherry-pick --continue
```

取消整次挑选：

```bash
git cherry-pick --abort
```

与合并一样，冲突解决要说明来源提交意图、目标分支现状和最终行为。

## 避免重复挑选

如果以后又把包含 F 的完整 `develop` 合入发布分支，Git 可能识别相同补丁，也可能因周边变化产生冲突。提交图中会同时存在 F 与 F'。在发布记录中写明修复来源，有助于后续判断。

## 适用与不适用

适合：向维护分支迁移独立修复、恢复误落在错误分支的单个提交、选择少量明确变化。

不适合：长期用大量挑选代替正常分支整合，或在不了解依赖时只挑最后一条提交。一个修复可能依赖之前的重构、配置或数据库变化。

## 小结

`cherry-pick` 复制的是提交表达的变化，并在当前上下文生成新提交。执行前检查依赖，执行后验证目标分支的完整行为。
