# 远程 URL、传输协议与认证边界

`clone`、`fetch` 和 `push` 都会与另一个仓库交换对象或引用，但“Git 在交换什么”和“连接怎样得到保护”是两组问题。把它们混在一起，常会出现三类误判：把协议版本当作加密方式，把提交作者当作登录身份，以及用改写历史解决网络或权限故障。

进入本章前，读者应已理解远程名称、远程跟踪引用和 fetch/push 的状态变化。本章完成后，应能选择 SSH、HTTPS 或本地传输，区分服务器身份、客户端认证、仓库授权和提交身份，并能按证据把连接故障分流到 DNS、代理、主机校验、TLS、凭据、权限或引用策略。

本章以 Git 2.49.0 的本地验证结果和 Git 官方手册为事实基线。SSH 服务、HTTPS 证书、令牌种类和平台权限属于部署环境；配置时必须再核对所用服务的当前文档。

## 一次远程操作经过哪些层

以 `git fetch origin` 为例，客户端至少经过下面几层：

```text
fetch：我要读取远端对象和引用
  |
remote/refspec：连接哪个地址，要更新哪些本地引用
  |
URL 与传输：本地文件、SSH、HTTPS 或 git://
  |
Git wire protocol：能力声明、引用发现、对象协商与传输
  |
服务端控制面：认证、仓库授权、受保护引用、审计与限流
```

这些层可能在同一条命令中连续发生，却不能互相替代。HTTPS 可以完成 TLS 握手，但令牌没有仓库权限；SSH 可以验证主机密钥，但服务端找不到 URL 指向的仓库；认证与授权都成功后，push 仍可能因非快进更新或保护规则被拒绝。

排障时先问“失败发生在哪一层”，比不断更换 Git 命令更有效。

## URL 选择的是连接方式和仓库位置

同一个仓库可能提供多个 URL。远程名称 `origin` 只是本地别名，真正影响连接的是它当前保存的 URL。

| 形式 | 连接与保护边界 | 典型用途 |
| --- | --- | --- |
| `/srv/git/project.git` 或 `file:///srv/git/project.git` | 通过本机文件系统访问；依赖操作系统文件权限，没有网络主机认证 | 同机实验、备份或受控共享存储 |
| `ssh://git@host.example/team/project.git` | SSH 加密传输并校验服务器主机密钥；通常用密钥认证客户端 | 工程师交互式读写、受控自动化 |
| `git@host.example:team/project.git` | SSH 的类 scp 写法；冒号后是远端路径，不是本地 Windows 盘符 | 与上一项相同，但 URL 解析规则不同 |
| `https://host.example/team/project.git` | TLS 保护 HTTP 连接；常由令牌、OAuth 凭据或客户端证书认证 | 桌面客户端、企业代理环境、CI |
| `git://host.example/project.git` | Git 原生传输；协议本身不提供加密和身份认证 | 只应出现在明确评估过风险的环境 |

`git://` 能否写入还取决于服务端配置，不能把“常见为只读”当成安全保证。即使只读取，未认证、未加密的连接也可能被篡改或观察。公网和不受信任网络应优先使用正确校验的 SSH 或 HTTPS。

本地路径和 `file://` 也不是“天然可信”。它们绕过网络认证，把边界移到了本机账号、目录权限、挂载点和来源仓库的可信度上。本书用它们建立隔离实验，是为了验证 Git 的对象与引用行为，不是模拟托管平台。

### 先确认客户端实际配置

下面的命令在已经配置远程的本地仓库中执行，只读取配置：

```bash
git remote -v
git remote get-url --all origin
git config --show-origin --get-regexp '^remote\..*\.(url|pushurl)$'
```

第一条列出 fetch 与 push 地址，第二条列出 `origin` 的所有获取地址，第三条同时显示配置来自哪个文件。预期看到远程名和 URL；具体路径因仓库而异。这些命令不连接网络，也不改变对象、引用、index 或工作区。

如果命令没有输出，先检查远程名是否写错；`git remote` 会列出本仓库已有名称。URL 中若已经嵌入用户名或秘密，不要把完整输出粘贴到工单。应先撤销泄漏的凭据，再把 URL 改成不含秘密的形式。

仓库还可能使用 `url.<base>.insteadOf` 重写 URL，或为 push 单独配置 `pushurl`。因此“页面上复制的地址”“`.git/config` 中保存的值”和 Git 最终使用的地址可能不同。诊断异常目标时同时检查来源：

```bash
git config --show-origin --get-regexp '^url\..*\.(insteadOf|pushInsteadOf)$'
git remote get-url --all --push origin
```

全局 URL 重写会影响多个仓库。修改前要先找出配置来源和受影响范围，不要在一个仓库出错时盲目删除用户级配置。

## Git protocol v2 不是 HTTPS 2，也不是安全协议

Git wire protocol 负责引用发现、能力协商和对象传输。protocol v2 改进了这套应用层交互，尤其减少了某些引用通告和后续扩展的成本。它可以承载在不同传输之上，名字中的“v2”不表示 HTTPS，也不自动带来 TLS、SSH 加密、客户端认证或仓库授权。

安全属性应从承载方式判断：SSH 看主机密钥、加密算法和客户端密钥；HTTPS 看证书链、主机名、TLS 与凭据；本地文件访问看操作系统权限。服务器是否支持 protocol v2 是另一个独立问题。

协议版本通常不需要日常用户手工固定。企业代理、老旧服务器或自定义网关出现兼容问题时，应记录客户端 Git 版本、URL 形式、服务端产品与原始错误，再按 Git 官方 `gitprotocol-v2` 和服务端文档核对。不要用关闭证书校验来“验证是不是协议版本问题”。

## 四种身份不能混为一个账号

一次远程操作至少要区分四类身份或证明。

| 层次 | 回答的问题 | 常见机制 | 不能证明什么 |
| --- | --- | --- | --- |
| 服务器身份 | 我连接的是预期主机吗 | SSH `known_hosts`、HTTPS 证书链与主机名校验 | 当前用户是否有仓库权限 |
| 客户端认证 | 服务端认为请求者是谁 | SSH 公钥、令牌、OAuth、客户端证书 | 该身份能否读取或写入目标仓库 |
| 授权 | 这个身份能对哪个仓库和引用做什么 | 仓库角色、部署密钥范围、分支规则、服务端 hooks | 提交内容是谁编写的 |
| 历史身份 | 提交记录声称作者和提交者是谁 | `user.name`、`user.email`、commit/tag 签名 | 推送者身份、代码正确性或运行安全性 |

修改 `user.email` 不会修复 403 或 `Permission denied (publickey)`。反过来，用高权限机器人推送也不会自动把已有提交的作者改成机器人。签名能把某个密钥控制者与特定 Git 对象关联起来，但仍不能代替仓库授权、代码评审和制品验证。

审计共享历史时，至少分别保留推送者、被更新引用、旧/新对象 ID、提交作者/提交者和签名验证结果。只看提交页面上的头像，无法还原完整身份链。

## SSH：先验证服务器，再证明客户端身份

SSH URL 常把一个受限服务账号写在 URL 中，例如 `git@host.example`。多个工程师可以使用相同 SSH 用户名，但服务端根据不同公钥映射到不同平台身份；不要据此推断大家共享同一个系统账户。

### 主机密钥是第一道边界

首次连接新主机时，SSH 可能展示主机密钥指纹并询问是否继续。这个提示只说明本机尚未信任该主机。应通过平台官方文档、管理员公告或另一条可信渠道取得预期指纹，逐字比较后再接受。`ssh-keyscan` 只能获取当前网络端点提供的密钥，不能独立证明端点身份，不能代替指纹核对。

如果出现 `REMOTE HOST IDENTIFICATION HAS CHANGED`，先停止连接。它可能来自主机密钥计划轮换、DNS/负载均衡变更，也可能表示中间人攻击。保留错误中的主机、端口、密钥类型和指纹，向服务所有者核对。只有确认新旧指纹和变更窗口后，才应更新 `known_hosts` 中对应记录；不要删除整个文件或全局关闭严格校验。

查看本机是否已有某个主机的记录时，可以在任意目录运行：

```bash
git_host=host.example
ssh-keygen -F "$git_host"
```

把 `host.example` 改为真实主机名。命令只读取默认 `known_hosts`，输出会随是否使用散列主机名、非默认端口和 SSH 配置而变化；无输出不等于主机一定不可信，还要检查 `ssh -G "$git_host"` 得到的 `userknownhostsfile` 和端口。不要把包含内部主机名的完整记录公开。

### 私钥、agent 和平台登记各有状态

SSH 公钥可以登记到服务端，私钥应只保存在受控客户端或硬件设备中。`ssh-agent` 代替进程直接反复读取私钥，并不把密钥“上传到 Git”。在本机任意目录查看当前 agent 已加载身份：

```bash
ssh-add -l
```

预期输出一行或多行密钥长度、指纹和注释；没有已加载身份时通常返回非零并说明 agent 中没有身份。若提示无法连接 agent，问题在本地会话或 agent 配置，还没有到 Git 服务器。加载密钥时先把受控路径赋给变量：

```bash
key_file=/absolute/path/to/id_ed25519
ssh-add "$key_file"
```

这会让当前 agent 持有该私钥的可用身份，不修改仓库，也不授予服务端权限。文件不存在、权限过宽、口令错误或 agent 不可用都会失败。恢复方式是修正本地密钥或 agent 状态；不要重新生成密钥覆盖仍在使用的私钥。`ssh-add -d "$key_file"` 可从当前 agent 移除指定身份，但不会删除磁盘文件或服务端公钥。

转发 agent 会把签名能力暴露给远端会话。除非跳板链路和威胁模型确实需要，不要把 agent forwarding 当成通用 Git 配置；CI 更适合短期、单仓库、最小权限凭据。

### 用 Git 操作验证最终路径

某些托管服务没有交互式 shell，`ssh -T` 即使认证成功也可能返回非零或平台自定义消息。判断 Git 读取链路时，在目标仓库中执行更贴近真实动作的只读命令：

```bash
git ls-remote origin
```

它连接 `origin` 并列出远端公开给当前身份的引用，不下载对象、不更新远程跟踪引用，也不改变工作区。非空仓库通常输出由对象 ID 和引用名组成的多行文本；空仓库可以成功且没有引用输出，因此还要检查退出状态。

如果失败，保留原始标准错误。`Host key verification failed` 指向服务器身份校验；`Permission denied (publickey)` 指向客户端密钥选择或服务端登记；认证看似成功后出现仓库不存在，则应检查仓库路径和授权。服务端为了隐藏私有仓库是否存在，可能把“无权限”也表示为 not found，不能只凭一句文案定性。

## HTTPS：TLS 和凭据是两次不同校验

HTTPS 首先用 TLS 校验证书链和 URL 主机名，并保护传输内容；随后 HTTP 服务再决定是否需要客户端凭据。证书有效只证明连接到了持有相应私钥、且证书满足本机信任策略的端点，不证明当前令牌有仓库权限。

企业代理可能终止并重新建立 TLS。这不是把 `http.sslVerify=false` 设为全局值的理由。正确做法是确认代理受组织授权，把企业 CA 纳入受控信任链，或为明确的服务配置 CA 文件，并保留变更范围与所有者。例如，在已经取得可信 CA 文件后，可由管理员按环境决定是否配置：

```bash
ca_file=/absolute/path/to/enterprise-ca.pem
git config --global http.sslCAInfo "$ca_file"
```

这会改变当前用户所有 Git HTTPS 请求的 CA 来源，影响范围很大。执行前应验证文件来源、权限和轮换流程。若只为某个主机配置，应使用 Git 配置的 URL 匹配作用域并按当前 `git-config` 文档验证结果。回退前先运行 `git config --show-origin --get-all http.sslCAInfo` 确认值来自何处，再用同一作用域删除自己添加的值；不要覆盖组织管理的系统配置。

`http.sslVerify=false` 会取消关键服务器身份校验，把“现在能连通”换成无法可靠判断连接对象。即使只是临时排障，也可能让凭据发送给错误端点。本书不把它作为修复步骤。

## 凭据助手负责取用秘密，不负责发放权限

HTTPS 令牌不应嵌入远程 URL。带秘密的 URL 可能进入 `.git/config`、Shell 历史、进程参数、日志和截图。Git 的 credential 子系统会按协议、主机以及可选路径向一个或多个凭据助手查询用户名和秘密；助手可能连接系统钥匙串、桌面登录管理器、内存缓存或专用身份代理。

在任意目录查看已配置助手及其来源：

```bash
git config --show-origin --get-all credential.helper
git config --show-origin --get-regexp '^credential\..*'
```

这些命令只读配置，不会显示助手保存的密码本身，但输出可能暴露内部主机、用户名和助手路径，分享前仍要脱敏。无输出表示当前 Git 配置没有声明助手，不代表操作系统、IDE 或环境变量一定没有另外注入凭据。

Git 会依次询问已配置助手。助手返回的用户名与密码字段足以组成完整凭据时，后续助手不再需要补全；认证成功后 Git 可以通知助手保存，失败后可以通知它删除匹配记录。`git credential fill` 会把取得的秘密写到标准输出，只适合隔离实验和实现助手时诊断，不能对真实账号随手执行并粘贴结果。

本书实验使用 `credential-store` 和虚构令牌，是因为它的明文文件便于断言 approve/fill/reject 协议。它不代表生产建议。真实环境应优先选择所用操作系统或组织认可、能加密保存并支持撤销的助手。

### `credential.useHttpPath` 决定同一主机怎样复用凭据

默认情况下，Git 在匹配 HTTP 凭据时可能不把 URL 路径作为边界，于是同一主机下多个仓库可能复用一条凭据。这对单账号服务方便，但在同一主机使用多个身份、多个租户或不同权限令牌时，可能把错误凭据发送给另一个仓库路径。

启用路径匹配：

```bash
git config --global credential.useHttpPath true
```

这会影响当前用户访问的所有 HTTP(S) Git URL；凭据助手将按仓库路径区分记录，用户也可能因此需要为多个仓库分别登录。执行前查看现有助手和多账号需求。验证时应使用专用测试凭据，不要运行会打印真实秘密的 `credential fill`。若决定回退自己添加的全局值，可以先确认来源，再执行：

```bash
git config --global --unset credential.useHttpPath
```

如果该值来自系统配置、条件包含文件或组织策略，不要用用户级命令假装已删除原配置。`--show-origin` 才能说明最终值来自哪里。

### CI 不应继承开发者的长期凭据

CI 作业没有安全的交互式提示，应使用短期、最小权限、绑定仓库或环境的机器身份。读取源码的作业不应自动拥有向受保护分支写入、创建发布或读取所有组织仓库的权限。凭据只在需要的步骤注入，日志必须掩码，工作目录、缓存和制品中不得留下 URL 或助手存储文件。

`GIT_TERMINAL_PROMPT=0` 可以让非交互作业在缺少凭据时立即失败，但它不是认证机制。作业仍需显式配置可信 CA、服务器身份和凭据来源。来自派生仓库或不受信任分支的代码尤其不能默认接触发布凭据，因为构建脚本本身可以读取环境和 Git 配置。

## 安全迁移一个远程 URL

下面是一份真实仓库的操作手册，不是本书自动实验。使用前应取得新 URL 的可信来源、确认账号至少有读取权限，并选择没有进行中 merge/rebase 的本地仓库。修改远程 URL 不要求工作区干净，但先记录状态有助于证明它没有改变文件或历史。

在目标仓库中先赋值；示例主机不可连接，必须替换为实际地址：

```bash
remote_name=origin
new_url=ssh://git@host.example/team/repository.git

git status --short --branch
old_url="$(git remote get-url "$remote_name")"
git remote set-url "$remote_name" "$new_url"
git remote get-url --all "$remote_name"
git ls-remote "$remote_name"
```

`set-url` 只修改本地仓库配置，不移动对象、分支、index 或工作区。`ls-remote` 发起只读连接；成功的非空仓库通常输出可变的对象 ID 和引用名，不能拿书中的固定哈希比较。空仓库可以没有输出，应以退出状态和服务端审计为准。

失败可能发生在 URL 解析、DNS、代理、SSH/TLS 校验、认证、仓库路径或读取授权。迁移验证失败时，不要继续 push。只要 Shell 会话仍保留 `old_url`，可以恢复：

```bash
git remote set-url "$remote_name" "$old_url"
git remote get-url --all "$remote_name"
```

恢复只撤销 URL 配置，不会撤销服务端凭据登记、CA 或 SSH 配置变更。关闭终端前若需要留存旧地址，应存入受控记录；URL 可能含内部路径，不要写进公开日志。读取成功也不证明具有写权限。验证写路径应在专用测试分支或测试仓库完成，并遵守平台保护规则，不能用向主线试推来探测权限。

## 按证据分流连接失败

Git 和不同 libcurl、SSH、代理、平台组合的文案不完全相同，下面的字符串只是常见线索，不是逐字匹配规则。

| 观察到的阶段或线索 | 优先检查 | 不应采取的动作 |
| --- | --- | --- |
| `Could not resolve host` | URL 主机名、DNS、VPN 和 split DNS | 重写提交或重置分支 |
| 连接超时、无法连接代理 | TCP 路由、代理地址、防火墙和服务状态 | 反复生成令牌 |
| `Host key verification failed` 或主机密钥变化 | `known_hosts`、实际端口、可信指纹和轮换公告 | 删除整个 `known_hosts` |
| TLS 证书链或主机名错误 | 系统时间、URL、企业 CA、代理终止和证书轮换 | 设置 `sslVerify=false` |
| `Permission denied (publickey)` | SSH 实际选择的用户、密钥、agent 与服务端登记 | 修改 `user.name` |
| HTTP 401 或反复要求登录 | 令牌有效期、助手中的旧记录、认证方式 | 把令牌写进 URL |
| HTTP 403、repository not found | 仓库路径、身份授权、SSO/策略要求；注意服务可能隐藏仓库存在性 | 仅凭文案断定仓库已删除 |
| non-fast-forward、hook declined、protected branch | 远端引用新旧值、服务端规则和审计事件 | 更换 SSH key 或直接强推 |

一个稳妥的最小诊断顺序是：

1. 用 `git remote get-url --all origin` 确认目标和传输方式；
2. 记录 `git --version`、操作系统、发生时间和完整退出状态；
3. 用 `git ls-remote origin` 测试只读路径，不先修改本地历史；
4. 分别核对服务器身份、客户端凭据和仓库授权；
5. 只有读路径成功后，才按专用分支和平台策略验证写路径；
6. 若 push 已到服务端但被拒绝，转向引用关系和控制面，不再把它当连接故障。

详细 trace 可能包含内部 URL、代理信息、用户名、引用、HTTP 头甚至由外部助手输出的秘密。只在受控终端采集所需最小范围，分享前人工检查和脱敏。不要为了获得“更多日志”把真实令牌写入命令行。

## 凭据泄漏时，先让秘密失效

令牌、密码或私钥一旦进入 Git 配置、日志、提交或制品，首要动作是从身份提供方撤销或轮换，而不是先重写历史。历史清理需要时间，也无法收回已经被克隆、缓存、索引或复制的秘密。

处理顺序通常是：

1. 记录发现时间、秘密类型、权限范围和可能接触的仓库；
2. 撤销或轮换凭据，暂停仍会继续使用旧秘密的自动化；
3. 从远程 URL、凭据助手、CI 变量、缓存和制品中删除旧值；
4. 检查身份与平台审计日志，确认泄漏窗口内的读取和写入；
5. 若秘密进入提交，制定覆盖所有引用、派生仓库、镜像和 LFS 的历史清理方案；
6. 通知协作者重新同步，并验证旧凭据确实不能再使用。

如果泄漏的是 SSH 私钥，应撤销服务端登记的公钥或证书，并检查该密钥是否在多个服务复用。删除本地私钥文件本身不能阻止已复制的副本继续认证。若泄漏的是提交签名私钥，还要处理签名信任和受影响对象，不能只换 Git 传输凭据。

## 隔离实验验证了什么

在本书仓库根目录运行：

```bash
./scripts/verify-remote-transport-auth.sh
```

前置条件是 Bash、Git 2.28 或更高版本以及可写临时目录。脚本使用 `mktemp` 创建实验目录，并通过 `trap` 清理；它不会读取用户级 Git 配置，不连接网络，也不修改蓝皮书仓库。

实验分为两段：第一段用 `file://` 裸仓库完成 clone、fetch 和 push，并断言 fetch 只更新 Bob 的 `origin/main`，不会移动 Bob 的本地 `main`；第二段把 Git 全局配置重定向到临时文件，使用虚构主机 `git.example.invalid`、虚构用户和虚构令牌验证凭据助手的 approve、fill、路径隔离与 reject。

成功时最后输出：

```text
File transport and isolated credential-helper experiments passed.
```

提交 ID 和临时路径每次都会变化，脚本通过读取 Git 状态断言，不匹配玩具哈希。任何断言失败都会返回非零；`trap` 仍会删除临时目录。需要调查失败时，可复制脚本并暂时调整清理逻辑，但只能在无真实凭据的隔离目录中进行。

这个实验不能证明 SSH 主机密钥正确、HTTPS TLS 有效、真实令牌可用、平台具备某种权限，也不能模拟分支保护或 CI。验证这些能力必须在专用测试仓库中记录平台、版本、账号角色、规则和真实服务端证据。

## 小结

远程协作的核心边界可以收束为三句话：URL 选择传输和仓库位置，Git wire protocol 交换对象与引用，服务端控制面决定身份和权限。SSH、HTTPS 和本地文件访问各自提供不同安全属性，protocol v2 不能替代它们。

遇到失败时，先确定服务器身份，再检查客户端认证和仓库授权，最后才判断引用更新策略。凭据泄漏则先撤销秘密，再处理配置、历史和审计。这样才能避免用历史命令修复连接问题，也避免用关闭校验换取表面连通。
