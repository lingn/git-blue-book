# 先别急着撤销：用状态矩阵判断位置

“我想回滚代码”不是一个足够明确的问题。至少要先回答：变化在哪里，它是否已经成为提交，这段提交是否已经分享给别人？

## 第一步：保护现场

事故发生后先停止继续提交、拉取、变基和清理。运行只读命令：

```bash
git status
git diff
git diff --staged
git log --oneline --graph --decorate -10
```

记录当前分支名和关键提交 ID。涉及远程时再执行 `git fetch`，但要知道它会更新本地远程跟踪引用；在准备带租约强推时，这个变化尤其重要。

如果项目目录中有 Git 从未跟踪的重要文件，先用普通文件备份保护它。Git 无法恢复自己从未记录过的内容。

## 第二步：判断变化所在区域

| 现场 | 目标 | 首选工具 | 是否改写提交历史 |
| --- | --- | --- | --- |
| 已跟踪文件只在工作区修改 | 丢弃未暂存修改 | `git restore` | 否 |
| 修改已经暂存 | 取消暂存并保留文件 | `git restore --staged` | 否 |
| 最近本地提交缺文件或说明错误 | 替换最近提交 | `git commit --amend` | 是 |
| 多条未分享提交需要改说明或顺序 | 重建提交序列 | `git rebase -i` | 是 |
| 错误提交已经分享 | 创建反向变化提交 | `git revert` | 否 |
| 本地分支误移动或删除 | 找到旧位置并新建引用 | `git reflog` + `git branch` | 通常否 |
| 必须重写个人远程分支 | 有条件地更新远程引用 | `--force-with-lease` | 是 |

这张表给出默认方向，不替代现场检查。例如错误提交虽然已经推送，但如果从未被任何人获取且团队明确允许改写，也可能采用另一策略；这个例外需要协调，而不是个人猜测。

## 第三步：判断是否正在进行某个操作

`git status` 可能说明正在合并、变基、挑选或回滚。此时不要混用其他恢复命令。优先使用当前操作对应的：

- `git merge --abort`
- `git rebase --abort`
- `git cherry-pick --abort`
- `git revert --abort`

中止会尝试回到操作开始前。若此前工作区本来就不干净，恢复边界可能复杂，所以高风险操作前必须先确认状态。

## 两个最容易混淆的词

本书约定：

- **改写历史**：用新提交替换原有提交关系，使原提交 ID 不再位于当前分支；
- **回滚变化**：创建新提交抵消旧提交效果，同时保留旧历史。

`amend`、变基、`reset` 可能改写历史；`revert` 通常回滚变化而不改写已有提交。

## 小结

先定位区域，再判断共享边界，最后选择工具。下一章从影响范围最小的情况开始：丢弃已跟踪文件尚未暂存的修改。
