# 已推送提交如何回滚：git revert

## 场景：错误已经进入共享历史

提交 B 已推送到 `main`，同事可能已经获取；后续还有正确提交 C：

```text
A <- B <- C  main
```

目标是撤销 B 的效果，同时保留 C 和共享历史。此时首选不是把分支移回 A，而是创建新提交 R，记录一组与 B 相反的变化：

```text
A <- B <- C <- R  main
```

## 操作前检查

```bash
git status
git fetch origin
git log --oneline --graph --decorate -10
git show <错误提交ID>
```

确认当前分支、错误提交、后续依赖和工作区状态。回滚一个基础重构可能让后续提交失效，不能只看 B 自身差异。

## 创建反向提交

```bash
git revert <错误提交ID>
```

`git revert` 计算指定提交相对其父提交引入的变化，尝试应用反向变化，并创建新提交。它通常打开编辑器准备说明；保留原提交引用和回滚原因。

完成后：

```bash
git show --stat HEAD
git diff HEAD~1..HEAD
git status
```

运行测试，确认反向变化没有破坏 C 等后续行为，再普通推送。

## 回滚也可能冲突

如果后续提交改过同一区域，自动反向应用可能冲突。理解当前最终行为和原提交意图，编辑正确结果后：

```bash
git add <已解决文件>
git revert --continue
```

取消尚未完成的回滚：

```bash
git revert --abort
```

## 回滚一次合并

合并提交有多个父提交，Git 需要知道相对于哪一侧计算反向变化，因此会出现 `git revert -m <父编号> <合并提交>`。这还会影响未来再次合并同一分支时的判断。

不要把 `-m 1` 当作固定答案。先画出父提交、确认要保留哪条主线，并为重新合并制定计划；复杂发布事故应由熟悉历史的人共同处理。

## “回滚回滚”

如果 R 之后需要重新启用 B 的效果，可以再回滚 R。结果是新增历史，不是删除事故记录。仍需检查这段时间其他提交是否改变了上下文。

## 小结

`revert` 用新提交表达撤销，适合已经分享的历史。它保留可追溯性，但业务影响仍必须测试。
