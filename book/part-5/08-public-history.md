# 为什么已公开历史不应随意改写

## 两套看起来相同的提交不是同一套历史

Alice 已获取远程提交 B，并从它创建 C。此时 Bob 把 B amend 成 B'，强制更新远程：

```text
远程：A <- B'

Alice：A <- B <- C
```

B 与 B' 即使文件差异只相差一个字，也是不同提交。Alice 下次同步时，Git 看到的是两条分叉历史，不知道旧 B 应被自动替换。

## 公开的判断标准不是“是否在 main”

历史一旦被其他人、自动化、发布系统或代码评审引用，就可能公开。功能分支也可能是共享历史；本地主分支如果从未推送，则未必公开。

判断时问：

- 是否已经推送？
- 是否有人拉取、检出或基于它提交？
- 是否有评审评论、构建产物或发布记录引用提交 ID？
- 是否有标签指向它？

## 改写公开历史的成本

- 同事需要变基、重置或重新克隆自己的工作；
- 旧评审链接和审计记录可能指向过时提交；
- 自动化可能重复处理或无法找到原对象；
- 发布系统可能把同名分支或标签解析成不同内容；
- 冲突解决可能重复发生。

因此主分支和发布分支通常使用 `revert`，不通过重置加强推隐藏事故。

## 可以协调改写的场景

个人评审分支为了整理提交，团队可能允许变基后更新远程。前提通常是：

1. 分支所有权明确；
2. 没有人基于旧历史继续开发，或已经协调迁移；
3. 没有稳定发布标签依赖旧提交；
4. 先核对远程没有未知新提交；
5. 使用带预期值的保护推送；
6. 更新后通知评审者提交 ID 已变化。

## 不要用“还在不在文件里”判断历史安全

改写后当前文件可能完全正确，但协作者损失的是父关系和提交身份。共享历史的安全问题存在于提交图，不只存在于工作区内容。

## 小结

改写本地私有历史是在整理自己的草稿；改写公开历史是在修改团队共同坐标。下一章只讨论已经获得明确授权的例外操作。
