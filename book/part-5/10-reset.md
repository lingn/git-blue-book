# 理解 git reset 的三种模式

`reset` 经常被当作万能撤销命令，危险来自它可以同时移动分支、改写暂存区并覆盖工作区。先用三个区域推导，不背口诀。

## 操作前建立保护引用

只在练习仓库执行。先确认当前位置，并为原提交创建名字：

```bash
git status
git log --oneline -5
git branch backup/before-reset
```

假设历史是：

```text
A <- B <- C  main
```

目标提交写成 `HEAD~1`，即 B。

## soft：只移动当前分支

```bash
git reset --soft HEAD~1
```

结果：

- `main` 从 C 移到 B；
- 暂存区保持 C 的内容；
- 工作区保持 C 的内容。

C 相对 B 的变化现在全部处于已暂存状态。常用于把最近本地提交重新组合，但 `amend` 往往更明确。

## mixed：移动分支并重置暂存区

```bash
git reset --mixed HEAD~1
```

`--mixed` 是提交形式 `reset` 的默认模式。结果：

- 分支移到目标提交；
- 暂存区变成目标提交快照；
- 工作区文件保持操作前内容。

被移出提交的变化成为未暂存修改。

## hard：三层都恢复到目标

```bash
git reset --hard HEAD~1
```

结果：

- 分支移到目标提交；
- 暂存区变成目标快照；
- 工作区中已跟踪文件也变成目标快照。

未提交的已跟踪修改会被覆盖。未跟踪文件通常不会被全面清理，但当它们妨碍写入目标路径时也可能受影响。不要把 `--hard` 当作“让状态干净”的快捷键。

## 三种模式对照

| 模式 | 移动分支 | 更新暂存区 | 更新已跟踪工作区 |
| --- | --- | --- | --- |
| `--soft` | 是 | 否 | 否 |
| `--mixed` | 是 | 是 | 否 |
| `--hard` | 是 | 是 | 是 |

## 路径形式不是移动分支

你也会看到：

```bash
git reset HEAD -- README.md
```

带路径时主要更新暂存区，不移动当前分支，传统上用于取消暂存。现代 Git 更推荐意图清楚的：

```bash
git restore --staged README.md
```

不要把路径形式和提交形式混成同一个模型。

## 已推送分支的边界

在已公开分支执行 `reset` 只移动本地引用，远程历史仍在。随后普通推送通常拒绝；强制推送会改写共享历史。主分支错误提交通常应使用 `revert`。

## 如何恢复练习

因为开始前创建了保护分支，可以回到原位置：

```bash
git reset --hard backup/before-reset
```

这条恢复仍会覆盖当前未提交修改，所以只在确认实验现场后执行。下一章学习没有预先创建保护分支时怎样从引用日志找位置。
