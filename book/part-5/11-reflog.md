# 用引用日志找回“消失”的提交

## 提交可能还在，只是名字移走了

错误 `reset` 后，`git log` 从当前分支看不到原提交 C：

```text
A <- B  main
      \
       C  暂时没有普通分支名
```

Git 在本地记录引用最近怎样移动，这份记录叫引用日志，也就是 reflog。

## 查看 HEAD 的移动记录

```bash
git reflog
```

输出类似：

```text
b2b2b2b HEAD@{0}: reset: moving to HEAD~1
c3c3c3c HEAD@{1}: commit: add payment validation
```

左侧是当时的提交 ID，`HEAD@{1}` 是“HEAD 在前一次记录时的位置”。选择时同时核对操作说明、时间和提交内容，不要机械使用固定序号；每次新操作都可能让序号变化。

## 最安全的第一步：创建恢复分支

先检查候选提交：

```bash
git show --stat c3c3c3c
```

确认后给它一个新名字：

```bash
git branch recovery/payment-work c3c3c3c
```

这一步不移动当前分支、不改工作区，只让候选提交重新可达。再比较和测试，决定合并、挑选或重置。

## 查看特定引用日志

```bash
git reflog show main
```

它关注 `main` 的移动。分支删除后，对应分支日志可能不再直接可用，但 `HEAD` 日志中常保留你切换和提交的线索。

## reflog 的边界

- 它通常只存在于本地，不会随 `push` 分享；
- 另一台电脑上的操作不会自动进入你的 reflog；
- 记录会按配置过期，不是永久档案；
- 长期不可达对象可能被垃圾回收；
- 从未提交、从未写入暂存区对象的普通编辑内容通常不在 reflog 中。

所以发现丢失后应减少清理和历史操作，尽快建立恢复引用。

## reflog 与远程恢复

如果本地 reflog 找不到，但提交曾推送，其他克隆、评审页面、构建日志或远程分支可能保留 ID。先查外部证据，不要运行垃圾回收或仓库清理命令。
