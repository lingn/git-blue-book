# 定位引入问题的提交：git bisect

## 从逐条猜测到二分查找

已知旧版本 A 正常，当前版本 H 失败，中间有很多提交。逐条检出测试最坏需要检查全部历史。`git bisect` 每次选择范围中间的提交，根据“好/坏”结果排除一半候选。

## 前提：必须有可靠判定

开始前定义一个可重复问题，例如：

- 某个测试是否失败；
- 命令是否返回错误状态；
- 固定输入是否产生错误输出。

“页面感觉变慢了”无法稳定二分。先让环境、数据和判定标准可复现。

## 手工二分流程

工作区保持干净，然后：

```bash
git bisect start
git bisect bad
git bisect good <已知正常提交ID>
```

当前 `HEAD` 被标记为坏，指定旧提交标记为好。Git 检出一个中间提交。运行判定：

```bash
<项目测试命令>
```

结果正常：

```bash
git bisect good
```

结果出现问题：

```bash
git bisect bad
```

重复直到 Git 报告第一个坏提交。

## 结束后一定复位

记录候选提交并检查：

```bash
git show <候选提交ID>
git bisect reset
```

`reset` 在这里是 bisect 子命令，用于返回开始前分支，不是第五篇的 `git reset --hard`。

## 自动运行

若项目已有稳定测试命令：

```bash
git bisect run <测试命令及参数>
```

测试退出码必须符合 bisect 约定：0 表示好，1 到 127 中除 125 外表示坏，125 表示该提交无法测试。不要把会随机失败的集成测试直接交给自动二分。

## 第一个坏提交不等于最终根因

候选提交可能只是暴露旧缺陷，或依赖环境变化。查看提交上下文、相关配置和后续修复，再编写能稳定复现的回归测试。
