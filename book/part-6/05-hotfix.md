# 热修复如何在多个分支之间迁移

## 场景：修复已在开发分支，发布分支也需要

开发分支包含多个未发布功能，其中提交 F 是一个独立线上修复。发布分支只能接收 F。

先取得并审查来源：

```bash
git fetch origin
git show <修复提交ID>
```

检查 F 是否依赖之前的接口、数据库迁移、配置或共享库变化。提交看起来只改一个文件，不代表运行时依赖独立。

## 在目标分支迁移

```bash
git switch release/1.x
git pull --ff-only
git cherry-pick <修复提交ID>
```

发生冲突时，不只保留“能编译”的文本，还要对照两条分支的业务差异。完成后运行目标版本适用的测试。

记录新提交 ID，并注明来源：

```text
来源提交：<开发分支提交ID>
目标提交：<发布分支新提交ID>
差异说明：因旧版接口保留了兼容调用
验证结果：列出实际测试和请求结果
```

## 判断哪些分支已包含修复

```bash
git branch --contains <提交ID>
git branch -r --contains <提交ID>
```

第一条检查本地分支，第二条检查本地保存的远程跟踪分支。运行前先 `fetch`，并记住结果仍是本地视角。

对于 cherry-pick 生成的新提交，目标分支不包含原提交 ID，虽然可能包含等价变化。需要同时查询来源和目标 ID，或比较补丁与文件行为。

## 哪些服务需要部署

Git 只能告诉你哪些路径和提交变化，不能直接决定部署范围。需要继续追踪：

- 改动属于哪个构建模块；
- 是否改变共享 SDK、自动配置或公共依赖；
- 哪些进程实际加载了该模块；
- 是否有数据库、消息格式或配置兼容变化；
- 发布制品是否包含该提交。

如果 manager 与 worker 都依赖被修改的共享模块，两者可能都需部署；只改 manager 私有路径时才可能只发布 manager。结论必须来自依赖和运行链路，不来自提交标题。

## 是否需要优雅停机

这同样不是 Git 决定。若 worker 正处理长任务、持有租约、消费消息或写入中间状态，部署前应按系统能力停止接收新任务、等待或迁移活跃任务，再替换进程。无状态且平台具备连接排空时，也要核对健康检查和终止宽限期。

发布说明应把“代码已包含修复”和“运行实例已安全替换”分开验证。
