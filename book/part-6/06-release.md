# 发布分支、标签与回滚策略

## Git 发布节点不等于运行中的版本

分支和标签能标识源码提交，真正部署的通常是由提交构建出的制品。可靠发布需要建立可追踪链：

```text
提交 ID -> 构建任务 -> 制品 ID / 镜像摘要 -> 部署记录 -> 运行实例
```

只说“从 main 发布”不够，因为 `main` 会继续移动。发布记录应保存不可变提交 ID和制品摘要。

## 发布分支的职责

团队可能直接从主线发布，也可能建立 `release/1.x` 维护稳定版本。发布分支适合承载：

- 当前版本仍需接收的修复；
- 与下一版本不同的兼容配置；
- 发布验证期间的有限变更。

它不应成为长期堆积未合并功能的第二开发主线。分支策略越复杂，同步和回滚成本越高。

## 标记不可变发布点

确认提交、测试与制品对应后创建附注标签：

```bash
git tag -a v1.4.2 <发布提交ID> -m "Release 1.4.2"
git show v1.4.2 --no-patch
git push origin v1.4.2
```

已公开发布标签不应移动。发现问题应创建新版本，例如 `v1.4.3`，并保留旧标签对应的事故证据。

## 两种“回滚”必须分开

### 回退运行制品

平台重新部署上一个已验证制品，代码仓库历史不变。它速度快，但数据库、消息格式和外部副作用必须向后兼容。

### 回滚源码变化

在共享分支使用 `git revert` 创建反向提交，重新构建和发布新制品。它保留审计历史，但完成时间更长。

事故预案应提前说明采用哪一种，不能等故障时把两个动作都叫“回滚代码”。

## 数据库与协议无法靠 Git 自动恢复

删除列、修改消息语义、调用外部支付或发送通知后，切回旧制品未必能撤销影响。发布前应检查向前/向后兼容、迁移顺序、幂等性和数据修复方案。

## 有状态任务的停机边界

worker 正在执行长任务时直接终止，可能造成重复消费、锁未释放或中间状态残留。发布计划应说明：

1. 停止接收新任务；
2. 等待或迁移活跃任务；
3. 达到超时后如何记录和补偿；
4. 替换实例并恢复流量；
5. 验证积压、失败率和重复执行。

是否优雅停机来自运行模型，不来自 Git 分支名。
