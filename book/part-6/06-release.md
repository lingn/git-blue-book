# 发布不是一个标签：源码、制品与运行状态

Git 标签可以为源码对象命名，发布分支可以承载稳定化和维护提交，但真正进入环境的是构建制品、配置与数据迁移。把 `git tag` 当作发布完成，会让源码、制品和运行状态之间失去可追溯关系。

进入本章前，读者应理解分支、附注标签、远程引用、revert 和受保护分支。读完后，应能选择发布基线、创建并核验不可移动的发布引用，把它关联到制品摘要，并在事故中区分制品回退、源码修复和数据恢复。

本章以 Git 2.49.0 的本地行为为验证基线。制品仓库、部署平台、签名、审批和数据库工具属于外部系统；正文给出厂商无关证据要求，不伪造平台输出。

## 发布链上有四个不同的“版本”

```text
源码提交 / 发布标签
  -> 构建制品及内容摘要
  -> 环境部署记录
  -> 运行实例实际加载的制品
```

源码提交回答“构建输入中的 Git 快照是什么”；制品摘要回答“生成了哪些字节”；部署记录回答“控制面要求哪个环境使用哪个制品”；运行实例回答“请求最终到达了什么版本”。四者可以暂时不一致，例如滚动发布期间新旧实例并存，或主线已经前进而生产仍运行上一版制品。

发布记录必须保存不可变提交 ID 和制品摘要。`main`、`release/1.x`、`latest` 和文件名都可能移动或被覆盖，不能独立充当证据。

## 先决定从哪条历史发布

发布分支不是成熟团队的必选项，而是隔离稳定化节奏的一种成本较高的工具。

| 策略 | 适用条件 | 主要代价 | 必须约定 |
| --- | --- | --- | --- |
| 主线直接发布 | 主线持续可发布、变更小、自动验证充分 | 未完成功能必须被隔离，修复节奏紧 | 失败提交怎样阻止继续发布 |
| 短期稳定分支 | 发布验证窗口与主线开发并行 | 修复需要在两条历史同步 | 分支何时创建、冻结和删除 |
| 长期维护分支 | 同时支持多个已发布大版本 | cherry-pick、合并和依赖分叉成本高 | 支持期限、允许变更和合回方向 |
| 候选标签 | 候选提交本身不再修改，问题用新候选修复 | 候选数量增加 | 命名、保留和晋级规则 |

发布分支不应成为第二条无限期开发主线。分支存在期间，团队要明确哪个方向是修复的权威来源：修复先进入主线再迁移到维护分支，还是先修复生产分支再合回主线。没有方向约定时，同一缺陷容易产生多份内容相似、依赖不同的提交。

## 固定候选提交，而不是记住分支名

下面的取证步骤在已经配置 `origin`、有读取权限的本地仓库中执行。示例假设从远端维护分支发布；团队直接从主线发布时把 `release_ref` 改为 `origin/main`。

```bash
git status --short --branch
git fetch --prune origin

release_ref=origin/release/1.x
release_commit="$(git rev-parse "$release_ref")"
release_tree="$(git rev-parse "$release_commit^{tree}")"

git show --no-patch --format='%H%n%P%n%T%n%s' "$release_commit"
printf 'release_tree=%s\n' "$release_tree"
```

`fetch --prune` 连接服务器、下载缺失对象并更新本地远程跟踪引用；它不合并当前分支，但会删除已确认远端不存在的映射引用。运行前应读懂本仓库 refspec，避免显式 tag 映射让 prune 影响本地标签。

`rev-parse` 把可移动的远程跟踪引用固定为提交和 tree ID。`show` 只读对象，输出依次包含提交、父提交、tree 和说明；对象 ID 每次发布都不同。分支不存在、认证失败或对象不是提交时应停止，不要退回到一个未经记录的本地分支。

候选提交固定后，评审、CI 和构建都应引用 `release_commit`，而不是稍后重新解析 `release_ref`。若分支继续移动，新的对象是另一个候选，需要独立证据。

## 先确认构建了哪个候选

构建 runner 应核对实际 `HEAD` 等于调度的 `release_commit`，记录流水线定义、runner、依赖锁和构建命令，并为制品计算 SHA-256 等内容摘要。完整方法见本篇的 [CI/CD 证据链](11-ci-evidence-chain.md)。

常见发布顺序有两种：

1. 候选标签触发构建：先为候选提交创建受控标签，构建记录必须保存标签对象和剥离提交；
2. 候选提交先构建：制品通过验证后，再为同一提交创建正式标签，并把已有制品摘要写入发布记录。

两种都可以，不能混成“从标签名重新构建一次生产制品”。若测试环境和生产环境分别构建，同一提交可能因工具链、依赖或时间戳得到不同字节。更可审计的方式是构建一次，在环境之间提升同一个不可变制品。

## 创建发布标签是一项共享状态变更

### 创建前的检查

以下命令在已经固定 `release_commit`、完成候选验证且工作区没有进行中 merge/rebase 的仓库中执行。示例版本号必须替换为团队已经批准、尚未使用的新版本：

```bash
release_tag=v1.4.2

git cat-file -e "$release_commit^{commit}"
if git show-ref --verify --quiet "refs/tags/$release_tag"; then
  printf 'tag already exists locally: %s\n' "$release_tag" >&2
  exit 1
fi

if ! remote_tag_output="$(git ls-remote --tags origin \
  "refs/tags/$release_tag")"; then
  printf 'cannot query tags from origin\n' >&2
  exit 1
fi

if test -n "$remote_tag_output"; then
  printf 'tag already exists on origin: %s\n' "$release_tag" >&2
  exit 1
fi
```

`cat-file -e` 验证对象存在并可剥离为提交。`show-ref` 只查本地完整标签引用。`ls-remote` 读取服务器当前公布的匹配标签：通信失败会进入第一处分支，通信成功但没有匹配引用时变量为空。正式自动化还应保存标准错误和退出码，只在已确认通信成功且输出为空时继续。

更稳妥的服务器端方案是用平台 API 或受保护标签规则执行条件创建，避免两个发布者同时通过“尚不存在”检查后的竞态。本地 Git 的先查后推不能提供全局锁。

### 创建附注标签

```bash
git tag -a "$release_tag" "$release_commit" \
  -m "Release $release_tag"

git cat-file -t "$release_tag"
git rev-parse "$release_tag^{}"
git show --no-patch --decorate "$release_tag"
```

`tag -a` 创建一个附注 tag 对象，并让本地 `refs/tags/v1.4.2` 指向它；不会构建制品、连接远端或部署。第一条验证命令应输出 `tag`，第二条应等于 `release_commit`。`show` 显示标签说明与目标提交，时间和对象 ID 会变化。

如果此时发现目标错误且标签尚未发布，可以先保存错误对象 ID 供复盘，再删除本地标签：

```bash
git tag -d "$release_tag"
```

删除只移动本地标签引用，tag 对象可能暂时仍在对象库中。修正候选证据后重新创建。标签一旦共享，默认不移动、不复用版本号；创建更高的新候选或补丁版本，并把错误标签保留为事故证据。只有组织明确要求撤销且已经评估缓存、镜像、消费者和签名影响时，才走受控删除流程。

### 显式发布一个标签

```bash
git push origin \
  "refs/tags/$release_tag:refs/tags/$release_tag"
```

这会发送服务器缺少的对象并请求创建同名远端标签引用，不会默认推送其他本地标签。成功输出通常包含 `[new tag]` 和标签名，具体 URL 与格式由 Git 版本和传输决定。

推送前需要发布权限、受保护标签规则允许，并确认制品/发布记录已经采用同一 `release_commit`。推送失败时本地标签仍存在；先按认证、授权、同名引用或服务端策略分流，不要加 `--force`。

服务器核验：

```bash
git ls-remote --tags origin \
  "refs/tags/$release_tag" \
  "refs/tags/$release_tag^{}"
```

附注标签通常返回 tag 对象与剥离目标两行，后者对象 ID 应等于 `release_commit`。这只证明服务器公布的 Git 引用，不证明制品已上传、签名可信或部署完成。

## 发布记录要把标签与制品连接起来

一个最小发布记录至少包含：

- 仓库稳定标识、发布标签完整引用和 tag 对象 ID；
- 剥离后的源码提交 ID、tree ID和目标分支基线；
- CI 候选类型、检查记录和流水线定义版本；
- 制品名称、制品仓库位置和不可变摘要；
- 依赖清单、SBOM 或来源证明的位置；
- 发布者、批准者、创建时间和变更说明；
- 允许部署的环境、配置版本和数据库兼容区间；
- 已知良好回退制品及其摘要。

发布说明服务于读者，证据记录服务于机器核对和事故调查，二者可以关联但不能相互替代。只写“包含若干修复”无法验证环境中的字节，只有摘要也无法解释业务影响。

制品仓库应阻止普通用户覆盖同一不可变版本。若服务允许标签式名称移动，部署配置仍应锁定 digest。发现制品摘要与发布记录不一致时，隔离制品并停止提升；不要移动 Git 标签去适配错误制品。

## 部署的是已验证制品，不是当前分支

部署请求要引用制品摘要和发布记录，而不是要求生产平台“拉取 `main` 再构建”。后者把源码解析、依赖下载和构建放进高权限环境，既增加不可重复输入，也扩大供应链攻击面。

部署前至少验证：

1. 制品重新计算的摘要等于发布记录；
2. 构建证据中的 `source_commit` 等于标签剥离目标；
3. 目标环境的配置和 secret 版本与制品兼容；
4. 数据库当前版本允许新旧应用同时运行；
5. 回退制品仍可读取当前数据和消息；
6. 发布身份只拥有目标环境所需最小权限。

滚动、蓝绿或金丝雀只是流量与实例替换策略。无论哪种方式，都要从实际实例读取制品 digest 或非敏感构建标识，并记录新旧数量、健康结果和流量比例。控制面显示“部署完成”不能代替运行核验。

## 数据库迁移决定能否回退制品

切回旧应用时，数据库不会自动回到旧 schema。删除列、收紧约束、重写数据或改变消息语义，都可能让旧制品无法启动或读错数据。

更安全的发布序列通常是 expand/contract：

1. 先增加向后兼容的列、表、字段或接口；
2. 发布能同时处理新旧格式的应用；
3. 回填数据并验证数量、校验和与异常记录；
4. 切换读写路径，观察完整业务周期；
5. 确认支持窗口内没有旧实例和旧消费者；
6. 在后续独立发布中删除旧结构。

每一步都要写明可回退到哪些应用版本、数据修复方式和停止条件。无法逆向的迁移应标记为向前修复型操作，准备恢复备份或补偿脚本；不要为了形式提供未经演练的 `down` 迁移。

数据库备份的存在不等于可恢复。恢复时间、恢复点、跨服务一致性和回放验证需要演练，并与发布变更窗口匹配。

## 长任务和异步消息有自己的发布边界

worker 正在处理长任务时直接终止，可能造成重复消费、锁未释放、外部副作用重复或中间状态遗留。Git 无法观察这些运行状态。

发布计划应说明：

1. 何时停止接收新任务或降低流量；
2. 怎样识别当前运行任务及其代码版本；
3. 等待、迁移或取消的最大时限；
4. 超时任务怎样记录、重试和补偿；
5. 新旧 worker 是否能同时读取队列消息；
6. 恢复流量前检查哪些积压、失败和重复指标。

manager、API 和 worker 共享库时，要根据实际构建依赖决定部署范围，不能从目录名或提交说明推断“只改了一个服务”。制品 SBOM、构建图和运行遥测才是证据。

## 事故中的四种动作

| 动作 | 改变什么 | 适用前提 | 主要证据 |
| --- | --- | --- | --- |
| 回退旧制品 | 运行实例选择 | 旧制品与当前配置、schema、消息兼容 | 旧制品摘要、兼容矩阵、实例核验 |
| 回退配置 | 环境配置或 feature flag | 配置版本可独立恢复，秘密没有失效 | 配置审计、作用范围、运行指标 |
| revert 源码再发布 | 共享 Git 历史并生成新制品 | 反向变化可构建且数据语义仍兼容 | revert 提交、新制品摘要、新部署记录 |
| 数据前向修复/恢复 | 数据库、消息或外部副作用 | 已有演练和审批 | 备份点、迁移日志、校验与补偿记录 |

事故开始时先记录当前运行制品摘要、配置版本、数据库迁移、实例分布和影响指标。不要先假设最新 Git 提交就是线上版本。

制品回退通常最快，但若不兼容就会扩大故障。源码 revert 保留历史，却需要重新测试、构建和部署，不能替代紧急流量控制。数据库动作风险最高，应由专门手册和审批控制。

恢复后分别验证控制面期望值与运行实例实际值，观察至少一个与故障机制匹配的业务周期。随后再决定是否需要永久源码修复和新正式版本。

## 常见失败与恢复

| 失败 | 判别证据 | 恢复 |
| --- | --- | --- |
| 本地标签指错且未推送 | `git rev-parse "$release_tag^{}"` 不等于候选 | 保存错误 ID，删除本地标签，修正证据后重建 |
| 同名远端标签已存在 | `git ls-remote --tags` 返回现有对象 | 停止并调查所有者；不用强推覆盖 |
| 标签提交与制品来源不一致 | 构建清单的 `source_commit` 不同 | 隔离制品或标签，重新走候选流程，不移动证据迁就错误 |
| 部署后仍有旧实例 | 实例 digest 与期望摘要不同 | 暂停继续发布，处理 rollout、容量或健康门槛 |
| 旧制品无法回退 | schema、配置或消息已不兼容 | 恢复兼容配置或执行已演练的前向修复 |
| 修复只进入维护分支 | 主线/其他支持分支不包含等价变化 | 按团队约定迁移并分别测试，不盲目合并整条分支 |

已经公开的错误标签是否删除是组织与消费者层面的决策。即使服务器删除，其他克隆、镜像、包索引和部署记录仍可能保存旧对象。对外发布通常更适合保留证据并创建新版本。

## 本地实验能证明到哪里

两个隔离脚本覆盖本章的 Git 和制品事实：

```bash
./scripts/verify-part-4-remotes.sh
./scripts/verify-ci-evidence-chain.sh
```

第一个在本地裸仓库创建附注标签并显式推送，断言远端对象类型为 `tag`。第二个创建合并候选和附注候选标签，runner 在分离 HEAD 上构建两份相同源码归档，核对 SHA-256、证据清单和模拟部署副本，并验证主线前进不会改变已记录候选。

脚本使用临时目录、虚构身份和 `file://` 远端，不连接网络。它们不能证明真实平台的受保护标签、签名验证、制品权限、数据库迁移、滚动发布或运行实例状态。真实发布演练必须在专用测试环境采集这些证据，不能引用本地脚本输出代替。

## 小结

发布标签为源码对象命名，制品摘要标识要部署的字节，部署与运行记录证明环境实际采用了什么。三类证据必须显式关联。

发布分支只在它解决稳定化或多版本维护问题时使用；标签一旦共享默认不移动；制品在环境间提升而不重建；数据库与长任务提前设计兼容窗口。这样“回滚”才能被拆成可判断、可验证的具体动作，而不是事故中的模糊口令。
