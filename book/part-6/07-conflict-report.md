# 冲突解决后如何准确说明

## 合并完成后还能看出冲突吗

工作区中的 `<<<<<<<` 等标记会被删除，Git 提交本身不会保存一份“当时屏幕上有哪些冲突标记”的清单。但合并提交保留两个父提交和最终快照，因此可以重建双方输入与最终选择。

查看合并提交的组合差异：

```bash
git show --cc <合并提交ID>
```

分别比较最终结果与两个父提交：

```bash
git diff <合并提交ID>^1 <合并提交ID>
git diff <合并提交ID>^2 <合并提交ID>
```

`^1` 是第一父提交，通常是合并时当前分支；`^2` 是第二父提交，通常是被合入分支。父顺序应通过 `git show --no-patch --format=raw` 核对，不凭印象。

这些证据能显示最终结果相对双方各改了什么，却不一定证明哪些路径曾触发机械冲突，也不能自动还原当时讨论的业务理由。因此解决时要留下说明。

## 一份可转发的冲突说明

```text
冲突范围：文件、函数或配置项
共同基础：合并前双方共同版本的行为
当前分支意图：为什么这样修改
合入分支意图：为什么那样修改
最终处理：保留、组合或重新实现了什么
舍弃内容：哪些实现没有保留，以及原因
验证证据：测试命令、请求样例、构建或运行结果
部署影响：受影响组件、配置、迁移和停机要求
```

## 不要只贴冲突标记

标记只能展示文本两侧，不能说明业务约束。尤其是配置、事务边界、重试策略和共享 SDK 冲突，简单选择一侧可能编译通过却改变运行行为。

## 合并提交已经创建怎么办

先不要为了重新展示冲突而重做合并。使用父提交差异和原分支提交调查；如果最终行为错误，在未公开分支可修改，已公开分支按团队策略新建修复或 revert。

## 评审者怎样复核

评审者应检查双方原提交、最终合并快照和测试证据，而不是只问“冲突是否解决”。冲突解决的质量由最终语义决定，不由 Git 状态干净决定。
