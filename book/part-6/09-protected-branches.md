# 受保护分支把团队约定变成服务器规则

Git 客户端允许用户在自己的仓库里创建、移动和删除引用。主线是否允许直接推送、合并前要经过哪些评审、谁可以绕过限制，属于托管平台或自建服务端的控制面。两层必须分开：Git 决定一次引用更新是否满足协议和对象关系，平台再按身份、评审、检查与组织策略决定是否接受更新。

本章使用厂商无关名称。不同 Git 托管平台会把这些能力称为分支保护、规则集、推送规则或合并检查，权限和计费也可能不同。配置前要核对平台文档和组织当前套餐，不能照抄界面步骤。

## 先画出一次主线更新

以功能分支合入 `main` 为例，一次受控更新至少涉及五类状态：

1. 提议的提交图和最终主线提交；
2. 发起者、评审者、合并者和自动化机器人的身份；
3. 评审结论及其对应的提交版本；
4. CI 检查名称、结果和被检查的提交；
5. 服务端对 `refs/heads/main` 的更新决定。

平台页面显示“可以合并”时，这些状态暂时满足规则。页面结论不是永久承诺。功能分支新增提交、目标分支前进、检查被重新运行或权限变化后，平台可能需要重新评估。

Git 客户端能观察其中一部分。下面的命令在已经配置 `origin` 的本地仓库中执行，只读取本地状态：

```bash
git status --short --branch
git log --graph --decorate --oneline --all --max-count=20
git rev-parse HEAD
git rev-parse origin/main
```

`HEAD` 和 `origin/main` 的对象 ID 是本地证据。`origin/main` 只记录最近一次 fetch 后看到的远端状态，不是服务器当前值。需要比较服务器最新状态时先执行 `git fetch origin`，再记录 fetch 时间和新的对象 ID。fetch 会更新本地远程跟踪引用，不会自动合并当前分支。

评审、CI 和绕过记录通常只能从平台读取。排障报告要把本地 Git 证据与平台证据分开，避免用一个过期的 `origin/main` 推断服务器刚刚发生了什么。

## 保护规则要对应具体风险

常见规则可以归入六类。

| 风险 | 控制 | 仍然没有解决的问题 |
| --- | --- | --- |
| 未经评审的改动进入主线 | 要求通过合并请求/拉取请求更新 | 评审是否覆盖真实风险 |
| 作者自己批准改动 | 要求独立审批或代码所有者审批 | 所有权文件是否准确、评审者是否有上下文 |
| 已批准代码随后又变化 | 新提交后撤销旧审批 | 细小变更是否需要完整重审 |
| 未验证的提交进入主线 | 要求指定 CI 检查通过 | 测试遗漏、检查误配和不稳定测试 |
| 主线被删除或改写 | 禁止删除和非快进更新 | 管理员或例外身份是否仍可绕过 |
| 并发合并让绿色结果过期 | 合并前更新主线或使用合并队列 | 队列使用的临时合并提交是否覆盖部署路径 |

规则数量不是成熟度指标。每条规则都应能回答三个问题：它防哪类事故，失败时由谁处理，紧急情况下怎样安全绕过。没人维护的必需检查会让仓库长期无法合并；所有人都能绕过的保护只剩提示作用。

## 检查必须绑定正确的提交

评审页面常同时出现功能分支头、目标分支头、临时合并结果和最终主线提交。CI 通过时应记录它验证的是哪一个对象 ID。

只测试功能分支头，无法发现它与最新主线组合后的问题。测试临时合并结果能覆盖这类组合，但目标分支在排队期间继续变化，先前结果仍可能过期。托管平台通常通过“合并前必须更新”“在临时合并提交上运行检查”或合并队列处理竞态，具体语义要按当前平台文档核对。

一条可审计的 CI 记录至少包含：

- 被检出的提交 ID；
- 目标分支和基线提交 ID；
- 工作流或流水线版本；
- 实际执行的测试与构建命令；
- 结果、时间和日志位置；
- 生成制品的摘要或不可变标识。

状态显示为绿色，只表示已配置检查对某个提交返回成功。路径过滤漏掉测试、工作流被同一变更修改、外部依赖不可用被当作跳过，仍可能产生错误结论。

## 三种合并方式留下不同历史

平台上的 merge、squash 和 rebase merge 最终都会更新目标引用，但产生的提交图不同。

**Merge** 保留功能分支提交并创建合并提交，主线可以看到分支拓扑。**Squash** 根据功能分支的最终差异生成一个新提交，原提交 ID 通常不在主线父历史中。**Rebase merge** 为功能分支提交生成新的副本，再把它们接到目标分支上，提交内容可能相同，对象 ID 会变化。

因此，`git branch --contains "$original_commit"` 只回答主线是否能沿父链接到达那个对象，不能单独证明 squash 后的变化没有合入。运行前要把 `original_commit` 赋值为原提交的完整 ID。调查时还要结合合并请求记录、补丁等价性和最终差异。团队应固定默认合并方式，并说明例外由谁决定；否则提交引用、发布说明和回滚手册会建立在不同假设上。

## 一份可执行的最小团队约定

约定需要落到仓库文档和平台配置，至少覆盖以下内容：

- 默认分支、发布分支和维护分支分别承载什么状态；
- 哪些引用受保护，是否允许创建、删除和强制更新；
- 功能分支是否允许改写，怎样判断已有协作者依赖它；
- 合并采用哪种方式，提交说明和评审记录如何关联；
- 哪些目录需要指定所有者审批，所有者不在时由谁代理；
- 哪些检查是必需检查，检查名称变化时谁同步保护规则；
- 热修复从哪个已发布点开始，如何合回仍受支持的分支；
- 标签由谁创建，签名和制品关联怎样验证；
- 已共享错误默认使用 revert，什么条件下允许例外改写；
- 紧急权限怎样获得、使用、撤销和复盘。

保护规则可以比这份约定更严格，不能与它相互矛盾。文档说“禁止直接推送”而管理员日常直接推送，会让审计记录和团队预期同时失真。

## 修改规则前先做影响检查

分支保护的变更可能立刻阻断开发或扩大权限。操作前应在平台侧记录当前规则、适用范围和例外身份，并确认自己有管理仓库策略的权限。若平台支持规则预览、评估模式或测试仓库，先在那里验证。

修改后至少检查四条路径：普通贡献者直接推送是否被拒绝；合并请求在缺少审批或检查时是否被阻止；满足条件后是否能合并；紧急身份是否只能执行预定的例外动作。服务端拒绝消息和审计事件属于平台输出，不能用本地 bare 仓库模拟后写成真实结果。

回退策略是在修改前保存旧规则，并明确恢复人。规则变更如果使主线完全无法更新，先恢复到上一份已知配置，再调查检查名称、应用范围或身份匹配，不要临时给所有人管理员权限。

## 紧急绕过仍要保留控制

事故处理中可能需要跳过等待时间、使用管理员身份或临时放宽一条检查。紧急通道的目标是缩短恢复时间，同时保留可追溯性。

绕过前记录事故编号、目标引用、当前对象 ID、拟更新对象 ID、被跳过的规则和批准人。操作完成后记录服务器最终对象 ID、CI/部署结果和权限回收时间。后续补评审不能假装发生在更新之前，审计中应如实保留时间顺序。

若更新涉及强推，先确认没有覆盖事故期间出现的新提交。仅有 `git push --force` 不提供并发保护；使用租约也要明确租约基线，并在操作前重新获取和核对远端。具体恢复流程见第五篇的 `--force-with-lease` 与 reflog 章节。

## 定期验证规则还在工作

仓库名称、默认分支、CI 工作流和团队成员都会变化。季度或重大迁移后可以做一次受控检查：保护范围是否仍匹配真实分支，必需检查是否仍会报告，所有者规则是否有有效维护者，机器人和离职账号是否仍有绕过权限，紧急通道能否在规定时间内启用和回收。

检查结果应包含日期、仓库范围、发现的问题和修复负责人。保护分支只是引用更新的一道控制，源码正确性、制品完整性和部署安全仍要由评审、CI/CD 与运行验证共同承担。
