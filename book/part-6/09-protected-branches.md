# 受保护分支和团队协作约定

## Git 客户端不能独自实施团队规则

Git 允许本地创建、重写和删除引用。共享平台的受保护分支用服务器规则限制谁能更新主线、需要哪些评审和检查。

常见保护包括：

- 禁止直接推送；
- 要求拉取请求或合并请求；
- 要求指定人数评审；
- 要求持续集成检查通过；
- 禁止强制推送和删除；
- 要求提交签名或线性历史；
- 限制谁能绕过规则。

规则应对应真实风险。只打开所有开关可能让紧急恢复无人能执行；完全依赖口头约定又难以审计。

## 最小团队约定

每个仓库至少明确：

1. 默认分支和发布分支分别做什么；
2. 功能分支能否重写，谁可能依赖它；
3. 合并采用 merge、squash 还是 rebase，由谁执行；
4. 提交和评审需要哪些测试；
5. 热修复从哪里开始，如何回灌其他分支；
6. 标签由谁创建，如何对应制品；
7. 已推送错误使用 revert 还是例外改写；
8. 紧急权限怎样审批和事后复盘。

## squash 合并改变提交身份

平台 squash 通常把功能分支变化生成一条新的主线提交。原分支的提交 ID 不会出现在主线父历史中，但变化可能已经包含。判断“是否合入”不能只搜索原 ID，还要查评审记录和最终差异。

## 保护分支不是质量保证

绿色检查只证明被配置的检查通过。缺失测试、错误部署范围和不兼容迁移仍可能进入生产。规则需要与真实运行链路一起维护。

## 紧急绕过后的责任

若事故处理中必须使用管理员权限，应记录操作者、原因、提交、验证、部署结果和后续补充评审。紧急通道应缩短恢复时间，不应消除审计。
