# 一套可恢复的 Git 排障流程

Git 问题常因连续试命令而扩大。使用下面的固定顺序，把观察与改变分开。

## 一、描述目标，不先说命令

把“reset 失败了”改成：

```text
我在 feature/payments，希望保留工作区修改，取消最近一次未推送提交，并让修改回到未暂存状态。
```

目标应包含当前分支、要保留什么、要改变什么、是否已推送。

## 二、收集本地证据

```bash
git status
git branch -vv
git log --oneline --graph --decorate --all -20
git diff
git diff --staged
```

操作正在进行时，`status` 会指出 merge、rebase、revert 或 cherry-pick 状态。不要跳过提示。

## 三、需要远程证据时再获取

```bash
git remote -v
git fetch --all --prune
git log --oneline --graph --decorate --all -20
```

获取会更新远程跟踪引用。准备显式租约强推时，应先记录预期提交 ID，并理解后台获取的影响。

## 四、画最小提交图

标出：当前 `HEAD`、本地分支、远程跟踪分支、目标提交、是否存在分叉。无法在图上说清操作对象时，不执行历史修改。

## 五、选择影响最小的动作

- 能用只读命令确认就不先改状态；
- 能创建恢复分支就不先 hard reset；
- 已公开错误优先 revert；
- 进行中的操作优先使用对应 abort；
- 推送拒绝先 fetch 和比较，不强制覆盖。

## 六、执行一个动作后立即验证

重复 `status`、提交图和差异检查，运行项目测试。不要连续执行多条互相补救的命令后才看结果。

## 七、保留事故记录

记录原始命令、关键 ID、错误原文、采取的恢复动作和验证结果。涉及协作者时说明共享边界；涉及部署时说明制品、实例、数据和停机处理。

## 求助时提供什么

可以提供脱敏后的状态、提交图、分支关系和完整错误。不要泄露仓库凭据、令牌、内部 URL 或客户数据。相比“我执行了很多命令，现在很乱”，可复现证据能更快得到正确方案。
