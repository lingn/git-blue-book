# 从候选提交到运行版本：CI/CD 证据链

Git 能精确标识源码对象，却不知道哪个 runner 执行了什么命令、依赖从哪里取得、生成了哪个制品，也不知道线上实例最终运行什么。可靠的 CI/CD 必须把这些状态连接起来，而不是把“主线是绿色的”当作发布证明。

进入本章前，读者应理解提交对象、引用、远程跟踪分支、浅克隆、受保护分支和发布标签。本章完成后，应能识别 CI 实际验证的候选提交，为构建产物建立不可变证据，并区分源码回滚、制品回退、配置回退和数据库恢复。

本章使用厂商无关模型。事件字段、合并队列、必需检查、身份令牌和制品服务的具体行为会随平台版本、权限和套餐变化；落地时必须按当前平台文档核对。本地实验只验证 Git 与文件摘要行为，不伪造平台状态或部署输出。

## 一次发布至少跨越七类状态

```text
触发事件
  -> 候选提交与目标基线
  -> checkout 后的实际 HEAD / tree
  -> 流水线定义、runner 与依赖输入
  -> 构建制品及其摘要
  -> 发布引用与发布记录
  -> 环境中的部署记录
  -> 运行实例实际加载的版本
```

任何箭头断开，都会出现“页面显示通过，但不知道通过的是什么”或“平台显示部署成功，但实例仍运行旧版本”。一条可审计链要为每一层保存不可变标识，并记录谁在什么时候把上一层推进到下一层。

Git 提交 ID 只覆盖提交对象中的 tree、父提交、作者/提交者和说明。它不覆盖未提交文件、外部依赖仓库、runner 镜像、环境变量、密钥、数据库状态、部署参数或运行流量。

## 先回答 CI 测试的是哪个提交

评审与合并期间可能同时存在多个对象：

| 候选 | 内容与父历史 | 能回答的问题 | 不能单独证明什么 |
| --- | --- | --- | --- |
| 功能分支头 | 贡献者最后一次推送的提交 | 分支自身是否通过检查 | 与最新目标分支组合后是否通过 |
| 目标分支头 | 当前主线或发布分支提交 | 基线自身是否健康 | 功能变化是否兼容 |
| 临时合并结果 | 某一功能头与某一目标头的合并提交 | 这两个精确输入组合后是否通过 | 目标分支再次前进后仍然通过 |
| 合并队列候选 | 平台按队列顺序形成的临时提交 | 这个队列位置的组合是否通过 | 最终主线对象一定与候选相同 |
| 最终主线提交 | 服务器实际写入受保护引用的对象 | 主线现在指向什么 | 该对象已经构建、部署和运行 |

Squash 或 rebase merge 还会生成不同于原功能提交的新对象。检查关联原提交 ID，不会自动转移成对新对象的密码学证明；平台可以按工作流规则复用或重新要求检查，但具体语义必须核对。

团队的必需检查规则应说明检查绑定哪类候选、目标分支变化后是否作废、最终写入提交与被测提交不同时怎样重新验证。只记录分支名不够，因为分支是可移动引用。

## Runner 必须核对调度值与实际 HEAD

许多 CI checkout 位于分离 HEAD：`HEAD` 直接指向被调度提交，没有可提交的当前本地分支。这是正常状态，不是仓库损坏。真正危险的是流水线以为自己在构建一个对象，工作树实际检出了另一个对象。

下面的入口检查在 CI 工作树中执行。调度系统必须把完整候选提交 ID 放入厂商无关变量 `CI_EXPECTED_COMMIT`：

```bash
expected_commit="${CI_EXPECTED_COMMIT:?CI_EXPECTED_COMMIT is required}"
actual_commit="$(git rev-parse HEAD)"

if test "$actual_commit" != "$expected_commit"; then
  printf 'checkout mismatch: expected %s, got %s\n' \
    "$expected_commit" "$actual_commit" >&2
  exit 1
fi

git status --short
git branch --show-current
git rev-parse HEAD^{tree}
git rev-parse --is-shallow-repository
```

`rev-parse HEAD` 和 `HEAD^{tree}` 读取实际提交与根 tree；不修改仓库。`status --short` 在干净 checkout 中无输出，但生成文件、缓存恢复或前置脚本可能让它非空。`branch --show-current` 在分离 HEAD 上输出空字符串。最后一条输出 `true` 或 `false`，决定后续历史命令是否可能缺祖先。

提交不匹配时应立即停止，保留调度事件 ID、预期/实际对象 ID、checkout 日志和远程 URL 的脱敏版本。不要用 `git reset --hard "$expected_commit"` 掩盖 checkout 组件或事件路由错误；那会改变现场，却没有证明缺失对象来自可信远端。

如果作业需要 merge-base、标签、变更范围、blame 或版本生成，浅克隆可能不满足前置条件。应在工作流配置中取得足够历史，再用 `git rev-parse --is-shallow-repository` 和目标祖先查询验证，而不是发现命令失败后无条件抓取所有引用和凭据。

### 远程跟踪引用仍可能过期

Runner 中的 `origin/main` 只表示最近一次 fetch 保存的状态。平台调度事件中的目标提交、checkout 的合并父提交和 `origin/main` 可能各不相同。诊断时分别记录：

```bash
git rev-parse HEAD
git show --no-patch --format='%H%n%P%n%T' HEAD
git rev-parse origin/main
```

`%H` 是提交 ID，`%P` 是父提交列表，`%T` 是根 tree。合并候选通常有两个或更多父提交；squash 候选可以只有一个。输出中的对象 ID 都随运行变化，不能与书中固定哈希比较。

若要向服务器确认最新主线，fetch 会改变本地远程跟踪引用和 `FETCH_HEAD`，应在采集初始证据之后执行。fetch 成功也不能改变已经调度的候选身份；如果目标前进使候选过期，应让平台重新生成候选并重跑检查，不在旧 runner 内私自合并一个未登记对象。

## 触发事件只是开始条件

常见触发源包括分支 push、标签 push、评审更新、合并队列、定时任务、手工批准和外部 API。事件回答“为什么启动”，不自动回答“应构建什么”和“允许做什么”。

### 分支与标签都会移动

分支触发器必须从事件载荷保留 old/new 对象 ID。作业稍后再解析 `main`，可能看到另一批推送后的值。标签在 Git 中也是引用；如果服务端允许删除或强制更新，标签名同样不是永久事实。发布证据应保存标签对象 ID、剥离后的提交 ID和制品摘要，并由服务器策略限制发布引用变更。

### 路径过滤是一种风险模型

“只有 `app/` 变化才运行应用测试”隐含假设：应用行为只受该目录影响。共享构建脚本、依赖锁文件、基础镜像、接口定义、数据库迁移和 CI 配置都可能改变应用结果。

路径过滤应从依赖图推导，并设保守兜底：共享输入变化触发所有消费者；过滤规则自身变化触发完整检查；定期或合并前运行不经过过滤的基线任务。计算 changed paths 时还要明确比较基线，功能分支头相对旧主线与临时合并结果相对最新主线可能得到不同集合。

平台对“被路径过滤跳过的必需检查”怎样显示和是否阻止合并并不统一。规则上线前要在专用测试仓库验证跳过、失败、取消、超时和重跑五类状态，记录平台版本、检查名称和适用分支。

### 不受信任代码不能接触发布凭据

来自派生仓库、外部贡献者或低信任分支的代码可以修改测试脚本、构建工具和依赖。若同一作业注入发布令牌、生产密钥或长期缓存写权限，攻击代码可以直接读取它们。

至少把“验证不受信任代码”和“使用受保护凭据发布已批准制品”拆成不同信任域。验证阶段使用只读源码权限和隔离缓存；发布阶段只接受经过策略验证的不可变制品与证据，不重新执行贡献者提供的任意脚本。具体事件是否会获得 secrets 是平台易变事实，不能凭经验猜测。

## 流水线定义也是构建输入

仓库内的 CI 文件、构建脚本和依赖锁文件通常随源码版本化。记录源码提交仍不足以快速回答“执行了哪一版流水线”，尤其当平台可能从目标分支、功能分支或外部模板读取配置时。

如果本仓库约定流水线入口为 `.ci/pipeline.sh`，在已经核对的 checkout 中可以记录其 blob ID：

```bash
actual_commit="$(git rev-parse HEAD)"
pipeline_blob="$(git rev-parse "$actual_commit:.ci/pipeline.sh")"
printf 'pipeline_blob=%s\n' "$pipeline_blob"
```

这只证明该提交 tree 中这条路径的内容。平台最终是否执行它、是否拼接组织模板、调用了哪个外部 action 或 runner 镜像，还要从平台日志和配置解析结果取证。路径不存在时命令失败，应停止并检查工作流入口约定，不能写一个空值继续发布。

流水线证据至少应包含：

- 工作流配置或入口脚本的不可变版本；
- runner 操作系统、容器/虚拟机镜像摘要和关键工具版本；
- 依赖锁文件摘要、内部制品源和离线缓存标识；
- 实际命令、退出状态、开始/结束时间和日志位置；
- 读取与写入凭据的身份、权限范围和有效期；
- 网络访问、缓存命中和外部服务降级情况。

环境变量可能包含秘密，不能把完整环境转储当作证据。采用字段白名单，并在写日志前验证脱敏效果。

## 可重复构建是输入与过程的约束

理想的可重复构建是：相同源码、工具链、依赖和构建参数得到逐字节相同的制品。现实中，时间戳、随机数、文件顺序、绝对路径、网络依赖和编译器版本都可能引入差异。

一次“本地重新构建成功”不能证明与已部署制品相同。要么消除非确定性并比较摘要，要么把无法消除的输入完整记录并评估差异。Git tree 相同也不保证构建相同，因为 tree 不包含 runner 和外部依赖。

发布流程通常更适合“构建一次，多环境提升同一制品”：测试、预发布和生产引用同一个不可变摘要，只改变经过审计的环境配置。若每个环境重新构建，就产生了新的制品，必须重新生成摘要、来源证据和验证结果。

### 制品需要独立于文件名的身份

`application.tar`、`latest` 或 `v1.4.2` 都可能被覆盖。发布记录应使用 SHA-256 等内容摘要或制品仓库提供的不可变 digest。下面的脚本片段在构建目录中读取一个已有制品，只计算摘要：

```bash
artifact_file=./dist/application.tar

if command -v sha256sum >/dev/null 2>&1; then
  artifact_sha256="$(sha256sum "$artifact_file" | awk '{print $1}')"
else
  artifact_sha256="$(shasum -a 256 "$artifact_file" | awk '{print $1}')"
fi

printf 'artifact_sha256=%s\n' "$artifact_sha256"
```

前置条件是制品已完成写入，且环境提供 `sha256sum` 或 `shasum`。命令不修改制品；文件不存在或摘要工具不可用时应失败。计算期间若另一个进程仍在写文件，结果没有意义，应先采用原子完成标记或只读制品存储。

不要把 Git 对象 ID 当成任意制品的 SHA-256。Git 对象 ID 包含对象类型和长度的 Git 编码，仓库还可能使用不同对象格式；它与文件摘要承担不同协议。

## 一份最小构建证据记录

格式可以是签名的 JSON、制品证明或组织定义的清单，字段语义比文件扩展名重要。最低应能表达：

```text
schema_version
repository_identity
source_commit
source_tree
candidate_kind
target_commit
feature_commit_or_change_id
pipeline_definition
runner_image_digest
dependency_lock_digest
build_command_identity
artifact_name
artifact_sha256
build_identity
started_at / finished_at
```

`source_commit` 保留历史与评审关系，`source_tree` 标识源码快照；两个不同提交可以拥有相同 tree，不能只留一个字段。`target_commit` 说明临时合并候选基于哪版主线。`artifact_sha256` 让后续部署无需重跑构建就能核对内容。

记录必须与制品一起进入不可随普通开发者任意覆盖的存储，并定义保留期。把清单写进同一个可变工作区后删除 runner，不能形成长期证据。签名与供应链证明将在第十篇展开；签名也只能证明签名者认可特定内容，不能弥补构建输入缺失。

## 发布标签连接源码，不直接包含制品

附注标签可以为候选或正式发布提交提供稳定名称，并保存标签说明与可选签名。验证映射时分别读取标签对象和剥离目标：

```bash
release_tag=v1.4.2
git cat-file -t "$release_tag"
git rev-parse "$release_tag^{}"
```

附注标签的第一条输出 `tag`，第二条输出最终提交 ID；轻量标签第一条通常直接反映目标对象类型。命令只读取本地对象，不能证明服务器仍保存同一标签，也不能证明对应制品存在。

可靠发布记录要同时保存发布引用的服务器对象 ID、提交 ID、制品摘要和发布审批。发现制品错误时创建新候选或新正式版本，通常比移动已经公开的标签更可审计。删除或替换发布标签是共享状态变更，必须由保护规则和事故流程控制。

## 部署记录要回答“哪个制品去了哪里”

一次部署至少记录：

- 环境与目标集群/区域的稳定标识；
- 制品仓库、不可变摘要和构建证据位置；
- 环境配置版本、secret 版本标识和基础设施变更；
- 数据库迁移版本及其前向/后向兼容条件；
- 发起者、批准者、部署工具身份和时间；
- 发布策略、批次、健康门槛与最终状态；
- 回退目标、触发阈值和实际执行结果。

“部署成功”可能只表示控制面接受了请求。还要从运行实例、任务定义或镜像运行时读取实际制品 digest，统计新旧版本实例数量，并验证流量是否到达预期版本。应用暴露版本端点时，应返回非敏感的构建标识，不能把凭据、内部 URL 或完整环境一起泄漏。

部署期间主线可以继续前进，因此平台页面上的 `main` 不能反推已部署提交。部署记录必须锁定构建时的 `source_commit` 和 `artifact_sha256`。

## 四种“回滚”必须分别设计

| 动作 | 改变的状态 | 速度与条件 | Git 中发生什么 |
| --- | --- | --- | --- |
| 重新部署旧制品 | 运行环境的制品选择 | 快，但要求配置、协议和数据兼容 | 可以完全不改 Git |
| 回退环境配置 | 配置控制面 | 取决于配置版本和 secret 轮换 | 源码提交可能不变 |
| revert 源码并重建 | 共享历史、构建和部署 | 慢但保留反向提交证据 | 新增 revert 提交和新制品 |
| 数据修复或迁移 | 数据库/消息/外部副作用 | 风险最高，常需前向修复 | Git 只能保存脚本和记录 |

制品回退不能自动撤销数据库列删除、消息语义变化、已发送通知或外部支付。发布前应采用 expand/contract 等兼容策略，把 schema 变化与应用切换分阶段，并定义每阶段可回退到哪些版本。

若新旧版本会同时运行，API、消息和数据格式必须覆盖混合版本窗口。无法回退的迁移应在审批前明确标记，准备停止发布、向前修复和数据校验方案，而不是在事故时临时执行未经验证的 SQL。

## 故障按断开的箭头处理

| 症状 | 首要证据 | 安全动作 |
| --- | --- | --- |
| 作业构建了错误提交 | 调度对象 ID、实际 `HEAD`、checkout 日志 | 停止作业，修复事件/checkout；不在现场强行 reset 后继续 |
| 功能分支绿色，合并后失败 | 功能头、目标头、临时合并提交及各自检查 | 为精确合并候选重跑，不复用旧 SHA 的结论 |
| 版本工具找不到 tag 或 merge-base | shallow 状态、refspec、现有引用 | 取得所需历史并验证；不把缺历史当“没有发布” |
| 同一源码构建摘要不同 | runner、依赖、时间戳、命令和缓存记录 | 隔离非确定输入，两个制品都不得冒充同一发布 |
| 制品库文件摘要与清单不符 | 清单、存储审计、重新计算摘要 | 隔离制品，阻止提升，恢复已知摘要版本并调查篡改 |
| 平台显示成功但实例仍是旧版本 | 部署批次、实例 digest、健康状态与流量 | 暂停继续发布，修复 rollout；不要先改 Git 标签 |
| 旧制品启动后应用失败 | 配置、schema、消息和外部依赖兼容矩阵 | 恢复兼容配置或向前修复，按数据预案处理 |

失败记录要保留原始时间顺序。重新运行成功不能覆盖第一次失败的候选 ID、日志和制品；否则复盘无法判断是代码变化、环境变化还是偶发依赖导致恢复。

## 隔离实验验证了什么

在本书仓库根目录运行：

```bash
./scripts/verify-ci-evidence-chain.sh
```

前置条件是 Bash、Git 2.28 或更高版本、`awk`，以及 `sha256sum` 或 `shasum`。脚本使用临时目录、虚构身份和本地 `file://` 裸仓库，不读取用户级 Git 配置、不连接网络，也不修改蓝皮书仓库。

实验创建功能分支头和前进后的 `main`，再生成一个有两个父提交的合并候选。runner 精确检出候选的分离 HEAD，核对提交、tree、流水线 blob 和附注标签；同一候选执行两次 `git archive`，断言摘要一致，并证明功能分支头的归档与合并候选不同。

脚本随后生成本地证据清单，把同一归档复制到模拟 staging 目录并核对 SHA-256；故意修改部署副本后断言摘要失配，再从已知构建制品恢复。最后让服务器 `main` 前进，验证 runner 的 `origin/main` 可以变化，而分离 `HEAD` 和部署记录仍锁定原候选。

成功时最后输出：

```text
Detached CI checkout, reproducible archive, manifest, and deployment verification passed.
```

`git archive` 的可重复性只证明这个隔离源码归档在当前环境中得到相同字节，不代表任意语言编译、容器镜像或跨平台构建已经可重复。模拟 staging 只是普通目录，不能证明真实平台的权限、签名、审计、滚动发布或运行状态。那些证据必须在专用测试环境中采集。

## 小结

CI 的绿色结果必须绑定精确候选提交，构建结果必须绑定制品摘要，部署记录必须绑定环境中的实际制品。分支、标签和平台状态文案都不足以替代这条链。

从提交到运行版本的每一步都要保留输入、输出、身份和时间。这样事故发生时，团队才能判断应该重跑检查、恢复制品、回退配置、revert 源码还是修复数据，而不是把所有问题都归结为“回滚 Git”。
