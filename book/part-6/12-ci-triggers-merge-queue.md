# CI 为什么会跑、跑哪一个：触发器、路径过滤与合并队列

一条 CI 结果只有绑定精确候选提交才有意义，但候选不会凭空出现。分支更新、评审事件、标签、定时任务和合并队列会选择不同输入；路径过滤又决定哪些检查真正执行。任何选择规则不清，都可能让“绿色”只覆盖了团队以为的变化的一部分。

进入本章前，读者应理解 merge-base、临时合并提交、受保护分支和 [CI/CD 证据链](11-ci-evidence-chain.md)。读完后，应能定义触发状态机，为路径过滤建立保守依赖规则，并解释为什么队列中的第二个变更必须在第一个候选之后重新验证。

本章不假设 GitHub、GitLab 或其他平台的事件名称。检查状态、队列实现、权限和计费属于易变平台事实，落地时必须记录产品、版本、角色与核对日期。本地实验只验证提交图、diff 和条件引用更新。

## 从事件到主线更新要经过哪些状态

一次自动检查和合并可以抽象为：

```text
引用或评审状态发生变化
  -> 事件快照：repository + old/new + target + change
  -> 生成候选提交或 tree
  -> 按路径与策略选择检查
  -> runner 对候选执行检查
  -> 结果绑定 candidate + check identity + attempt
  -> 保护规则重新求值
  -> 以预期旧值为条件更新目标引用
```

这里没有一个状态可以只用分支名表达。事件入队后，功能分支可能强推，目标分支可能前进，流水线定义可能变化，权限也可能被撤销。系统应把每次尝试当作不可变快照，并在最后更新引用前重新核对条件。

最低事件记录应包含：

- 仓库稳定标识和事件唯一标识；
- 触发类型、触发者与信任级别；
- 被更新引用、old/new 对象 ID；
- 目标引用及事件发生时的目标对象 ID；
- 功能头、merge-base、候选提交和候选 tree；
- 路径策略版本、被选择与被跳过的检查；
- 检查定义版本、attempt、结果和时间；
- 最终引用更新的期望旧值与实际新值。

事件载荷可能来自不受信任贡献者。分支名、标签说明、提交说明和路径都只能作为数据处理，不能未经引用和转义拼进 Shell 命令、日志控制语句或部署参数。

## 触发源决定初始问题，不决定最终权限

| 触发源 | 初始问题 | 仍需固定的对象 | 常见误区 |
| --- | --- | --- | --- |
| 分支 push | 这个引用从 old 移到 new 后要做什么 | old/new 完整 ID | 作业启动时重新解析分支名 |
| 评审创建或更新 | 这版变更能否进入目标 | 功能头、目标头、候选 | 沿用上一版功能头的结果 |
| 标签创建 | 这个发布引用要构建或发布什么 | tag 对象和剥离目标 | 只保存标签名 |
| 定时任务 | 当前策略要检查哪个快照 | 调度时解析并保存的提交 | 运行结束时用最新主线解释结果 |
| 手工重跑 | 为什么重做某个候选 | 原候选、流水线版本和新 attempt | 把重跑成功覆盖原失败 |
| 合并队列 | 按当前队列顺序，哪个组合可以进入主线 | 队列基线、前序候选、当前候选 | 复用进入队列前的绿色状态 |

触发器只授予“开始评估”的理由。是否能读取秘密、写缓存、创建标签或部署生产，要由独立身份与策略决定。特别是评审代码的验证作业，不应因为触发方式变化就突然获得发布凭据。

### 去重、取消和重跑不是同一个动作

同一功能分支连续推送 F1、F2 时，F1 的运行可以为节约资源而取消，但其日志和取消原因仍是审计事实。F2 是新候选，不能继承 F1 的成功。对同一个对象重新运行则是新 attempt；runner 镜像、外部依赖或平台故障已经可能变化，应保留每次输入和结果。

去重键至少包含仓库、候选提交、检查身份和策略版本。只用分支名去重，会把不同提交混为一次运行；只用提交 ID 去重，又可能误把两套不同流水线定义当成同一个检查。

取消旧作业还要控制并发副作用。被取消的构建可能已经上传缓存、发布预览环境或写入外部测试数据。取消协议应定义清理责任和幂等键，不能认为进程停止就自动撤销外部状态。

## 三种 diff 回答不同问题

假设目标分支头为 T，功能分支头为 F，它们的最佳共同祖先为 B，平台又生成了合并候选 C。

```text
      F
     / \
B---+   C
     \ /
      T
```

实际图会因合并方式不同而变化，但需要区分以下比较：

```bash
target_commit="${CI_TARGET_COMMIT:?CI_TARGET_COMMIT is required}"
feature_commit="${CI_FEATURE_COMMIT:?CI_FEATURE_COMMIT is required}"
candidate_commit="${CI_CANDIDATE_COMMIT:?CI_CANDIDATE_COMMIT is required}"
runner_temp="${CI_RUNNER_TEMP:?CI_RUNNER_TEMP is required}"
if ! test -d "$runner_temp"; then
  printf 'runner temp directory does not exist: %s\n' "$runner_temp" >&2
  exit 1
fi

git cat-file -e "$target_commit^{commit}"
git cat-file -e "$feature_commit^{commit}"
git cat-file -e "$candidate_commit^{commit}"

merge_base_file="$runner_temp/merge-bases.txt"
git merge-base --all "$target_commit" "$feature_commit" \
  > "$merge_base_file"
merge_base_count="$(wc -l < "$merge_base_file" | tr -d ' ')"
if test "$merge_base_count" != 1; then
  printf 'expected one merge base, found %s\n' "$merge_base_count" >&2
  exit 1
fi
merge_base="$(sed -n '1p' "$merge_base_file")"

git diff --name-status "$merge_base" "$feature_commit"
git diff --name-status "$target_commit" "$candidate_commit"
```

第一组 diff 回答“功能分支相对共同起点提出了什么变化”，等价于常见的 `target...feature` 三点比较。第二组回答“把候选应用到这一版目标后，候选 tree 相对目标增加了什么”。两者可能路径相同，但候选 tree 还包含目标分支在 B 之后的所有状态。

命令在已经取得三个对象的 runner 仓库中读取 Git 对象，并在隔离临时目录写一份 merge-base 证据。提交缺失、浅克隆没有 merge-base 或最佳 merge-base 不止一个时会停止。复杂 criss-cross 历史应让实际合并策略生成候选，再对候选 tree 评估，不把随意挑出的单一祖先当权威。

如果 C 是以 T 为第一父提交的普通合并提交，还可核对：

```bash
git rev-parse "$candidate_commit^1"
git show --no-patch --format='%H%n%P%n%T' "$candidate_commit"
```

第一条预期等于 T，第二条记录候选、全部父提交和 tree。Squash、rebase merge 或平台自定义候选不一定有这种父结构，不能强行套用。平台必须说明最终主线对象与被测候选怎样关联。

### 自动化解析路径要保留字节边界

文件名可以包含空格、制表符和换行。脚本不要把 `git diff --name-only` 的换行输出放进 `for path in $(...)`。使用 `-z` 让路径以 NUL 分隔，并交给支持 NUL 的程序：

```bash
changed_paths_file="$runner_temp/changed-paths.zlist"
git diff --name-only -z "$merge_base" "$feature_commit" \
  > "$changed_paths_file"
```

这会在 runner 临时目录创建二进制路径清单，不修改 Git 对象或引用。目标目录必须是本次作业的隔离临时目录；作业结束后由 runner 清理。消费者也必须按 NUL 解析，不能再用普通逐行工具破坏边界。

若策略需要区分新增、删除、重命名或 submodule gitlink 变化，应使用 `--name-status -z` 并正确处理重命名记录的两个路径字段。没有相应解析测试时，宁可触发更大范围检查，也不要静默漏测。

## 路径过滤必须表达依赖闭包

“`services/payment/` 变化时运行 payment 测试”只是依赖规则的一部分。一个服务还可能依赖：

- 根目录构建脚本、工具链和依赖锁文件；
- 公共库、接口定义、代码生成器和数据库 schema；
- 基础镜像、部署模板和 feature flag 定义；
- CI 流水线、测试夹具和秘密的版本标识；
- submodule、LFS 对象或仓库外部制品。

路径策略应该从构建图和所有权关系生成或至少交叉验证。共享输入变化触发全部消费者；路径策略自身变化触发完整检查；无法确定依赖时采用保守检查集。

目标分支已经包含的新共享配置，通常不会出现在“候选相对目标”的 changed paths 中，但它仍参与候选构建。也就是说，路径列表可以只显示 payment 文件，而候选的 payment 已经在新构建配置下运行。组合测试不能因为 shared path 不在本次 diff 中就省略。

### 一个稳健的选择结果需要解释

每次运行都应保存：比较的两个或三个对象 ID、merge-base、原始 NUL 路径清单、路径策略版本，以及每个检查为何被选中或跳过。这样规则误配时才能回放。

只保存“payment-test skipped”不够；要能回答是没有相关路径、策略显式排除、上游检查失败、平台取消，还是 runner 根本没有启动。跳过不是成功的同义词。

建议为路径规则准备表驱动测试，覆盖共享文件、重命名、删除、子模块更新、策略文件自身变化和空 diff。定期运行不带路径过滤的全量基线，并比较漏测率、时延和资源成本。

## 检查结果必须绑定候选与检查身份

一条可用于保护规则的检查结果至少包含：

```text
repository
candidate_commit
candidate_tree
check_identity
pipeline_definition
path_policy_version
attempt
result
started_at / finished_at
log_and_artifact_locations
```

`check_identity` 不能只是一段可由任意低权限工作流随意复用的显示名称。平台配置要确认哪些应用或工作流有权报告这个检查，保护规则匹配名称、发布者还是更强身份，以及改名后会发生什么。

平台状态很多，正文可先归入四类：

| 抽象状态 | 含义 | 保护规则默认态度 |
| --- | --- | --- |
| 满足 | 对精确候选和有效策略完成并成功 | 可以作为一项通过证据 |
| 失败 | 检查执行并发现问题 | 阻止，修复或按受控例外处理 |
| 未执行 | 路径跳过、条件不满足或没有调度 | 只有策略明确允许时才视为满足 |
| 不确定 | 等待、取消、超时、基础设施异常、结果过期 | 不应当作成功 |

不同平台会用 success、skipped、neutral、canceled、timed out 等名称，映射必须在测试仓库实测并登记日期。基础设施失败和测试失败的责任人不同，但二者都没有提供“代码可合并”的正面证据。

功能分支新推送、目标基线变化、流水线或路径策略变化后，哪些结果过期必须是显式规则。重新运行同一候选可以生成新 attempt，不能删除旧失败来制造从未失败过的时间线。

## 为什么两个绿色变更仍可能不能连续合并

假设 P 和 S 都基于主线 T，各自在临时合并到 T 后通过：

```text
      P
     /
----T
     \
      S
```

如果 P 先进入主线，S 的真实前序状态不再是 T，而是包含 P 的 Q1。S 必须在 Q1 上形成新候选 Q2。即使 Git 合并没有文本冲突，P 与 S 仍可能在运行行为、生成代码、依赖或测试资源上冲突。

```text
      P
     / \
B---T---Q1---Q2
 \            /
  S----------/
```

图只是概念示意；平台可以使用合并提交、rebase、squash 或批量候选。不可缺少的约束是：后一个候选必须包含前序即将落地主线的状态，检查结果绑定这个新候选。

## 合并队列是有条件的引用更新协议

一个最小队列循环可以描述为：

1. 读取目标引用当前值 T，并固定第一项功能头 P；
2. 生成候选 Q1，记录其基线 T、输入 P 和 tree；
3. 对 Q1 运行必需检查；
4. 若全部满足，只有目标仍为 T 时才推进到 Q1 或平台定义的等价最终对象；
5. 以新的主线状态为基线，为下一项 S 生成 Q2；
6. 目标被队列外身份更新、功能头变化或策略变化时，使相关候选过期并重建。

Git 本地的 `update-ref` 可以演示“期望旧值”条件。下面只允许在脚本创建的临时仓库、且当前没有检出 `main` 时运行；两个变量必须由队列实验提供：

```bash
expected_old_commit="${QUEUE_EXPECTED_OLD:?QUEUE_EXPECTED_OLD is required}"
new_commit="${QUEUE_CANDIDATE:?QUEUE_CANDIDATE is required}"
git update-ref refs/heads/main "$new_commit" "$expected_old_commit"
```

它只在本地仓库 `main` 当前仍等于 `expected_old_commit` 时更新为 `new_commit`，否则失败且不移动引用。成功通常没有输出，失败会返回非零并保留旧引用。命令会改变本地分支，是高风险 plumbing 操作；本书只在临时实验仓库运行，恢复方式是让实验的 `trap` 删除整个临时目录，不把它用于真实主线。它不能模拟平台的评审、权限、服务端 hooks、分布式锁或最终合并方法。

队列还要定义：

- 单项还是批量候选，批量失败后怎样定位和拆分；
- 优先级、公平性、超时、暂停和饥饿处理；
- 功能分支更新后队列位置是否保留；
- 不稳定测试重跑次数和隔离规则；
- 管理员/事故变更怎样插队，谁批准并怎样审计；
- 队列生成的临时引用、提交和日志保留多久；
- 最终主线提交不同于被测候选时怎样证明等价或重跑。

“启用合并队列”不是完整政策。没有失败归因、绕过和过期规则，队列会成为新的不可解释等待区。

## 目标分支或功能分支变化时怎么办

| 变化 | 受影响状态 | 默认动作 |
| --- | --- | --- |
| 功能头 F1 → F2 | 所有基于 F1 的候选和结果 | 取消未完成运行，保留证据，以 F2 重建 |
| 目标 T1 → T2 | 所有以 T1 为基线且尚未落地的候选 | 按队列策略重建，不能只改基线字段 |
| 路径策略变化 | 检查选择结论 | 用新策略重新选择；策略自身须通过高信任评审 |
| 流水线定义变化 | 检查过程身份 | 生成新 attempt，记录定义来源；不覆盖旧结果 |
| 检查名称变化 | 保护规则匹配 | 先验证新旧报告与规则切换，避免永久 pending 或无保护窗口 |
| 紧急绕过 | 审批、引用更新和部署链 | 保存被跳过规则、旧/新 ID、批准人和后补验证 |

平台可能自动完成其中部分动作，但组织仍要验证实际行为。特别要测试 force-push、目标分支快速连续更新、队列中途修改检查配置和管理员直接更新四种路径。

## 平台上线前的验证清单

在专用测试仓库和非生产规则集上记录：

1. 事件载荷中的功能头、目标头和候选提交分别是什么；
2. 检查跑在功能头、临时合并还是队列候选；
3. 新推送和目标前进后，旧检查是否自动过期；
4. skipped、canceled、timeout 和基础设施失败如何映射到保护规则；
5. 路径过滤没有命中时，必需检查会处于什么状态；
6. 两个同时绿色的变更按不同顺序入队会生成哪些对象；
7. 队列候选与最终主线对象是否相同，不同时如何验证；
8. 批量失败、重跑、插队和绕过留下哪些审计事件；
9. 哪些身份能报告同名检查、修改队列和绕过保护；
10. 功能所需版本、许可、权限和计费影响。

结果写入 `docs/FACT-REGISTER.md` 对应厂商条目后，才能把实例加入正文。界面截图只能辅助，不作为长期语义来源。

## 常见故障怎样分流

| 症状 | 先收集 | 恢复方向 |
| --- | --- | --- |
| 修改了代码却没有触发 CI | old/new ID、事件投递、路径清单、策略版本 | 修复触发或路径依赖；对遗漏候选补跑 |
| 必需检查永久等待 | 候选 ID、检查名称、是否被跳过、报告者身份 | 恢复正确报告或规则映射，不临时把所有检查设可选 |
| 旧提交成功被显示在新提交上 | 检查绑定的 candidate、平台复用规则 | 让新候选重新运行，调查状态关联错误 |
| 队列不断重建 | 目标外部更新、功能头变化、不稳定测试、策略变更 | 限制绕过写入，隔离 flaky 检查，记录重建原因 |
| 队首失败阻塞所有人 | 失败类型、批次内容、重试历史 | 移出或拆分失败项，保持其证据；不重排到无法复现 |
| 合并后主线变红 | 被测候选与最终提交、合并顺序、路径选择 | 停止后续合并，重现最终对象，按共享历史和发布策略修复 |

主线变红不一定说明队列无效，也可能是检查漏项、外部依赖漂移或最终提交与候选不等价。复盘必须比较对象和输入，不能只比较工作项编号。

## 隔离实验验证了什么

在本书仓库根目录运行：

```bash
./scripts/verify-ci-trigger-queue.sh
```

脚本要求 Bash、Git 2.28 或更高版本和可写临时目录。它创建本地临时仓库，不读取用户级 Git 配置、不连接网络，也不修改蓝皮书仓库。

实验从共同基线创建 payment 与 search 两个功能头，并用含换行符的文件名验证 `--name-only -z` 能保留路径字节边界，再让 `main` 的共享构建配置前进。三点 diff 分别只显示各功能路径，但合并候选 tree 已包含新共享配置，证明 changed paths 不能描述候选全部输入。

脚本先生成 search 基于旧主线的候选，再构造 payment 队列候选 Q1 和 search 基于 Q1 的 Q2。它断言旧 search 候选既不等于 Q2，也不是 Q2 的祖先，tree 还缺少 payment 变化。最后用带期望旧值的 `update-ref` 让 main 从 T 推进到 Q1；使用过期 T 更新 Q2 必须失败，改用 Q1 作为期望值后才成功。

成功时最后输出：

```text
CI path selection, stale candidate, queue order, and conditional ref updates passed.
```

实验使用 Git 合并提交和本地引用，只证明提交图与条件更新语义。它不能证明托管平台如何创建临时提交、报告检查、实现队列锁、处理批次、授权绕过或计费。真实平台结论必须来自带日期的测试记录。

## 小结

触发器决定为什么开始，候选生成决定测试什么，路径策略决定运行哪些检查，合并队列决定多个绿色变化以什么顺序重新组合。四层都必须绑定对象 ID 和策略版本。

路径列表只是候选输入差异，不是完整依赖图；旧候选成功不能证明新队列位置；引用更新必须以被测试基线仍然有效为条件。只有这些约束同时成立，受保护分支上的“绿色”才具备可解释的工程含义。
