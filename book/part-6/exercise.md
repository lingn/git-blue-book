# 综合场景：从线上缺陷到发布复盘

线上结算任务出现重复执行。开发主线近期有十几条提交，稳定发布分支落后，manager 和 worker 使用同一个公共任务 SDK。

## 一、固定事故基线

记录线上制品摘要、对应提交、配置和发生时间。不要先假设最新提交就是根因。

用稳定请求或测试重现问题，确定已知正常与已知异常提交，再执行二分：

```bash
git bisect start
git bisect bad <线上提交ID>
git bisect good <已知正常提交ID>
```

逐个测试，找到首个坏提交后 `git bisect reset`，使用 `git show` 和历史搜索验证因果。

## 二、形成独立修复

从团队规定的热修复基线创建分支。修复重复执行并增加回归测试，提交应同时表达幂等策略和兼容边界。

若修复先在开发分支完成，检查依赖后挑选到发布分支：

```bash
git cherry-pick <修复提交ID>
```

记录来源 ID、目标 ID、冲突处理和测试结果。

## 三、判断部署范围

检查差异所在模块和依赖树。因为 manager 与 worker 都加载修改后的公共 SDK，只部署 manager 不能让 worker 使用新逻辑；两类进程都需要新制品。

如果 worker 正在执行任务，先停止领取新任务，等待或迁移活跃任务，记录超时与补偿，再滚动替换。manager 是否也需要连接排空取决于请求和会话模型。

## 四、发布与回滚预案

为验证通过的发布提交创建新标签并绑定不可变制品。预案同时写明：

- 可以直接回退的旧制品；
- 数据和消息格式是否向后兼容；
- 必要时使用哪个 revert 提交重新构建；
- 任务重复执行怎样检测和补偿。

## 五、验证线上状态

分别核对 manager、worker 实例实际运行的制品摘要，不只看发布平台显示“成功”。观察新任务、存量任务、失败率、重复率和积压。

## 六、复盘记录

```text
根因提交与证据：
修复来源/目标提交：
冲突及双方意图：
影响模块和部署组件：
优雅停机与任务处理：
测试及线上验证：
回滚条件和执行结果：
需要补充的保护规则：
```

这个场景的关键不是使用了多少 Git 命令，而是提交图、代码依赖和运行状态三类证据彼此一致。
