# 写作规范

## 1. 首次出现规则

任何术语、命令、选项或符号在首次出现时，都必须满足：

1. 先说明它要解决的问题。
2. 用普通语言建立直觉。
3. 给出本书后续保持一致的工作定义。
4. 说明它依赖的前置概念，并确认前文已介绍。
5. 命令出现时解释输入、作用对象、状态变化和输出。

标题、学习目标、图注和练习题同样受此规则约束，不能在正文解释前提前堆叠术语。

## 2. 命令写法

- 主线优先使用职责更清晰的 `git switch` 和 `git restore`。
- `git checkout` 放在兼容旧教程和旧环境的章节中对照解释。
- 不展示无法直接运行的省略命令；变量使用清晰占位符并解释如何替换。
- 每个高风险命令都标记前提、影响范围、验证方法和恢复路径。
- 不把 `git pull`、`git reset --hard`、`git push --force` 写成无条件快捷方案。

## 3. 实验规范

每个实验必须说明：

- 当前目录和初始状态
- 将要执行的命令
- 关键输出，不依赖完整逐字一致
- 状态变化如何验证
- 如何清理或回到实验起点

涉及历史改写和恢复的实验必须在专用沙盒仓库中进行。

## 4. 公开发布边界

- 公司名、内部项目名、仓库地址、真实提交哈希、Jira 信息和同事身份全部匿名化。
- 案例保留技术因果链，替换业务专有信息。
- 不复制来源不明的图、表或大段文本。
- Git 的历史和行为结论优先核对官方文档、Git 源码文档或可复现实验。

## 5. 章节结尾

章节结尾按需选择，不要求全部出现：

- “小结”：收束本章建立的模型。
- “动手试试”：一个短小、可恢复的实践任务。
- “遇到这种情况怎么办”：链接到后续恢复章节。
- “下一章”：说明为何自然需要下一个概念。

不使用“验收题”作为每章固定标题。综合能力检查放在每篇末尾，并提供判断过程。

## 6. 质量检查

- 术语首次出现审计
- 命令首次出现审计
- 本地链接与 GitBook 导航检查
- Shell 命令可执行性检查
- 高风险操作恢复路径检查
- 示例输出与当前 Git 版本核对
- 中文标点、代码格式和匿名化检查
